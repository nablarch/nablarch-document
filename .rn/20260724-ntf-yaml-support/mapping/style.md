# NTF解説書 トンマナ規約

## 1. 適用範囲と file:line の基準

本書は、`design.md`「8. トンマナ」が定めた8観点について、FW解説書のライブラリ
（`ja/application_framework/application_framework/libraries/`、以下 `FW:`）から
記述の調子を抽出し、ページ作成時にCCが従う基準として定めたものである。

`FW:` の行番号の基準は作業ツリーである（`mapping/glossary.md` §1 と同じ記号体系）。

本書の役割は「ページ作成時にCCが従う基準」であり、網羅性を追求する対象ではない。
観点は次の13個に限定する（S-01〜S-08は`#4`確定時点の8観点、S-09・S-10は
2026-08-06の`/rn:gm`フィードバックを受けて追加、S-11は`#9`で追加、S-12・S-13は`#28`で追加）。文の長さ・改行位置・図の配置・括弧の全角半角・英数字と日本語の間の空白・
送り仮名や漢字/かなの揺れなど、機械判定できない規則性は対象外とし、本書には記載しない。

## 2. 規約一覧

### S-01 文体（だ・である調）

**規約**: 本文はである調（常体）で書く。「〜である。」「〜する。」「〜行う。」で文を終える。
「です・ます」調は使わない。

**根拠**:

- `FW:libraries/exclusive_control.rst:10` 「この機能では、データベースのデータ更新に対する排他制御を行う。」
- `FW:libraries/exclusive_control.rst:18` 「この機能は、以下の理由により **非推奨** である。」
- `FW:libraries/static_data_cache.rst:8` 「データベースやファイルなどに格納した静的データへのアクセスを高速化するためのキャッシュ機能を提供する。」
- `FW:libraries/session_store.rst:169` 「テーブル名およびカラム名は変更可能である。」

「です・ます」調が使われている箇所は、確認した範囲（`exclusive_control.rst`、`date.rst`、
`session_store.rst`）で1件も見つからなかった。

### S-02 ページのセクション構成

**規約**:

- 各ページは、目次（`.. contents::`）の直後に、見出しの無い**リード文**を置く。そのページで何ができる
  ようになるか、何を説明するページかを述べる。
  - リード文は最初のL2見出しより**前**に置く。L2見出しの直下に置かない。
  - リード文は「機能概要」の代わりではない。「機能概要」を持つページでも、その前にリード文を置く。
  - `.. toctree::` のみで構成される表題ページ（`setup/index.rst`・`implementation/index.rst`・
    `tools/index.rst`・`index.rst`）には適用しない。
  - 他ページへ送るだけの導線ページ（`setup/request_unit_test/db_queue.rst`・
    `implementation/request_unit_test/db_queue.rst`・`implementation/deal_unit_test/db_queue.rst`）にも
    適用しない。いずれも「ラベル → タイトル → 導線の1文」の6行で、L2セクションを持たないため、
    リード文と導線文が同一になる（S-09の適用外と同じ3ページ。実測、2026-08-16）。
  - 文頭を「ここでは、」で始めない。リード文はページ全体を指すため「ここ」の指す範囲が曖昧になる。
    FW解説書のリード文と同じく、対象を主語に立てて言い切る（下記「根拠（リード文の位置と書き出し）」参照）。
- 第2部のページは「使用方法」のみ必須とし、「機能概要」「拡張例」は出典が無い場合は見出し自体を
  置かない。置く場合は「機能概要 → 使用方法 → 拡張例」の順に並べる。
- 第3部のページは「機能概要 → 使用方法」の順に並べる（拡張例の見出しは置かない）。
  - 第2部と同じく、**「機能概要」は出典が無い場合は見出し自体を置かない**（`#28` §3-1）。第3部で必須なのは
    「使用方法」だけである。
  - `design.md`「4. 第3部 テストの実装方法」＞「ページのアウトライン」節が挙げる「使用方法」配下の5つ
    （テストクラスを作成する／テストメソッドを作成する／テストデータを作成する／テストを実行する／
    テスト結果を確認する）は、**標準的な手順の並びであって、全ページに5つ揃えることを求めるものではない。**
    「使用方法」配下のL3は出典にある手順がそのまま見出しになり、出典に無いL3は立てない
    （`ntf-doc-27-small-3rd.md:26`・`:28`）。
  - 例外は次の2ページである（いずれも `design.md` §4 による）。
    - 「テストデータの書き方」は「機能概要 → テストデータの構造 → 使用方法」の3セクション構成とする。
    - 「テストデータの記載例」は「機能概要」も「使用方法」も持たず、記述例の見出しをL2として
      並べる構成とする。ページ全体を対象にした導入文が出典に存在しないため機能概要を持たず、
      また記載例が並ぶだけのページであり「使用方法」という1つの説明を持たないためである。
- 第4部のページ（`tools/` の4ページ）は「機能概要 → 導入 → 使用方法」の順に並べる。「導入」は、配布物の
  展開・依存関係の取得・起動設定など、ツールを使う前に一度だけ行う作業があるツールにのみ置く（`design.md`
  「5. 第4部 ツール」＞「ページのアウトライン」節）。「拡張例」「モジュール一覧」の見出しは置かない。
  - 「前提事項」は、「導入」を持つページでは「導入」配下の**先頭**のL3に、持たないページでは「機能概要」
    配下の**末尾**のL3に置く（`glossary.md` §5.13 の「前提事項」の定義と対応する）。
- 第2部・第3部のいずれのページにも「モジュール一覧」の見出しは置かない。処理方式固有の依存関係は、
  それを必要とする当該ページ（第2部・第3部）の「機能概要」または「使用方法」配下で個別に触れる。

この構成は `design.md` の「3. 第2部 導入と設定」＞「ページのアウトライン」節、および
「4. 第3部 テストの実装方法」＞「ページのアウトライン」節の決定に基づく。`design.md` は
更新が続く文書のため、行番号ではなく節見出しで指す。

FW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）の一般的なページは
「機能概要 → モジュール一覧 → 使用方法 → 拡張例」の4セクション構成である（下記「根拠（セクションの
並び順）」参照）。しかしNTF解説書はこの型をそのまま採用しない。`design.md` の「モジュール一覧は第1部に
置かない。「稼動環境」は対応バージョンの premise 1文＋`:ref:`のみとする」節は、第1部の「稼動環境」を
対応バージョンの1文のみとし、依存関係のモジュール一覧はどのページにも一覧として置かないと決めている。
処理方式固有の依存（RESTfulウェブサービスの `nablarch-testing-rest` 等、YAML形式の
`nablarch-testing-yaml`）は、当該ページ（第2部・第3部）にのみ記載し、第1部には集約しない。
そのため第2部・第3部のページには「モジュール一覧」の見出し自体を置かない。処理方式固有の依存がある
場合のみ、当該ページの「機能概要」または「使用方法」配下で個別に触れる。

拡張できる内容が無い機能（第2部のみ。第3部には「拡張例」の見出し自体を置かない。`design.md` の
「4. 第3部 テストの実装方法」＞「ページのアウトライン」節「拡張例は第3部に置かない。」）では、
「拡張例」の見出し自体を置かない。

**根拠**（design.mdの決定）:

- `design.md`「4. 第3部 テストの実装方法」＞「ページのアウトライン」節。第3部ページのアウトラインは

- 同節「拡張例は第3部に置かない。拡張はコンポーネント設定とクラス差し替えであり、アーキテクトの

### S-03 セクションタイトルの形式（「〜する」形式）

**規約**: 「使用方法」「拡張例」配下の小見出しは、動詞終止形の「〜する」で終える。
読者が見出しから目的の操作に直接辿り着けるようにする。

**根拠**:

- `FW:libraries/exclusive_control.rst:95` 「排他制御を使うために準備する」
- `FW:libraries/exclusive_control.rst:154` 「楽観的ロックを行う」
- `FW:libraries/exclusive_control.rst:381` 「悲観的ロックを行う」
- `FW:libraries/date.rst:143` 「システム日時を切り替える」（拡張例配下）
- `FW:libraries/date.rst:152` 「業務日付を切り替える」（拡張例配下）
- `FW:libraries/service_availability.rst` の「使用方法」配下 「サービス提供可否をチェックする」
  「サービス提供可否に応じて画面表示を制御する」

なお「機能概要」配下の小見出しは「〜できる」（能力を示す形。例: `FW:libraries/exclusive_control.rst:32`
「楽観的ロック/悲観的ロックができる」、`FW:libraries/static_data_cache.rst:20` 「任意のデータをキャッシュできる」）
や体言止めが使われており、必ずしも「〜する」形式ではない。「〜する」形式を適用するのは
「使用方法」「拡張例」配下の小見出しとする。

**追加規約（内容の条件、`#6`確定）**: 「〜する」形式は見出しの形式にすぎず、それだけでは
中身の一意性・可読性を保証しない。上記の形式規約に、以下の内容条件を加える。

- **ページタイトルとセクションタイトルの組で一意であり、かつその組だけで中身が分かること。**
  利用者は見出しを見て目的の情報に辿り着く。加えて Nabledge がセクションタイトルであたりを
  付けるため、タイトルが検索面そのものになる
- セクションタイトル単独での文書全体一意は不要。ページタイトルが処理方式名等を持つため、
  組で一意になる（`vocabulary.md` の確定34ページはすべて一意であることを確認済み）
- 「〜する」形式でも、`概要` / `補足` / `注意事項` / `その他` / `準備する` / `設定する` の
  ように、ページタイトルを足しても情報が増えない語は不可
- 同一ページ内でセクションタイトルを重複させない
- 出典の見出し（`目的別API使用方法` のような作成側の都合による名前）をそのまま使わない

**例外1（形式別L4対は重複禁止と「〜する」形式の対象外。`#9`確定）**: S-10 規約3 に従って立てる
`Excel形式の場合` / `YAML形式の場合` のL4見出し対は、上記「同一ページ内でセクションタイトルを
重複させない」の対象外とし、あわせて本節冒頭の「〜する」形式（動詞終止形）の対象外とする。
形式名を示す固定の見出し文言であるため体言止めのままとする。この見出し対は S-10 規約3 が定める
とおり、規約1に該当しない記述方法の説明があるL3にのみ置くものであり、全L3に置くものではない
（「テストデータの書き方」では10個のL3のうち8個が該当し、うち5個が「使用方法」配下にある）。
**ただし「テストデータの記載例」のように、全L3が「あるシナリオをExcel形式とYAML形式の両方で
示す」という同一の型を持つページでは、全L3に見出し対を置く**（`#10`確定。同ページは28個の
L3すべてが該当する）。

重複を許す根拠は次の2点である。Nabledge の検索の入口となる `knowledge/index.md` に現れるのは
level 2 と level 3 だけで level 4 は現れないため、この重複によって検索面の一意性が損なわれる
ことはない（`nablarch/nabledge` の `main`、2026-08-06 時点で確認）。S-11 のとおりページが選定
された後のフェーズでは L4 も候補になるが、その段階の読者はページ本文に到達しており、ページ内の
`.. contents::` 目次では各L4が親L3の下にネストされて表示されるため、どのL3の形式別記述かを位置で
判別できる（`_build/html/development_tools/testing_framework/implementation/testdata_notation.html`
の目次で実測）。

**例外2（構造セクション配下は体言止め。`#9`確定）**: 「〜する」形式を適用するのは
「使用方法」「拡張例」配下の小見出しであり、「テストデータの書き方」の `テストデータの構造`
配下（`design.md` §4 で定めた第3部の唯一の例外セクション）は対象外とする。構造セクションが
答えるのは「これは何か」という問いであるため、体言止めにする（`テストクラスとテストデータの対応`・
`データブロックとデータタイプ`・`グループIDによる使い分け`）。

**例外3（ページ単位の作業指示がセクションタイトルを名指しした場合は、その指示を優先する。`#28`確定）**:
`ntf-doc-27-small-3rd.md` のようにページ単位でセクション構成を指定した作業指示が、
セクションタイトルの文言まで名指ししている場合は、本節の内容条件よりその指示を優先する。
優先してよいのは、**指示が出典の構成を実際に見たうえでページ単位に決めたものである場合に限る。**
優先した箇所は、後から規約違反と区別できるように、指示のファイル名と行番号を `checks/` に記録する。

実例: `implementation/deal_unit_test/web.rst:22` 「テストを準備する」・`:30` 「テストを実施する」は、
本節の内容条件のうち「ページタイトルを足しても情報が増えない語は不可」（`準備する` / `設定する` と同型）に
該当するが、`ntf-doc-27-small-3rd.md:129-132` が4本のL3の文言を名指ししているため、そのままとする。
同指示 `:135` は出典の体言止め（「テスト準備」「テスト実施」）を「〜する」形式へ書き換えると
明記しており、出典の構成を見たうえでの指定である。

### S-04 見出しのアンダーライン記法とレベル対応

**規約**: 見出しのアンダーライン記号とレベルの対応は次のとおりとする。

| レベル | 記号 | 用途 |
|---|---|---|
| L1（ページタイトル） | `=` | ページ全体のタイトル1つのみ |
| L2（大セクション） | `-` | ページの大セクション。構成は `S-02` による |

### S-07 表の記法

**規約**: 2〜3列程度の短い説明表は simple table（`====` の区切り線）を使う。
セル内に複数行の説明や `:ref:` を含む長文が入る表は `list-table` を使い、`:widths:` で列幅を指定する。
grid table（`+---+` 形式）は使わない。

**例外（表が多く、セルにコードリテラルと日本語が混在するページは `list-table` に揃える。`#9`確定）**:
1ページ内に表が多数あり、かつセル内でコードリテラル（半角）と日本語（全角）が混在する表が
大半を占めるページでは、短い2列表であっても `list-table` に揃えてよい。
`=` のみで罫線を引く simple table は、セル文字列の列位置を「表示幅」（全角2・半角1）で
揃える必要があり、文字数基準で詰めると `sphinx-build` が `Malformed table` エラーを出す
（`steering.md` Rules に実測記録あり。2026-08-03、`about/index.rst` の表で実際に発生）。
半角と全角が1セル内で混ざる表が多いページでは、この幅合わせの保守コストが表の数だけ積み上がる。

適用実績: 「テストデータの書き方」（`testdata_notation.rst`）は表34件すべてが `list-table` で
simple table は0件である（実測）。34件のうち `:ref:` を含むセルは0件であり、規約本体の基準だけで
判断すると「短い2列表」に該当するもの（処理方式/対応クラス、値の指定/記述方法、用語/定義など）が
複数含まれるが、本例外により現状の形を正とする。承認済みの `about/index.rst`（`#8`）は
simple table 3件・`list-table` 1件であり、表が4件と少ないため本例外の対象にならない。
本例外は、**Excelのセル内容を格子状に示す表を多数持つページ**にも適用する（`#10`確定）。
この種の表はセル内容が例示データそのものであり、半角の識別子・数値と全角の日本語データが
行ごとに入れ替わるため、コードリテラルを含むか否かにかかわらず表示幅の保守コストが
表の数だけ積み上がる。「テストデータの記載例」（`testdata_examples.rst`）は表50件超が
すべてこの型であり、`list-table` に揃える。
**本例外の適用はページ単位で判断する**（同一ページ内で表ごとに記法を使い分けない）。

**規約（表の中のクラス名は コードリテラル と `:java:extdoc:` のどちらで書くか。`#28`確定）**:

  （地の文の規範は `reviews/page-class_unit_test.md:120`「散文中のクラス名は
  ``:java:extdoc:`単純名 <完全修飾名>`` で書く」）。

### S-09 各ページ先頭の目次（`.. contents::` ディレクティブ）

**規約**: 複数のL2セクション（「機能概要」「使用方法」等、`-` の下線）を持つページは、
ページタイトルの下線の直後（本文・イントロ段落より前）に次の3行を置く。

```
.. contents:: 目次
  :depth: 3
  :local:
```

ページ先頭にラベル（`.. _xxx:`）がある場合は、ラベル→タイトル→目次の順とする。

**適用しないページ**: L2セクション（`-` の下線）を1つも持たないページ。`:local:` はページ内の
セクション見出しにのみリンクするため、セクションを持たないページに置いても空の目次になり
意味がない。NTF解説書では次の7ページが該当する。

- `.. toctree::` のみで構成されるランディング/インデックスページ4件
  （`index.rst`・`setup/index.rst`・`implementation/index.rst`・`tools/index.rst`）
- 他ページへ送るだけの導線ページ3件（`setup/request_unit_test/db_queue.rst`・
  `implementation/request_unit_test/db_queue.rst`・`implementation/deal_unit_test/db_queue.rst`）。
  いずれも「ラベル → タイトル → 導線の1文」の**6行**で、L2セクションを持たない（実測、2026-08-16）

**根拠**:

- `FW:libraries/exclusive_control.rst:1-8`、`FW:libraries/date.rst:1-6`、

### S-10 Excel形式/YAML形式の書き分け方

NTF解説書の読者は、実際にはExcel形式かYAML形式のどちらか一方しか使わない
（プロジェクトで採用した形式で書く）。両方を比較したい読者は少数派であり、
「Excel列・YAML列を左右に並べた比較表」を毎回読ませる構成は、片方の形式しか
使わない大多数の読者に無関係な列を読み飛ばす負担を強いる。そのためNTF解説書
では、**比較して伝える意味がある内容だけ共通の地の文・比較表とし、それ以外の
「Excel形式ではどう書くか」「YAML形式ではどう書くか」という記述方法の説明は、
Excel専用・YAML専用に分けて書く**（`design.md`§4、`testdata_notation.rst`が
代表例。FW解説書には存在しない構成のため本節を追加した）。4つの規約からなる。

**規約1（比較して伝える価値があるものだけ共通にする）**: 以下に該当する内容
だけを、Excel/YAML両方に触れる地の文または比較表として書く。それ以外の
「記述方法」の説明は規約3に従いExcel専用/YAML専用に分ける。

- 両形式の対応関係そのものを理解しないと概念が掴めないもの（例: 「Excelの
  1シート＝YAMLの1ファイル＝読み込み単位」という粒度の対応）
- 片方の形式の挙動・制約が、もう片方の形式の実装上の理由に由来するという
  関係性の説明（例: 「Excel形式は上から順に読むため交互記述ができない。
  YAML形式はトップレベルキーごとに独立して読むためこの制約がない」）

**規約2（識別子行は表の中に含める）**: Excelのセル格子を表す表では、
識別子行を表の1行目に含める。2列目以降は空セルにする（`- ` のみを書く）。

- **「Excelのセル格子を表す表」とは**、シートに実際に並ぶセルの配置を
  そのまま写した表を指す。列見出しと説明を対にした説明表（例:
  「値の指定／記述方法」「カラム名／説明／必須」）はこれに当たらない。
  説明表は本規約の対象外であり、通常どおり `:header-rows: 1` とする
- **複数のデータタイプに共通する規則を示すための断片は、識別子行を持たなくてよい。**
  識別子を1つ選ぶと、その規則が特定のデータタイプ専用であるかのように読めてしまう
  ためである。特定のデータブロックの記述例を示す表には、識別子行を含める
- **セル格子を表す表は `:header-rows: 0` とする。** Excelのシートに
  見出し行という概念はなく、識別子行・列名行・データ行はいずれも同じ
  セル行だからである。構造行とデータ行の区別は地の文で説明する
- 識別子行のほかに、**ディレクティブ行・レコード種別行・データ型行・
  フィールド長行のようにシート上に実在する行がある場合は、それらも
  すべて表に含める。** 「名前・値」形式の行（ディレクティブ行・
  フレームワーク制御ヘッダ行）は、1列目に名前、2列目に値を置き、
  3列目以降を空セルにする
- コメント行（`//` で始まる行）・マーカーカラムのように、シート上に
  実在するものは表に含めてよい
- 表の直前の地の文には、識別子の**意味**（何のデータブロックか、識別子の
  値が何を指すか）だけを書く。**「どの行に続けて記述するか」という並び順の
  説明は表が示すため、地の文に重ねて書かない**
- **セル結合は使わない。** セル結合（HTMLの`colspan`相当）は、本書が使用する
  docutils 0.15.2では`list-table`が非対応（短い行を書くと`Malformed table`
  エラー）であり、RSTのgrid table（`+---+`形式）はS-07が既に禁止している。
  識別子を1列目に置き2列目以降を空セルにすれば、セル結合は不要である

**規約3（Excel専用/YAML専用にはL4見出しを使う。太字ラベルは例外的にのみ使う）**:
規約1に該当しない「記述方法」の説明は、共通の地の文の後にL4見出し
（`S-04`の`^`の下線）で「Excel形式の場合」「YAML形式の場合」の2小見出しを
立て、それぞれの下に該当する表・コードブロック・地の文をまとめる。1つの
L3セクションにこの見出し対は1組だけ置く（同じL3内でExcel/YAMLの記述方法の
説明が複数の話題にわたる場合も、2組目の見出し対を作らず、その1組の下に
まとめる。同一見出しがセクション内で複数回現れると`.. contents::`目次で
見分けが付かなくなるため）。
**形式別のL4対は、そのL3の末尾2つに置く。用途別・規則別のL4がある場合は、
それらを先に置く。** 読者が自分の形式の記法を、どのL3でも同じ位置（末尾）で
見つけられるようにするためである。
太字ラベル（`**Excel\ 形式**` ／ `**YAML\ 形式**`）は、以下の場合に限り例外的
に使う。いずれも「見出しを追加できない/追加する価値がない」場合であり、
太字か見出しかを分量の多寡だけで選ばない（過去に「短い一対は太字、長い一対は
見出し」という基準を試したが、同じページ内で見出しと太字が混在し
「区切りの探し方がセクションごとに変わる」というユーザー指摘を受け撤回した）。

- 既にL4見出しの下（`testShots本体を記述する`など）にあり、RSTの見出し階層上
  これ以上下の見出しレベルを追加できない場合
- 形式別のL4対を持つL3の共通部（L3見出しから最初のL4までの範囲）で、短い記述方法の
  違いに触れる場合（例: ディレクティブの書式）。形式別のL4対はそのL3の末尾2つに
  固定されるため、共通部の記述は必ずL4対より前に位置する。同じL3に2組目のL4見出し対を
  作らない代わりに太字1文で済ませる
- 形式別のL4対を持たないL3で、短い記述方法の違いに触れる場合（例: コメント記号、
  マーカーカラムの対象データタイプ）。該当するL3は「テストデータの書き方」の
  `コメント・マーカーカラム・空エントリを扱う` のみであり、そのL3が形式差に触れるのは
  **6箇所**である（`#9`ラウンド7で全件走査。太字ラベル2件・コメント記号の対比・
  空エントリの判定・整形/補完の表のセル2件）。触れる箇所が少ないことを条件にはしない。
  形式差がいずれも1文以内に収まり、かつ規則（コメント／マーカーカラム／空エントリ）ごとに
  分散していて、形式別L4対に分けると規則単位の説明が分断されるためである
  （分割の是非は`#10`以降で判断する）

**規約4（識別子行は普通の文字で書く）**: 識別子行は、コード書式（`` ` ``）を
使わず、他の例示セル（カラム名・値など）と同じ普通の文字で書く。規約2に従って
表のセルに書く場合は、囲みを付けない（例: `SETUP_TABLE=テーブル名`）。表に含め
られず地の文で識別子に言及する場合（例: レコード定義を持たない空ファイルのように
表を持たない記述例）は、読みやすさのため和文引用符「」で囲んでよい
（例: 「SETUP_TABLE=テーブル名」）。

**規約5（Excel形式の図しか無い場合は形式を明示する）**: 記載例をExcel形式の図
（`.. image::`）でしか示せない場合は、**図の直前の本文で「Excel形式で示す」と明示する。**
図だけを置くと、YAML形式を使う読者が自分の形式の記載例と読み違えるためである。
規約3のL4見出し（「Excel形式の場合」）を立てられる箇所では、見出しで示せば足りる。

**技術的注意（RST構文）**: `**語**` の直後に空白を挟まず日本語が続く場合
（例: `**Excel形式**では`）、docutils が `Inline strong start-string
without end-string` 警告を出すことがある。閉じ `**` の直後に `\ `
（バックスラッシュ+半角スペース）を置いて回避する（例: `**Excel\ 形式**\ では`）。

**由来**: 2026-08-06、`testdata_notation.rst`のSETUP_TABLE例・SETUP_FIXED例に
対するユーザーの`/rn:gm`フィードバック3点（セル結合の検討・識別子行の書式・
Excel/YAML説明ブロックの視認性）を受けて追加。同日、ユーザーから3回にわたり
追加指摘を受け改訂した。(1)「ファイル構成と記述時の注意点を確認する」節に
Excel/YAMLの区切りがなく分かりにくい→太字ラベルを試したが、複数ブロックに
またがる長い説明では区切りとして機能しなかった。(2)「太字/見出しの使い分けが
セクションごとに違って混乱する」→太字とL4見出しの併用をやめ、L4見出しに統一
する方向とした。(3)「読者はExcel/YAMLどちらか一方しか見ない。比較表で毎回
両方読ませる今の構成に違和感がある」→比較して伝える価値がある内容（規約1）を
除き、ページ全体の比較表・比較文をExcel専用/YAML専用の地の文・表に分割した
（`testdata_notation.rst`の使用方法セクション全体を対象に実施）。
2026-08-07、`#10`のuser reviewで「セル格子の表から識別子行が抜けており、
表をそのまま写しても動くテストデータにならない」という`must`指摘を受け、
**規約2を差し替えた**（旧規約2「識別子行は表の外に出す」→ 新規約2「識別子行は
表の中に含める」）。旧規約2はセル結合が使えないことへの回避策として`#9`で
作ったものだが、識別子を1列目に置き2列目以降を空セルにすればセル結合は不要で
あり、回避策を残す理由がないため例外を足さず本文を差し替えた。規約4は旧規約2の
「表から出した識別子行」を前提にしていたため、実態に合わせて参照を改めた
（普通の文字で書くという規約の内容自体は変えていない）。
2026-08-16、`#28`§6-5の判断により**規約5を追加した**。NTF解説書内の前例は
`implementation/deal_unit_test/mom.rst:77`（「応答電文を2件記述した場合の例を\ Excel\ 形式で示す」）
の1件のみで（`grep -rn "形式で示す"`、`guide/`を除く全`.rst`の実測）、書き方が割れる余地があったため
規約化して揃える。
適用: `testdata_examples.rst`のセル格子47件・`testdata_notation.rst`の2件。

### S-11 L4見出しを持つL3セクションの導入文

**規約**: L4見出しを持つL3セクションは、最初のL4より前に、そのセクションが何を扱うかが
単独で読んで分かる導入文を置く。配下にどのようなL4があるかも導入文から分かる状態にする。

**根拠**: Nabledge の知識JSONはセクションをフラットに切り、L3の`content`に配下のL4の本文を
含まない。`nablarch/nabledge`の
`plugins/nabledge-6/skills/nabledge-6/knowledge/component/adapters/adapters-redisstore-lettuce-adaptor.json`
では、`s2`（level 3「設定内容」）の`content`が57文字の導入文のみであるのに対し、実体の2,802文字は
`s3`（level 4）側にある。導入文が薄いと、L3だけを切り出して読んだ際に情報がほぼ得られない。

なお、ページが選定された後のフェーズではページJSON全体が読まれるため、L4も候補にはなる
（同ページのJSONには`s3`・`s4`がlevel 4として存在する）。それでも、L3単独で切り出された場合に
何を扱うセクションかが分かることを本規約の要件とする。

**参照した時点**: 2026-08-06、`nablarch/nabledge`の`main`。

### S-12 キャプチャのUIロケールと本文のUI項目名

**規約1（既存のキャプチャは撮り直さない）**: 既に配置されているキャプチャのUIロケールは変更しない。
ページ間でロケールをそろえることも求めない。撮り直しはツールのバージョン差による画面差異を
持ち込むうえ、本刷新の対象（文章の刷新）ではないためである。

**規約2（同一ページ内でアプリケーションのUIロケールを混在させない）**: 1つのページに置くキャプチャは、
アプリケーション（Eclipse等）のUIロケールをそろえる。OSが表示するダイアログ（ファイル選択など）は
利用者の環境で決まるため、本規約の対象外とする。

**規約3（新規に撮るキャプチャは日本語ロケールで撮る）**: 本解説書に新しく追加するキャプチャは、

### S-13 日本語とインラインマークアップの境界（`\ ` エスケープ）

**規約**: インラインマークアップ（コードリテラル・`:ref:`・`:java:extdoc:`・`:doc:` など）の直前・直後に
**全角の文字**が来る場合は、`\ `（バックスラッシュ＋半角空白）を置く。仮名・漢字・全角英数だけでなく、
全角の約物（`、` `。` `・` `（` `）` など）も全角の文字に含める。半角の文字（英数字・記号・半角空白）や
行頭・行末が隣接する場合は置かない（置いても表示は変わらないため、本規約の対象外とする）。

判定方法: `guide/` を除く `.rst` から `` `` `` 囲みと `:role:` 記法を機械抽出し、直前・直後の1文字が
全角のときに `\ ` があるかを数える。

**実測**（2026-08-16、`guide/` を除く38ページ。インラインマークアップ2,159件の境界を数えた）:

- 直前が仮名・漢字等の全角文字: 564件すべて `\ ` 付き。付いていないものは0件。
- 直後が仮名・漢字等の全角文字: 1,255件すべて `\ ` 付き。付いていないものは0件。
- 直後が全角の約物: 383件が `\ ` 付き、付いていないのは `index.rst:13`（`` :doc:`setup/index`、 ``）の1件のみ。
- 直前が全角の約物: 512件が `\ ` 付き、185件が付いていない。内訳は
  `implementation/testdata_notation.rst` 128件・`implementation/testdata_examples.rst` 46件・
  `implementation/request_unit_test/batch.rst` 4件・`implementation/deal_unit_test/batch.rst` 2件・
  `implementation/deal_unit_test/http_messaging.rst` 2件・`about/index.rst` 1件・
  `implementation/class_unit_test/component.rst` 1件・`index.rst` 1件の8ファイル。
- 半角が隣接する場合: 直前799件・直後59件が `\ ` 無し、直前18件・直後30件が `\ ` 付きで割れている。
  表示が変わらないため規約の対象外とし、既存の記述も直さない。

**この規約に反する箇所は186件**（上記の185件＋`index.rst:13` の1件）である。全角の約物を全角の文字から
除く案も採り得るが、直後側が383件対1件で `\ ` を置く側にそろっている以上、直前だけを別扱いにする理由が
無いため、`\ ` を置く側に統一する。

# dest_part / dest_page / dest_section 語彙一覧

`mapping.csv` の `dest_part` / `dest_page` / `dest_section` に使ってよい値の一覧。
30バッチのプロンプトに埋め込む前に、この一覧が `design.md` と一致しているかを
確認するために先にコミットする。

`status` 列の意味:

- **確定** — `design.md` が確定として書いている値。`mapping/tools/extract_vocabulary.py`
  が `design.md` から機械抽出し、この一覧はその出力をそのまま転記したもの
  （再現方法は本ファイル末尾を参照）。
- **暫定** — 次のいずれかに該当する値。`#6`（未確定事項の確定）で正式な語彙に
  置き換わる。`#5` では暫定語彙の使用を許可するが、`#6` の完了条件は「暫定語彙を
  使用している行が0件であること」を機械検証する（`steering.md` #6 Completion
  criteria）。
  - `design.md` 自身が「暫定構成」「未確定事項」と明記している範囲
    （§3冒頭・§12 未確定事項#1・#2）に属する値
  - `design.md` 上は確定しているが、`dest_page` の値単体ではテスト種別
    （リクエスト単体テスト/取引単体テスト）を判別できないため、由来を保持する
    目的で処理方式名にテスト種別を付与した値（リクエスト単体テストの処理方式別
    6ページ。§4 ツリー図の子は本来テスト種別プレフィックスなしの処理方式名の
    みで確定しているが、`mapping.csv` はフラットな表でツリーの親子関係を保持
    しないため、`dest_page` の値自体に由来を持たせる。`#6` で design.md 記載の
    正式名称（プレフィックスなし）に一括置換する）

**例外: `HTMLチェックツール`は「導入」を持たない。** リクエスト単体テストに標準で
組み込まれ、テスト実行時に自動実行されるためインストール手順がない（design.md §5）。
`HTMLチェックツール`の行に`dest_section=導入`は使わない。

`design.md` の「ページのアウトライン」ツリーにある `<個別設定>する` /
`<拡張手順>する` / `<操作手順>する` のようなプレースホルダのサブ項目
（`テストを実行できるようにする` `コンポーネントを設定する` `テストクラスを作成する`
等の具体的な小見出しを含む）は `dest_section` の語彙に含めない。これらはページごとに
内容が異なり `design.md` がプレースホルダのまま定義していない（機械抽出できる確定値が
存在しない）ため。ページ作成時（`#8〜`）に各ページの `使用方法` セクション内で
個別に判断する。`#5` の `mapping.csv` では `dest_section` はこの14件のみを使う
（`HTMLチェックツール`の行を除く）。

## 再現方法

```
python3 mapping/tools/extract_vocabulary.py
```

`design.md` から機械抽出したときの件数を assert しているため、`design.md` が
更新されて構成が変わった場合はこのスクリプトが失敗する。失敗したら本ファイルを
再生成し、暫定語彙（処理方式ごとの仮ページ名を含む）を見直すこと。

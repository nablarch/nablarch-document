## 3. 守ること

- **解説書は直さない。** 解説書の記述が実装と食い違い、かつ**解説書側が誤っている**と判断した場合は、
  根拠（`file:line` と参照コミット）を添えて報告し、その項目は止める。自分で解説書を直しに行かない
- **`src/main` を変更しない**（user 判断 2026-08-26）。解説書と実装が食い違い、**解説書側が正しいと判断した
  場合も同じ**である。実装を直しに行かず、根拠を添えて報告して止める。理由は、`nablarch-testing` が既に
  リリース済みであり、実装を動かすと利用者の後方互換が壊れること
- **§4-2 では `src/test` も変更しない。** 不一致が疑われる現行挙動を特性テストで固定すると、
  誤っている疑いのある挙動を正解として確定させることになる。§4-2 の成果物は全件表と報告だけである。
  **§4-1 の特性テストと §4-3 のカバレッジのテスト追加は、この禁止の対象外**（いずれも user が扱いを確定済み）
- **`main`・`develop` は対象外。** PR ブランチ `convert-testdata-excel-to-text` 上で作業する。変更したら push する
- **事実には `file:line` と参照コミットハッシュを添える。示せないことは書かず「未確認」と書く**
- **1箇所確認した時点は、まだ根拠ではない。** 具体（文面・条件式・シグネチャ・API 呼び出し）が依存する処理を
  末端まで追う。「その処理が呼ばれている」ことを確認しても、後段で効果が打ち消されていないかは別に確かめる
- **確かめる手段があるなら、読むだけで済ませない。動かして確かめる**
- **既存のテストが緑であることを、変更が正しい根拠にしない。** 緑は「変更が正しい」証拠にも
  「そのテストが変更を検知していない」証拠にもなる
- 見つけた欠陥は、範囲外を理由に先送りしない。**ただし本指示の対象外と判定したものは §4-2 の表に記録する**

### 4-1. 論点4 —— フィールド数を超えた値を無警告で捨てる挙動の決着

#### ディレクターが実測した事実（`3c4bd2a`）

- `src/main/java/nablarch/test/core/file/DataFileFragment.java:102`-`:115`（`addValue`）と
  `:169`-`:183`（`addValueWithId`）は、いずれも `for (int i = 0; i < names.size(); i++)` でループを回す。
  引数 `line` の `names.size()` 番目以降の要素は読まれない
- 同ファイルにログ出力は0件（`grep -ci 'logger\|log\.'` が 0）。捨てた旨の警告も例外も無い
- 呼び出し元は4箇所。`src/main/java/nablarch/test/core/reader/DataFileParser.java:197`、
  同 `MessageParser.java:75`、同 `SendSyncMessageParser.java:129`・`:134`

#### 解説書側の事実（`40b9c52`）

- 解説書はこの挙動に**一切触れていない**。
  `grep -rn "数を超える\|超えた位置\|余り" ja/development_tools/testing_framework --include=*.rst --exclude-dir=_build`
  が **0件**
- かつて `implementation/testdata_notation.rst` にあった「フィールドの数を超える位置の値は読み込まない。」の1文は、
  解説書に書く基準（「利用者が正しく書こうとしても踏むもの」だけを書く。「間違えたときにどうなるか」は書かない）に
  照らして削除済み

#### user 判断（2026-08-26）

> 現行どおりで解説書影響なし、利用者影響なしなら仕様です。

解説書影響が無いことは上のとおり確認済みである。**残るのは利用者影響の判定だけ。**

#### やること

1. **利用者影響の有無を判定する。** 判定基準は「**解説書のとおりに正しく書こうとした利用者が、この挙動を踏むか**」。
   実装から追って判定し、根拠を `file:line` ＋ SHA で示す
2. **「踏まない＝仕様」と判定した場合** —— 現行挙動を固定する特性テストを追加する。
   **負のテストを必ず併せて行う**: ループ上限を `names.size()` から `line.size()` に変えると
   追加したテストが落ちることを確認し、その実行結果を記録する。
   落ちなければ、そのテストはこの挙動を押さえていない
3. **「踏む」と判定した場合** —— 是正案と根拠を出して**止まる**。自分で直さない。
   既存の `.xls` テストデータに超過値が含まれていると後方互換を壊すため、影響範囲の調査を伴う

## 5. 順序 —— 具体は着手前に検証させる

**§4-1 の「案」を実装に反映する前に、案そのものに反例が無いかを実物で確かめてから着手する。**
反例が出たら、反映せずに報告して止まる。

理由: 〈指示 → 反映 → レビュー → 差し戻し → 再指示〉では、矛盾が見つかるたび1往復が丸ごと無駄になる。

## 6. レビュー

**回す。** 判断と理由は次のとおり。

| 対象 | 回すか | 理由 |
|---|---|---|
| §4-1 の特性テスト | **観点D のみ** | 新しい検証物が入る。押さえるべきは「そのテストは通るように書かれただけではないか」。負のテストの実行結果が完了条件にあるため、それが本当に検知力の証明になっているかを見る |
| §4-2 の全件表 | **観点A・観点D** | 全件表を求める作業では、「表が全件でないこと」より「**同じ表が全件であることを、その抽出方式では証明できないこと**」が本当の欠陥になる。観点A（抜け・漏れ）と観点D（検証の妥当性）を別担当で回す |
| §4-2 の不一致の報告 | **観点B のみ** | §4-2 は記録だけで実装もテストも変えない。押さえるべきは「不一致という判定そのものが実物と矛盾していないか」であり、これは観点B（既存のもの・実物と矛盾しないか。呼び出し元・後方互換）に当たる |
| §4-3 のカバレッジ | **回さない** | 計測コマンドと全件列挙が機械的に差分を固定するため |

### 4観点

| 観点 | 見るもの |
|---|---|
| A 充足 | 求められたものを満たしているか。抜け・漏れはないか。境界値・異常系・エラー処理 |
| B 整合 | 既存のもの・実物と矛盾しないか。呼び出し元・後方互換 |
| C 規約 | 既存の約束事と揃っているか。命名・構造・コーディング規約 |
| D 検証の妥当性 | **それを確かめた手段は、本当に欠陥を検知できるか。そのテストは通るように書かれただけではないか** |

### 各観点は別のサブエージェントで実施する。プロンプトに必ず次の3点を入れる

- **実測コマンドで裏付けよ。推測で書くな**（指摘は実行したコマンドまたは実ファイルの引用で裏付ける）
- **成果物に付属する検証スクリプトを正解として使わず、独立に組め**
- **敵対的にレビューせよ**（欠陥は存在するという前提で、境界・抜け道・見落としを探す）

### レビューの対象に、本指示書自体を明示的に含める

**「指示された案そのものに反例がないか」を観点に入れる。**
直近のラウンドでレビューが拾った重大な指摘は、いずれも成果物ではなく**指示側が逐語指定した内容の誤り**だった。

### 運用

- ラウンド1は上の表のとおり。**ラウンド2以降は差分限定の2観点だけ**を回す
  （「是正が指示範囲に収まっているか」「是正が新しい欠陥を生んでいないか」）
- **各ラウンドの指摘件数と観点を記録する**
- 是正ラウンドの上限は**3回**
- **指摘を全部飲まない。** 既決事項（§4-1 の user 判断、解説書が SSoT であること）に反する指摘は却下し、
  却下の理由を記録する

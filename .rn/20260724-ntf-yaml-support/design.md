# NTF解説書 刷新設計

## 1. 読者と構成

読者は2種類。両者に共通する前提は独立させ、3部構成とする。

| 読者 | 知りたいこと | 参照する部 |
|---|---|---|
| アーキテクト | NTFの全体構造・仕組み・設定 | 第1部、第2部 |
| アプリ開発者 | テストの書き方 | 第1部、第3部 |

第4部はツールの利用者が参照する。ツールごとに導入と使い方を1箇所にまとめ、他の部を行き来せずに完結させる。

```
テスティングフレームワーク
├── テスティングフレームワークとは      第1部・概念（両読者の共通前提）
├── 導入と設定                          第2部・アーキテクト向け
├── テストの実装方法                    第3部・アプリ開発者向け
└── ツール                              第4部・ツールごとに完結
```

読者の振り分けは最上位 `index.rst` の本文で行う。

## 2. 第1部 テスティングフレームワークとは

**1ページ。** FW解説書の `Nablarchアプリケーションフレームワークとは`（`ja/application_framework/application_framework/nablarch/`）の構成に倣う。

| セクション | 記載内容 |
|---|---|
| 全体像 | NTFの位置づけ。JUnitベースであること。Nablarchに特化したテスト補助機能を提供すること |
| アーキテクチャ | 自動テストフレームワークの構成。テストクラスの継承構造。リクエスト単体テストがハンドラキューを通す仕組み |
| テストの種類 | クラス単体テスト / リクエスト単体テスト / 取引単体テストの違いと使い分け |
| テストデータ | テストデータを外部ファイル化する意味。セットアップデータと期待値。データブロックの考え方 |
| 対象範囲 | 対応する処理方式の一覧。対応しないもの（Jakarta Batch、マルチスレッド機能） |
| 稼動環境 | JUnit 4 / JUnit 5、Java・Jakarta EEの要件。モジュール一覧（依存関係） |

### 「テストの種類」に置く対比

読者が自分の書くべきテストを判断できるよう、以下を示す。

| テストの種類 | 実行方法 | テスト範囲 | 備考 |
|---|---|---|---|
| クラス単体テスト | JUnitで自動実行 | クラス単体 | エンティティ、コンポーネント |
| リクエスト単体テスト | JUnitで自動実行 | 1リクエスト（ハンドラキューを通す） | 本番に近い構成でテストできる |
| 取引単体テスト | 手動操作 | 複数リクエストにまたがる業務の流れ | APサーバへのデプロイが必要。エビデンスは画面ハードコピー・DBダンプ |

取引単体テストが自動テストではないことを明示する。

### モジュール一覧の集約

依存関係（`nablarch-testing`、`nablarch-testing-junit5`、JUnit関連等）は本ページの「稼動環境」に集約する。処理方式ごとのページには置かない。

処理方式固有の依存があるものだけ、当該ページに記載する。現時点で該当するのはRESTfulウェブサービス（`nablarch-testing-rest`、`nablarch-testing-jetty12`、`nablarch-testing-default-configuration`）およびYAML形式（`nablarch-testing-yaml`）。

## 3. 第2部 導入と設定

暫定構成を以下とし、**ページ分割はマッピング作成後の文量集計で確定する。**

```
導入と設定
├── 共通設定                    テストデータの配置、日時固定、採番、トランザクション等
├── クラス単体テストの設定
├── リクエスト単体テストの設定   処理方式ごと（6ページ）
│     ウェブアプリケーション / RESTfulウェブサービス / HTTPメッセージング /
│     Nablarchバッチアプリケーション / MOMによるメッセージング /
│     テーブルをキューとして使ったメッセージング
├── 取引単体テストの設定         処理方式ごと（同上6ページ）
├── テストデータの形式          Excel / YAML の比較、使い分け、YAML使用時の設定
├── JUnit 5用拡張機能
└── マスタデータ復旧機能
```

処理方式ごとにページを立てるか、1ページ内のセクションとするかは、文量集計で確定する。ページ名は `mapping/vocabulary.md` に暫定語彙として定義し、確定後に一括置換する。

### ページのアウトライン

第2部の各ページは以下のセクション構成に揃える。FW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）の型に倣う。

```
<ページタイトル>
├── 機能概要
│     全体像（図）              何がどうテストされるか
│     主なクラスとリソース      名称・役割・作成単位の表
│     前提事項                  適用できないケース
├── 使用方法
│     テストを実行できるようにする
│     コンポーネントを設定する
│     <個別設定>する
└── 拡張例
      <拡張手順>する
```

**セクションタイトルは「〜する」形式とする。** 読者がタイトルを見て目的の情報に辿り着けること。ライブラリの「排他制御を使うために準備する」「楽観的ロックを行う」と同じ形式。

「主なクラスとリソース」の表にクラスの役割を集約する。同じクラスの説明を拡張例で再掲しない。拡張例では「拡張するには〇〇を継承する」と手順として記載する。

### 記載範囲

| 記載する | 記載しない |
|---|---|
| 主なクラスとリソース | テストソースコードの実装例 |
| コンポーネント設定ファイルの設定項目一覧 | テストデータの記述例 |
| 設定ファイルの記述例 | |
| 拡張方法（クラス差し替え、独自Extension等） | |

「使い方」に該当するものは第3部に置き、第2部からは `:ref:` で参照する。

## 4. 第3部 テストの実装方法

```
テストの実装方法
├── テストデータの書き方                            1ページ
├── テストデータの記載例                            1ページ
├── クラス単体テスト
│     ├── エンティティ単体テスト
│     └── コンポーネント単体テスト
├── リクエスト単体テスト
│     ├── ウェブアプリケーション
│     ├── RESTfulウェブサービス
│     ├── HTTPメッセージング
│     ├── Nablarchバッチアプリケーション
│     ├── MOMによるメッセージング
│     └── テーブルをキューとして使ったメッセージング
└── 取引単体テスト
      ├── ウェブアプリケーション
      ├── RESTfulウェブサービス
      ├── HTTPメッセージング
      ├── Nablarchバッチアプリケーション
      ├── MOMによるメッセージング
      └── テーブルをキューとして使ったメッセージング
```

処理方式ごとのページ名は、`dest_page` の値だけでテスト種別を判別できるよう、マッピング上は `リクエスト単体テスト（ウェブアプリケーション）` の形式を暫定語彙として使う。ページ分割の確定後、`mapping/vocabulary.md` の定義に従って正式名称へ一括置換する。

### ページのアウトライン

第3部の各ページは以下のセクション構成に揃える。

```
<ページタイトル>
├── 機能概要        このページで何ができるようになるか
└── 使用方法
      テストクラスを作成する
      テストメソッドを作成する
      テストデータを作成する      （「テストデータの書き方」への :ref:）
      テストを実行する
      テスト結果を確認する
```

**拡張例は第3部に置かない。** 拡張はコンポーネント設定とクラス差し替えであり、アーキテクトの領域のため第2部に置く。

**セクションタイトルは「〜する」形式とする。**

### テストデータの2ページ

| ページ | 役割 |
|---|---|
| テストデータの書き方 | 記法の仕様。どう書けばどう解釈されるか |
| テストデータの記載例 | 用途別の実例。Excel と YAML の対比で示す |

**それぞれ1ページにまとめる。** 開発者が記法を調べるとき、テーブル・ファイル・メッセージングを同じページ内で探せる状態にする。ページを跨がせない。

**「書き方」から「記載例」へのリンクを必須とする。** 仕様を読んだ読者が対応する実例に到達できること。

## 5. 第4部 ツール

NTFが提供するツールを、ツールごとに1箇所にまとめる。導入と使い方を同じ場所に置き、他の部を行き来せずに完結させる。

```
ツール
├── リクエスト単体データ作成ツール    ブラウザ操作からテストデータを作成する
├── テストデータ変換ツール            Excel と YAML を相互変換する
├── マスタデータ投入ツール            データベースにマスタデータを投入する
└── HTMLチェックツール                HTMLの妥当性を検査する
```

### ページのアウトライン

```
<ツール名>
├── 機能概要        何ができるか。どの場面で使うか
├── 導入            インストール手順、依存関係、設定
└── 使用方法
      <操作手順>する
```

現行解説書のリクエスト単体データ作成ツールとマスタデータ投入ツールは、本体ページとインストールガイドの2ページに分かれている。これを1ページに統合し、「導入」セクションとして収める。

HTMLチェックツールはリクエスト単体テストに標準で組み込まれ、テスト実行時に自動実行される。インストール手順を持たないため「導入」セクションは設けず、実行要否や検査内容の設定を「使用方法」に記載する。

### 第2部・第3部との切り分け

ツールの設定であっても、第2部には置かない。ツールを使う人が1箇所で完結できることを優先する。第2部・第3部からツールに言及する場合は `:ref:` で参照する。

## 7. 用語

### 用語集を作成する

既存解説書とinput資料で用語が揺れているため、マッピングと合わせて用語集を作成し、全ページで統一する。

用語集の作成方針は次のとおり。

- 既存解説書（`ja/development_tools/testing_framework/`）とinput資料の双方から用語を抽出する
- FW解説書に同じ概念の用語がある場合、**FW解説書の用語を採用する**
- input資料の `ntf-doc-terms.md` は用語の候補として扱う。そのまま採用せず、既存解説書およびFW解説書と突き合わせて確定する
- 表記揺れ（例: 「主なクラス, リソース」と「主なクラスとリソース」）は正表記を1つ決める

### 「〜したい」形式の見出しを廃止する

現行の「目的別API使用方法」（`03_Tips.rst`）は「〜したい」形式の逆引きページだが、独立ページとしては設けない。

各項目は該当する第2部・第3部のページの「使用方法」セクションにマージし、見出しを「**〜する**」形式に統一する。読者はセクションタイトルから直接辿り着ける。

## 8. トンマナ

既存解説書のRSTとinput資料は、いずれもFW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）と記述の調子が揃っていない。作成するページは**FW解説書のライブラリに揃える**。

揃える対象は以下。

- 文体（だ・である調）
- セクションタイトルの形式（「〜する」）
- 見出しのアンダーライン記法
- コードブロックのインデントと言語指定
- アドモニション（`tip` / `note` / `important`）の使い分け
- 表の記法
- `:ref:` ラベルの命名規則
- 1文の長さ、改行位置

**既存RSTおよびinput資料の文面をそのまま流用しない。** 内容は引き継ぐが、記述はFW解説書の調子に合わせて書き直す。

## 10. マッピングの仕組み

本書の章構成に従って解説書を再構築するにあたり、記載内容が失われないこと、および各記述の出自を追えることを保証する仕組みを定める。

### 10.1 ファイルの関係

```
[入力]
  develop の ja/development_tools/testing_framework/   47 rst
  .rn/20260724-ntf-yaml-support/input/                 10 md
        │
        │  mapping/tools/extract_sections.py
        ▼
[全量の台帳]
  mapping/sections-current.csv    377セクション   9,783行
  mapping/sections-input.csv      202セクション   3,203行
                                  計579セクション 12,986行
        │
        │  30バッチのサブエージェント
        │  （判断材料）
        │    design.md        割当先の定義
        │    vocabulary.md    dest_page / dest_section の許容値
        │    split-plan.md    100行超23セクションの分割位置
        │    glossary.md      用語の正表記
        │    style.md         記述規約
        ▼
[中間成果物]
  mapping/_batch/batch-01.csv 〜 batch-30.csv
        │
        │  統合
        ▼
[最終成果物]
  mapping/mapping.csv
        │
        │  mapping/tools/verify_mapping.py
        ▼
[検証]
```

`_batch/` は統合後も残す。どのサブエージェントがどのセクションを判断したかを追跡でき、指摘が出たときの再実行単位が明確になるため。

### 10.2 網羅性の保証

3段階で担保する。

| 段階 | 保証すること | 検証方法 |
|---|---|---|
| 抽出時点 | 全行がいずれかのセクションに属する | `body_start_line`〜`body_end_line` の和集合が全行を覆い、未カバーの非空行が0件であること |
| マッピング時点 | 全セクションが `mapping.csv` に登場し、行が消えていない | `verify_mapping.py`（下表） |
| ページ作成時点 | `mapping.csv` の該当行がページに反映されている | 観点A（網羅性）のサブエージェントレビュー |

抽出時点の検証により、**12,986行が台帳の全量**であることが確定している。

`verify_mapping.py` が機械検証する項目は次のとおり。

| 検査 | 意味 |
|---|---|
| 全 `section_id` が `mapping.csv` に登場する | セクションの取りこぼしゼロ |
| 各セクションについて、紐づく行の行範囲の和集合が元のセクション範囲と一致する（隙間・重複ゼロ） | `SPLIT` で行が消えていない |
| `lines` 合計が 12,986 と一致する | 全量が台帳に載っている |
| `dest_part` / `dest_page` / `dest_section` が `vocabulary.md` の値と完全一致する | 存在しないページへの割当を防ぐ |
| `disposition` / `audience` / `dest_page` に空欄がない | 判断漏れがない |
| `DROP` の全行に `note` がある | 落とした根拠が残る |
| 重複を理由とする `DROP` に、重複先の `section_id` が記載されている | 重複を口実に内容が失われることを防ぐ |
| 同一内容が複数の `dest_page` に `MOVE` されていない | 重複の混入を検出する（検出のみ。判定は人が行う） |

`lines` 合計 12,986 の一致は、`DROP` 行を `mapping.csv` に残す限り必ず成立する。これは**取りこぼしがないこと**の確認であって、**全量が新構成に移ったこと**の証明ではない。両者を混同しないよう、`verify_mapping.py` は次の2つを並べて出力する。

- `lines` 合計（全行）— 台帳の全量
- `lines` 合計（`DROP` を除く）— 新構成に移る実質的な分量

### 10.3 トレーサビリティ

`mapping.csv` の1行が、出典と行先を両方向に指す。

```
mapping_id      M-0087
src_section_id  current-0080
src_type        current
src_file        .../05_UnitTestGuide/02_RequestUnitTest/index.rst
src_body_start  132
src_body_end    145
heading_path    リクエスト単体テストの実施方法 > テストデータの書き方 > setUpDbシート
lines           14
audience        user
dest_part       第3部 テストの実装方法
dest_page       テストデータの書き方
dest_section    使用方法
disposition     MOVE
note            判断根拠
```

これにより次が追える。

- **出典 → 行先** — 旧解説書のこの14行がどのページのどのセクションへ移ったか
- **行先 → 出典** — 新ページのこの記述がどこから来たか
- **失われたもの** — `disposition=DROP` の行と、その理由
- **判断主体** — `_batch/` のどのCSVに含まれるかで、どのサブエージェントが判断したか

### 10.4 規模

| 項目 | 数 |
|---|---|
| 入力ファイル | 現行解説書 47 rst / input資料 10 md |
| セクション | 579（current 377 / input 202） |
| 行数 | 12,986（current 9,783 / input 3,203） |
| マッピングのバッチ数 | 30（1バッチあたり9〜21セクション） |

## 11. 刷新の品質担保

本刷新は現行解説書を全面的に作り直す。作り直しは記載内容が失われる危険を伴うため、何をどう担保するかを定める。

### 11.1 担保すべき4点

| # | 担保すること | 失敗したときに起きること |
|---|---|---|
| 1 | 全量を失わない | 現行解説書にあった情報が新解説書から消える |
| 2 | 重複がない | 同じ内容が複数ページにあり、片方だけ更新されて食い違う |
| 3 | 用語が統一されている | 同じものが別の名前で呼ばれ、読者が別物と誤解する |
| 4 | トンマナが揃っている | ページごとに調子が違い、解説書全体として読みにくい |

### 11.2 白紙から作る

現行ファイルを部分的に編集する方式は採らない。**現行の解説書を削除してから、マッピングに基づいて1ページずつ作成する。**

理由は3点。

- 旧記述が残ったまま新記述を追加すると、重複が発生する
- どの記述がどの作業で入ったか追跡できなくなる
- **マッピングにない記述の混入を検出できない**

削除後に増えたファイルはすべてマッピングに基づくものになる。混入を構造的に防げる。削除しても develop ブランチで元の内容を参照できるため、情報は失われない。

### 11.3 マッピングを唯一の基準とする

作成するページの内容は `mapping/mapping.csv` に従う。**マッピングにない記述を追加しない。マッピングにある記述を落とさない。** 判断に迷う場合は、その場で判断せずレビューに上げる。

マッピングそのものの網羅性は「10. マッピングの仕組み」で担保する。

### 11.4 1ページずつ作り、1ページずつレビューする

1ページ作成するごとにレビューを行い、承認を得てから次ページへ進む。まとめて作らない。

理由は、**差分を小さく保ち、全量を確認できる状態を維持する**ため。20ページを一度に作れば、レビューは要点の抜き取りにならざるを得ない。1ページなら、マッピングの該当行とページの内容を1対1で突き合わせられる。

### 11.5 最初の1ページで基準を作る

第1部（概念、1ページ）を作った時点で、以下を確認する。

- 書き直しの度合いは適切か（変えすぎていないか、変えなさすぎないか）
- 内容が失われていないか
- トンマナが揃っているか

ここで基準が固まれば、残りのページは同じ基準で進められる。**方針が誤っていた場合の手戻りを1ページ分に抑える。**

### 11.6 ページごとの4観点レビュー

各ページについて、以下4つを**それぞれ別のサブエージェント**で実施する。1つのサブエージェントに複数観点を持たせない。観点を混ぜると、どれかが手薄になる。

| 観点 | 見るもの | 入力 |
|---|---|---|
| **A 網羅性** | `mapping.csv` の当該 `dest_page` の行がすべて反映されているか。`disposition` ごとの扱いが正しいか（`REFERENCE` が本文を持っていないか、`DROP` が混入していないか）。出典と照合して記載が欠落していないか | `mapping.csv` の該当行、作成したページ、出典ファイル |
| **B トンマナ** | `style.md` の全規約に適合しているか。セクション構成が本書のページアウトラインと一致しているか。セクションタイトルが「〜する」形式か。**出典の文面がそのまま残っていないか** | 作成したページ、`style.md`、本書、FW解説書ライブラリ |
| **C 用語** | `glossary.md` の正表記が使われているか。揺れ表記が混入していないか。処理方式の名称が正式名称と一致しているか | 作成したページ、`glossary.md` |
| **D 整合性** | 他ページと内容が重複していないか。`:ref:` の参照先が実在するか。参照が一方向で切れていないか。前提の矛盾がないか。第2部に使い方が、第3部に設定が混入していないか | 作成したページ、作成済みの全ページ、本書 |

観点AとDが「11.1 担保すべき4点」の1と2に、CとBが3と4に対応する。

### 11.7 レビューの運用

- レビューは**最大3ラウンド**。3ラウンドで解決しない指摘は、未解決のまま記録してユーザーレビューに上げる。4ラウンド目を自己判断で実施しない
- 指摘は**対応の有無にかかわらず全件記録する**。対応しないと判断したものも、理由とともに残す
- 指摘が0件だったラウンドも、その旨を記録する
- レビュー記録は `reviews/page-<ページID>.md` に、以下の形式で残す

| 列 | 内容 |
|---|---|
| 指摘ID | 一意 |
| ラウンド | 1〜3 |
| 観点 | A / B / C / D |
| 指摘内容 | |
| 対応要否 | 要 / 不要 |
| 不要の理由 | 「不要」の場合は必ず記入 |
| 対応内容 | |

対応しなかった指摘を消さないのは、**後から「なぜそう判断したか」を検証できるようにする**ため。記録がなければ、見落としと意図的な判断を区別できない。

### 11.8 機械検証できないもの

次の3点は機械検証の対象外であり、人またはサブエージェントの判断に委ねる。曖昧にせず、担保方法を定めておく。

**割当先が適切かどうか**

`dest_page` が `vocabulary.md` に存在することは検証できるが、その割当先が内容に照らして適切かは検証できない。マッピング作成時の3観点レビュー（割当先の妥当性 / `disposition` の妥当性 / `audience` の妥当性）で担保する。

**`DROP` が妥当かどうか**

`note` に理由が書かれているかは検証できるが、その理由が妥当かは検証できない。マッピング統合後に `DROP` の全件をレビューする。内容が失われるかどうかを決める最後の砦であるため、件数の多寡にかかわらず全件を対象とする。

**書き直しによる内容の変質**

本刷新では出典の文面をそのまま流用せず、トンマナに合わせて書き直す（「8. トンマナ」）。書き直しの過程で内容が変質する危険があり、これは機械検証できない。観点Aのレビューで出典と照合して検出するが、完全ではない。**1ページずつ作り、1ページずつレビューする理由がここにある。**

### 11.9 段階ごとのゲート

各段階で担保することと、次に進む条件を定める。前段階の承認を得るまで次に進まない。

| 段階 | 担保すること | 次に進む条件 |
|---|---|---|
| セクション抽出 | 現行解説書とinput資料の全行が台帳に載る | 未カバーの非空行0件、冪等性（md5一致） |
| 用語集 | 表記揺れの正表記が確定する | 表記揺れが実在する用語と、本書が章・セクション名に使う用語を網羅 |
| トンマナ規約 | 記述の基準が明文化される | 8観点すべてにFW解説書からの根拠2件以上 |
| 分割判断 | 大きいセクションの分割位置が確定する | 分割後の行範囲が元セクションを過不足なく覆う |
| マッピング | 全セクションの行先が決まる | `verify_mapping.py` の全検査を通過、`DROP` 全件のレビュー完了 |
| 現行解説書の削除 | 白紙の状態を作る | 削除前のファイル一覧が記録済み、画像・素材が保持されている |
| ページ作成 | マッピングどおりのページができる | ページごとに4観点レビュー完了、`make html` エラー0 |

# NTF解説書 刷新設計

## 1. 読者と構成

読者は2種類。両者に共通する前提は独立させ、3部構成とする。

| 読者 | 知りたいこと | 参照する部 |
|---|---|---|
| アーキテクト | NTFの全体構造・仕組み・設定 | 第1部、第2部 |
| アプリ開発者 | テストの書き方 | 第1部、第3部 |

第4部はツールの利用者が参照する。ツールごとに導入と使い方を1箇所にまとめ、他の部を行き来せずに完結させる。

```
テスティングフレームワーク
├── テスティングフレームワークとは      第1部・概念（両読者の共通前提）
├── 導入と設定                          第2部・アーキテクト向け
├── テストの実装方法                    第3部・アプリ開発者向け
└── ツール                              第4部・ツールごとに完結
```

読者の振り分けは最上位 `index.rst` の本文で行う。

**参照した規範**: design.md 本節冒頭が「倣う」としているFW解説書 `Nablarchアプリケーションフレームワークとは`（`ja/application_framework/application_framework/nablarch/`）の実際の構成を確認した。`big_picture.rst`（全体像に相当）は、①全体像を1〜2文で示す、②「Nablarchアプリケーションフレームワークは、以下の特長がある。」という1文で特長の列挙へ地続きに移る、③各特長は「Xができる」という能力の提示に続けて、その特長がもたらす具体的なメリット（例:「柔軟な機能追加・変更」「開発方法の共通化」→「開発者の生産性向上・学習コスト低減を実現でき」）を同じ場所で言い切る、という一体の節として書かれている。「全体像」と「特長（特徴）」を別見出しに分けて`:ref:`で往復させる構成は、参照元のどのページにも存在しない。

**改訂内容**:

- 「全体像」と「特徴」を1つのH2「全体像」に統合する。「特徴」という独立したH2見出しは廃止する。各特徴はH2「全体像」配下のH3見出し（`style.md` S-04のL3、「〜できる」形式）として並べる。
- 「全体像」冒頭の1〜2文で、NTFの位置づけ（3種類のテストを提供するJUnitベースのフレームワークであること、Nablarch特化APIを提供すること）を述べたら、「テスティングフレームワークには、次の特徴がある。」で特徴の列挙へ地続きに移る。「テストの種類」への`:ref:`は置かない（直後に続くセクションであり、読者は読み進めれば自然に到達するため、明示的なリンクは不要）。
- **冒頭の1〜2文には、3種類それぞれが「何単位のテストか」を一言で添える。** 2026-08-05 #8フィードバック「この直後に、テストの種類の3つを入れないと、特徴のリクエスト単体テストと言われても意味不明なままです」を受けて追加。「テストの種類」への`:ref:`を置かない代わりに、名前を列挙するだけでは足りない。直後の「特徴」1点目が「リクエスト単体テストは〜」と個別の種類を主語にした説明を始めるため、読者がその時点で各名称の中身（クラス単体=クラス単位、リクエスト単体=1リクエスト単位、取引単体=複数リクエストにまたがる業務単位）を知っている必要がある。「テストの種類」節が持つ実行方法・備考まで含めた詳細（フルの対比表）はそちらに譲り、ここでは名称と対象粒度の対応だけを一文で添える。これは「行き来するリンク」の問題ではなく、後続の文が使う固有名詞を先に定義しておくという、通常の説明文の順序の問題であるため、直前の「同一ページ内`:ref:`は原則置かない」という改訂とは矛盾しない。

- 3点目（テストデータ形式を選べる）から第4部「テストデータ変換ツール」への`:ref:`のみ残す。これは同一ページ内の別セクションではなく、実体が別ページにある内容への正当な導線であり、「行き来する」批判が向けられた同一ページ内リンクとは性質が異なる。

### 「全体像」に含める特徴

各特徴は「Xができる」という能力の提示だけで終えず、それによって読者（アプリ開発者・アーキテクトのいずれか、あるいは両方）にとって何が嬉しいのかという具体的な裏付け・帰結までを1つの塊として書く。2026-08-05 #8フィードバック「特徴、XXXできる、だから何が嬉しいの？利用者のベネフィットを伝えませんか？」を受けた規約。

1. **本番同等の経路でテストできる** — リクエスト単体テストはNAFのハンドラキューを通して実行されるため、環境差分以外は本番と同じ経路でテストできる。単体テストの段階から経路に起因する不具合を早期に見つけられ、結合テストや本番運用まで問題を持ち越さずに済む
2. **テストコードは定型・少量で済む** — テストデータのセットアップや期待値とのアサートなどのテストロジックはNTFが提供し、利用者はテストデータをテストコードとは別ファイルに宣言的に書くだけでよい。基幹システムはテーブル数や項目数が多くテストデータのパターンも多数に上りやすいため、テストデータをテストコードから切り離せることは、大量のテストを効率的に用意・保守するうえで欠かせない（2026-08-05 `/rn:gm`フィードバック「テストコードは定型かつ少量で済むには、暗黙的にテストデータの外部化が含まれてますよね。基幹システムだとテーブル数やカラム数など大規模なデータが想定されるので、外部化必須ですよね」を受けて改訂。旧「テストデータ」節が担っていた外部化の事実をここへ統合した。詳細は下記「「テストデータ」節を廃止する」参照）
3. **利用目的に応じたテストデータ形式を選べる** — 人が書きやすいExcel形式、AIが扱いやすいテキストのYAML形式を相互変換可能な形で提供する。開発者がレビュー・編集する場面とAIエージェントが自動生成・解析する場面のどちらにも、同じテストデータ資産を使い分けられる
4. **使い慣れたJUnitの書き方をそのまま活かせる** — JUnit 4を基盤とするため、アノテーション・assertメソッドなどJUnitの機能や知識をそのまま使え、新たに専用の記法を覚える必要がなく学習コストを抑えて導入できる

**マッピング行の `dest_section` は変更しない。** 4点とも実体は `全体像` セクション（統合後のH2）の中にそのまま存在する。

- 1・2・4: `current-0162`/`0164`/`0166`（JUnitベース・Nablarch特化API・JUnit4互換性とコード例）・`current-0165`（アーキテクチャの図。ハンドラキューを通す仕組みの裏付けとして1点目が要約）は `全体像`／`アーキテクチャ` という元の割当のまま存在し、特徴の各点はその要約として同一ページ内に新規マッピング行を追加せず書く。`current-0163`/`0176`（テストデータ外部化）は、2026-08-05 #8フィードバック対応（「テストデータ」節廃止、下記参照）で `dest_section` を `テストデータ` から `全体像` へ変更し、2点目の要約として統合した。
- 3: 出典 `input-0183`（`テストデータ変換ツール`、第4部）も割当を維持し、`:ref:`\`テストデータ変換ツール <testdata_converter>\` で第4部へ導線を張る（2026-08-05、`tools/testdata_converter.rst` を見出しのみで先行作成し `undefined label` 警告を解消済み。詳細は steering.md #9〜「前方参照によるスタブページ」参照）。

### 「テストの種類」に置く対比

読者が自分の書くべきテストを判断できるよう、以下を示す。

| テストの種類 | 実行方法 | テスト範囲 | 備考 |
|---|---|---|---|
| クラス単体テスト | JUnitで自動実行 | クラス単体 | エンティティ、コンポーネント |
| リクエスト単体テスト | JUnitで自動実行 | 1リクエスト（ハンドラキューを通す） | 本番に近い構成でテストできる |
| 取引単体テスト | 処理方式によって異なる（手動操作またはJUnitで自動実行） | 複数リクエストにまたがる業務の流れ | 手動操作の場合は、アプリケーションサーバへのデプロイが必要で、エビデンスは画面ハードコピー・DBダンプとなる |

**取引単体テストの実行方法が処理方式によって異なることを明示する。** 対比表のセルに加えて、対比表と次節の内訳（本節末尾の「リクエスト単体テストの処理方式ごとの内訳」）の間に地の文の1段落を置き、どの処理方式がどちらかを名指しする。根拠と決定は以下のとおり。

#### 決定と理由

**公開本文で名指しするのは3処理方式だけとする。** ウェブアプリケーション＝手動（`03_DealUnitTest/index.rst:7-8`）、RESTfulウェブサービス＝自動（同 `rest.rst:7`）、Nablarchバッチアプリケーション＝自動（同 `batch.rst:5-6`）。出典が手動・自動の区別を述べているのがこの3つだけだからである。

**拡張例は第3部に置かない。** 拡張はコンポーネント設定とクラス差し替えであり、アーキテクトの領域のため第2部に置く。

**セクションタイトルは「〜する」形式とする。**

**例外はテストデータの2ページとする。** 第3部は原則として`機能概要`＋`使用方法`の2セクション構成とするが、次の2ページはこれに従わない。

- **「テストデータの書き方」**は`機能概要`＋`テストデータの構造`＋`使用方法`の3セクション構成とする。`テストデータの構造`配下には`テストクラスとテストデータの対応`・`データブロックとデータタイプ`・`グループIDによる使い分け`の3つを置く。本ページは手順ではなく記法の仕様であり、器の説明（構造）と記法の説明（使用方法）を分けたほうが読者の探索単位に一致するためである。`テストデータの構造`配下は「これは何か」に答える見出しであるため「〜する」形式を適用せず体言止めとする（`mapping/style.md` S-03）。
- **「テストデータの記載例」**は`機能概要`も`使用方法`も持たず、記述例の見出しをL2として並べる構成とする。ページ全体を対象にした導入文が出典に存在しないため機能概要を持たず、記載例が並ぶだけのページであるため「使用方法」という1つの説明も持たない。理由の詳細と並べる見出しは次の「テストデータの2ページ」に示す。

### テストデータの2ページ

| ページ | 役割 |
|---|---|
| テストデータの書き方 | 記法の仕様。どう書けばどう解釈されるか |
| テストデータの記載例 | 用途別の実例。Excel と YAML の対比で示す |

確定事項は次のとおり。

- **それぞれ1ページにまとめ、ページを跨がせない。** 記法を調べるとき、テーブル・ファイル・メッセージングを同じページ内で探せる状態にするため
- **「書き方」から「記載例」へのリンクは、使用方法内の各セクション・各形式（Excel/YAML）の説明ごとに置く。** ページ末尾1箇所にまとめない
- **「記載例」の実例は、実開発でそのまま流用をイメージできる水準・分量にする。** Toy／サンプルレベルの最小例にしない
- **「書き方」には第3部ページアウトラインを機能概要＋テストデータの構造＋使用方法の形で適用する。** 主要出典 `ntf-testdata-doc.md` がページ全体を対象とする導入文であり、機能概要に該当するため
- **「記載例」はページアウトラインの2セクションをいずれも持たず、「使用方法」も置かない。** 出典にページ全体を対象とした記述が無く（`HTMLチェックツール`の「導入」と同型）、記載例が並ぶだけのページに「使用方法」という見出しは合わないため。L2見出しを並べるだけの構成とする
- **「記載例」のL2見出しは「書き方」の対応する見出しと文言を一致させる。** 名前だけで導線が分かるようにするため。「テストクラスとテストデータの対応」はデータ内容の実例を持たないので、対応する見出しを置かない
- **Excel形式/YAML形式の書き分けとセル格子の表記は `style.md` S-10 に従う。** セル格子には識別子行など実在する行をすべて含めて `:header-rows: 0` とする。ただし複数のデータタイプに共通する規則を示す断片は識別子行を持たなくてよい。セルに素のダブルクォートを書く場合はリテラル記法で囲む（smartquotes が既定で有効なため）
- **`input-0002`/`input-0116` は第1部から本ページ群へ編入し、`#9` の再構成で `dest_section=テストデータの構造` とした。** 記法の詳細は本ページ群の主題であり、第1部は概念（外部化の意味・テストの独立性）にとどめる方が役割が明確になるため

両ページとも user review 承認済み（`#9`・`#10`）。ラウンドごとの指摘と判断の経緯は `reviews/page-testdata_notation.md`・`reviews/page-testdata_examples.md`、検証記録は `checks/task-09*.md`・`checks/task-10*.md`、マッピングの割当根拠は `checks/task-06.md` 分類6 を参照。

## 5. 第4部 ツール

NTFが提供するツールを、ツールごとに1箇所にまとめる。導入と使い方を同じ場所に置き、他の部を行き来せずに完結させる。

```
ツール
├── リクエスト単体データ作成ツール    ブラウザ操作からテストデータを作成する
├── マスタデータ投入ツール            データベースにマスタデータを投入する
├── HTMLチェックツール                HTMLの妥当性を検査する
└── テストデータ変換ツール            Excel と YAML を相互変換する
```

**並び順は、現行解説書の3ツールの順序をそのまま保ち、今回新設したテストデータ変換ツールを末尾に置く**（`#37` で user 確定。2026-08-26）。現行解説書の順序は `08_TestTools/` の `01_HttpDumpTool`（リクエスト単体データ作成ツール）・`02_MasterDataSetup`（マスタデータ投入ツール）・`03_HtmlCheckTool`（HTMLチェックツール）である。**新設のツールを既存の並びの途中へ挿し込まない。** 挿し込むと挿入位置ごとに理由が要るうえ、ライフサイクル順など別の説明を持ち出すと既存3ツールの順序まで組み替える話になる。末尾に足す規則なら、次にツールが増えても同じ扱いで済む。

### ページのアウトライン

```
<ツール名>
├── 機能概要        何ができるか。どの場面で使うか
├── 導入            インストール手順、依存関係、設定
└── 使用方法
      <操作手順>する
```

現行解説書のリクエスト単体データ作成ツールとマスタデータ投入ツールは、本体ページとインストールガイドの2ページに分かれている。これを1ページに統合し、「導入」セクションとして収める。

HTMLチェックツールはリクエスト単体テストに標準で組み込まれ、テスト実行時に自動実行される。インストール手順を持たないため「導入」セクションは設けず、実行要否や検査内容の設定を「使用方法」に記載する。

**テストデータ変換ツールは「導入」を持つ**（`#28` §3-16 確定。`#6` の「導入を持たない」を改める）。

`#6` 時点の判断は「出典（`input/testdata-converter-design.md` 全362行）にインストール手順・依存関係・設定に該当する記述が存在しない。候補となる記述（解くべき課題、形式に依存するか否かという設計思想の説明）はいずれも『機能概要』に該当する」であった（`#6`確定、`checks/task-06.md`分類8参照）。この出典の事実は2026-08-16に再確認済みで、同ファイルに `pom.xml`・`dependency`・`plugin`・`artifactId`・「導入」・「インストール」はいずれも0件である。

しかし `#27` のページ作成時に、§8「出典が欠いている、実装上必須の設定の追記」により実装から pom.xml への追加手順を書き足した結果、実質的な導入手順が「使用方法」配下に入っている（移設前の `870e809:ja/development_tools/testing_framework/tools/testdata_converter.rst:97-109` の `<plugin>` 追加、`:182-191` の `<dependency>` 追加）。**第4部の他ページと構成を揃えるため、この2箇所を「機能概要」と「使用方法」の間に置く「導入」（L2）へ移す。**

- 「導入」には pom.xml への追加だけを置く。Mavenプラグインとして実行する場合の `<plugin>` と、Javaのコードから呼び出す場合の `<dependency>` を、どちらの使い方をするかで選ぶものとして並べる
- 「使用方法」の2つのL3には実行手順だけを残す（`convert` ゴールの実行とパラメータ表、`TestDataConverter` の呼び出し）
- **「前提事項」は「機能概要」配下のまま動かさない**（`tools/testdata_converter.rst:61-69`）。内容は往復で再現されない情報の範囲であり、導入の前提条件ではないため。他の2ページ（`tools/master_data_tool.rst:36`・`tools/request_data_tool.rst:26`）が「前提事項」を「導入」配下に置いているのと配置が異なるが、`mapping/glossary.md` §5.13 のとおり「前提事項」は機能概要・導入のどちらの下位にも立つ

`.rst` の節移動は `#last` で実施済み。`ja/development_tools/testing_framework/tools/testdata_converter.rst:71-100` に `.. _testdata_converter-setup:` ラベル付きの「導入」（L2）を新設し、`<plugin>` 追加を `:77-89`、`<dependency>` 追加を `:91-100` に置いた。「使用方法」（`:102`）の導入部は他の2ページと同じく `:ref:` で「導入」へ送る形にした（`:104`）。「導入」に L3 は設けていない。S-03 の「〜する」形式で2つを見出しにすると手順の並びに読めるが、この2つは順に実施するものではなく、どちらの使い方をするかで選ぶ択一だからである。

### 第2部・第3部との切り分け

ツールの設定であっても、第2部には置かない。ツールを使う人が1箇所で完結できることを優先する。第2部・第3部からツールに言及する場合は `:ref:` で参照する。

本節（ツールへは `:ref:` で参照する）と §8「出典が書いていない適用範囲・副作用の追記」の「承認済みのページが同じ事実を持つ場合は `:ref:` で導線を張る」が両方該当する場合は、**設定値そのものはツールページに置き、他ページから見た制約だけを `:ref:` で残す**（`#28` 確定）。ツールページから設定値を追い出すと、ツールを使う人が1箇所で完結できるという本節の目的に反するためである。

## 8. トンマナ

既存解説書のRSTとinput資料は、いずれもFW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）と記述の調子が揃っていない。作成するページは**FW解説書のライブラリに揃える**。

揃える対象は以下。

- 文体（だ・である調）
- セクションタイトルの形式（「〜する」）。加えて、ページ作成時は `mapping/style.md` のセクションタイトル規約（ページタイトルとセクションタイトルの組で一意であり、かつその組だけで中身が分かること。`#6`確定）に従う
- 見出しのアンダーライン記法
- コードブロックのインデントと言語指定
- アドモニション（`tip` / `note` / `important`）の使い分け
- 表の記法
- `:ref:` ラベルの命名規則
- 1文の長さ、改行位置
- 各ページ先頭の目次（`.. contents::` ディレクティブ）（2026-08-06、`/rn:gm`フィードバックにより追加。`mapping/style.md` S-09参照）
- Excel/YAML形式を対比するイラストの書き方（識別子行は表の外・普通の文字、紛れる場合は太字ラベル）（2026-08-06、`/rn:gm`フィードバックにより追加。`mapping/style.md` S-10参照）

**既存RSTおよびinput資料の文面をそのまま流用しない。** 内容は引き継ぐが、記述はFW解説書の調子に合わせて書き直す。

### 出典と確定設計が食い違う場合

出典（現行解説書・input資料）と、`#6` で確定した設計（`design.md` の各節、
`mapping/vocabulary.md` のページ名、`mapping/glossary.md` の正表記）が食い違う場合、
**確定した設計を優先する。**

出典に無いことは、確定した設計に基づく記述を妨げない。「マッピングにない内容を
追加しない」が禁じているのは、出典にも確定設計にも根拠のない**新規の主題内容**を
書くことであって、確定設計を反映することではない。

例（`#8` A-3）: テスト種別の正式名称表は本文書の名称索引であり、`vocabulary.md` の
ページ名と一致させる。出典 `input-0028` が6区分時代の資料で当該行を持たないことは、
行を落とす根拠にならない。

**陳腐化した例示は落としてよい**（`#16` 確定。`#15` の `decide` 2 に対する判断）。
出典が挙げている具体的な製品名・バージョン・型番のうち、現在では事実が変わっているものは
落としてよい。§11.3「マッピングにある内容を落とさない」の例外とする。

- 判断の基準は、**その例示を残すと今日の読者にとって意味が反転または誤解を生むかどうか**である。
- 例示を落としても、判断に必要な内容（その記述が何を言いたいか）は必ず残す。例示ごと記述を
  落とすことはしない。
- 落とした場合は、落とした語と理由を `reviews/page-*.md` に記録する。

例（`#15`）: 出典は「Pentium4、Pentium Dual-Core等の処理性能が低いCPUに効果がある。
これら以降のCPUではそれほど効果的ではない」としていたが、これらは現在では旧世代のCPUであり、
残すと読者は効果の有無を逆に読む。製品名を落とし「比較的新しいCPUを搭載したPCでは効果が小さい」とした
（`reviews/page-request_unit_test_setting_web.md`）。

### 出典と実装が食い違う場合

出典の記述が、検証可能な実装の挙動と食い違う場合は、実装を優先する。根拠として、
確認した実装のファイル名・行番号・参照したコミットを `reviews/page-*.md` に記録する。
実装を確認できない場合は `decide` としてユーザーに上げる。

**ここでいう「実装」には、出典が前提にしている外部の挙動を含む**（`#16` 確定。`#15` の `decide` 3 に
対する判断）。NTF・NAF の実装だけでなく、JVM・JDK・データベース・ビルドツールなどの挙動も対象とする。
出典が勧める手順が現在は非推奨・廃止・挙動変更になっている場合、その事実を書き足してよい。
§11.3「マッピングにない内容を追加しない」の例外とする。

- 追記は**出典が述べている手順に対する注記に限る。** 出典が触れていない新しい主題を追加してよい
  という意味ではない。
- 追記の根拠は、**実際に動かして確かめた結果**とする。確認した内容・環境・結果を
  `reviews/page-*.md` に記録する。
- 出典の手順そのものは残し、注記（`important` 等）を添える形にする。手順を書き換えない。

例（`#15`）: 出典が勧める `-Xverify:none` は JDK 13 で非推奨になっている。オプションの記述は残し、
非推奨である旨を `important` で追記した（Temurin 21 で警告つきで起動することを実測。
`reviews/page-request_unit_test_setting_web.md`）。

### 設定項目表の「デフォルト値」の基準

コンポーネント設定ファイルの設定項目一覧に載せる「デフォルト値」は、テスティングフレームワークの
デフォルト設定（`nablarch-testing-default-configuration`）を読み込んだ状態で有効になる**実効値**とする
（`#18` 確定。`#17` の `decide` 2 に対する判断）。クラスのフィールド初期値ではない。

根拠は次の2点である。

- ブランクプロジェクトがデフォルト設定を読み込むこと。ウェブアプリケーションは
  `nablarch/test/http-request-test.xml` を、RESTfulウェブサービスは `nablarch/test/rest-request-test.xml`
  を読み込む（`nablarch-web-archetype` / `nablarch-jaxrs-archetype` の
  `archetype-resources/src/test/resources/unit-test.xml`）。読者が実際に目にするのは実効値である
- 同名・同クラスのコンポーネント定義が**プロパティ単位でマージ**され、上書きしなかったプロパティに
  デフォルト設定の値が残ること（`nablarch-core-repository` の
  `XmlComponentDefinitionLoader.java`。既定ポリシーは `DuplicateDefinitionPolicy.OVERRIDE`）。
  読者が同名で上書きしても、実効値を基準にした記載と矛盾しない

運用は次のとおり。

- **表を持つページは、その基準を表の直前の地の文で明示する。** 「デフォルト値の欄には、デフォルト設定を
  読み込んだ状態で有効になる値を示す」に相当する1文を置く
- フィールド初期値と実効値が食い違う場合、**実効値だけを載せる。** 両方を並べない
- デフォルト設定が設定していない項目は、フィールド初期値がそのまま実効値になる
- 確認した `file:line`（デフォルト設定の XML と `.config` の組）を `reviews/page-*.md` に記録する

### 出典が欠いている、実装上必須の設定の追記

出典にもマッピングにも無いが、**それが無いとページに書かれた手順が動かない設定は、書き足してよい**
（`#18` 確定。`#17` の `decide` 1 に対する判断）。§11.3「マッピングにない内容を追加しない」の例外とする。

- 追記の根拠は、**実装で必須であることを確かめた結果**とする。確認した `file:line` とコミットハッシュを
  `reviews/page-*.md` に記録する。
- 追記は**ページに書かれた手順を成立させるために必要なものに限る。** 出典が触れていない新しい主題を
  追加してよいという意味ではない。
- **記載例についても同じ基準（無いと読者が書けない）で追記してよい**（`#28` 確定。§6-2-3）。
  「無いと読者が書けない」は、次の3つを**すべて**満たす場合とする。いずれも実物を開いて判定する。
  1. **出典に当該の記載例が無い。** `mapping.csv` で当該 `dest_page` に対応する出典ファイルを開き、
     その記載例が0件であることを確かめる
  2. **読者が書くべきファイルの項目名・カラム構成が、当該ページのどこにも示されていない。**
     ページ全体を開いて、記載例・表・本文のいずれにも現れないことを確かめる（同じページの他節や
     `:ref:` の参照先に示されている場合は、この条件を満たさないため追記しない）
  3. **書き足す内容を実装またはテストコードで確かめられる。** 根拠とする `file:line` を示せること
- **記載例の追記にも、上記1点目の記録義務がそのまま掛かる。** 根拠とした `file:line` とコミット
  ハッシュを `reviews/page-*.md` に記録する（§11.9「ページ作成」のゲートが求める4観点レビューで、
  記録の有無を確認する）。

例（`#17`）: `httpServerFactory` の登録。デフォルト設定に含まれず（5u24〜6u3 の全版で0件）、未登録だと
内蔵サーバの生成時に `IllegalConfigurationException` が発生する（`SimpleRestTestSupport.java:45`・
`:298-300`。`reviews/page-request_unit_test_setting_rest.md`）。

### 出典が書いていない適用範囲・副作用の追記

**出典が書いていない適用範囲・副作用のうち、書かなければ読者が誤った設定に至るものは書き足してよい**
（`#21` 確定）。追記の根拠は実装で確かめた結果とし、`file:line` とコミットハッシュを
`reviews/page-*.md` に記録する。既に承認済みのページが同じ事実を持つ場合は、書き下ろさずに `:ref:` で
導線を張る。

「適用範囲の限定」と「副作用の注意喚起」は1つの類型として扱う。どちらも**書かなければ読者が誤るか**
という同じ判定基準で決まるためである。前節（実装上必須の設定の追記）が「無いと手順が動かない設定」を
扱うのに対し、本節は「設定は動くが、読者が適用範囲を取り違える／副作用に気づかない」場合を扱う。

例（`#21`）:

- 適用範囲の限定 — `reader.fwHeaderfields` は同期応答メッセージ送信のテストでは使用されない
  （`SendSyncMessageParser.java:42-43`・`GroupMessageParser.java:58`）。書かないと、送信のテストのために
  不要な設定を書く（`setup/request_unit_test/mom.rst`）
- 副作用の注意喚起 — `file-type` の値は応答電文のアサート方式にも影響し、`Fixed` 以外を指定すると
  データレコード単位のアサートから電文全体の比較に切り替わる（`MessagePool.java:54`・`:155-163`）。
  ページの手順そのものが読者をその状態へ導くため、注記が無いと手順が不完全になる（同ページ）
- 値の書式の制約 — `reader.fwHeaderfields` の値はカンマで分割されるだけで前後の空白を取り除かない
  （`NablarchTestUtils.java:36`・`:45-49`）。空白を入れるとフィールド名の一部になり、無言で一致しなくなる
  （`MessageParser.java:103`）

本類型は既存の承認済みページにも遡って当てはまる（`setup/request_unit_test/batch.rst:78` の「共通の
デフォルト値には両方の種別で有効なキーだけを設定する」など）。既存ページの記述を変える必要はない。

### 10.2 網羅性の保証

3段階で担保する。

| 段階 | 保証すること | 検証方法 |
|---|---|---|
| 抽出時点 | 全行がいずれかのセクションに属する | `body_start_line`〜`body_end_line` の和集合が全行を覆い、未カバーの非空行が0件であること |
| マッピング時点 | 全セクションが `mapping.csv` に登場し、行が消えていない | `verify_mapping.py`（下表） |
| ページ作成時点 | `mapping.csv` の該当行がページに反映されている | 観点A（網羅性）のサブエージェントレビュー |

抽出時点の検証により、**12,986行が台帳の全量**であることが確定している。

`verify_mapping.py` が機械検証する項目は次のとおり。

| 検査 | 意味 |
|---|---|
| 全 `section_id` が `mapping.csv` に登場する | セクションの取りこぼしゼロ |
| 各セクションについて、紐づく行の行範囲の和集合が元のセクション範囲と一致する（隙間・重複ゼロ） | `SPLIT` で行が消えていない |
| `lines` 合計が 12,986 と一致する | 全量が台帳に載っている |
| `dest_part` / `dest_page` / `dest_section` が `vocabulary.md` の値と完全一致する | 存在しないページへの割当を防ぐ |
| `disposition` / `audience` / `dest_page` に空欄がない | 判断漏れがない |
| `DROP` の全行に `note` がある | 落とした根拠が残る |
| 重複を理由とする `DROP` に、重複先の `section_id` が記載されている | 重複を口実に内容が失われることを防ぐ |
| 同一内容が複数の `dest_page` に `MOVE` されていない | 重複の混入を検出する（検出のみ。判定は人が行う） |

`lines` 合計 12,986 の一致は、`DROP` 行を `mapping.csv` に残す限り必ず成立する。これは**取りこぼしがないこと**の確認であって、**全量が新構成に移ったこと**の証明ではない。両者を混同しないよう、`verify_mapping.py` は次の2つを並べて出力する。

- `lines` 合計（全行）— 台帳の全量
- `lines` 合計（`DROP` を除く）— 新構成に移る実質的な分量

## 11. 刷新の品質担保

本刷新は現行解説書を全面的に作り直す。作り直しは記載内容が失われる危険を伴うため、何をどう担保するかを定める。

### 11.1 担保すべき4点

| # | 担保すること | 失敗したときに起きること |
|---|---|---|
| 1 | 全量を失わない | 現行解説書にあった情報が新解説書から消える |
| 2 | 重複がない | 同じ内容が複数ページにあり、片方だけ更新されて食い違う |
| 3 | 用語が統一されている | 同じものが別の名前で呼ばれ、読者が別物と誤解する |
| 4 | トンマナが揃っている | ページごとに調子が違い、解説書全体として読みにくい |

### 11.2 白紙から作る

現行ファイルを部分的に編集する方式は採らない。**現行の解説書を削除してから、マッピングに基づいて1ページずつ作成する。**

理由は3点。

- 旧記述が残ったまま新記述を追加すると、重複が発生する
- どの記述がどの作業で入ったか追跡できなくなる
- **マッピングにない記述の混入を検出できない**

削除後に増えたファイルはすべてマッピングに基づくものになる。混入を構造的に防げる。削除しても develop ブランチで元の内容を参照できるため、情報は失われない。

### 11.3 マッピングを唯一の基準とする

作成するページの内容は `mapping/mapping.csv` に従う。**マッピングにない記述を追加しない。マッピングにある記述を落とさない。** 判断に迷う場合は、その場で判断せずレビューに上げる。

マッピングそのものの網羅性は「10. マッピングの仕組み」で担保する。

### 11.4 1ページずつ作り、1ページずつレビューする

1ページ作成するごとにレビューを行い、承認を得てから次ページへ進む。まとめて作らない。

理由は、**差分を小さく保ち、全量を確認できる状態を維持する**ため。20ページを一度に作れば、レビューは要点の抜き取りにならざるを得ない。1ページなら、マッピングの該当行とページの内容を1対1で突き合わせられる。

### 11.5 最初の1ページで基準を作る

第1部（概念、1ページ）を作った時点で、以下を確認する。

- 書き直しの度合いは適切か（変えすぎていないか、変えなさすぎないか）
- 内容が失われていないか
- トンマナが揃っているか

ここで基準が固まれば、残りのページは同じ基準で進められる。**方針が誤っていた場合の手戻りを1ページ分に抑える。**

### 11.6 ページごとの4観点レビュー

各ページについて、以下4つを**それぞれ別のサブエージェント**で実施する。1つのサブエージェントに複数観点を持たせない。観点を混ぜると、どれかが手薄になる。

| 観点 | 見るもの | 入力 |
|---|---|---|
| **A 網羅性** | `mapping.csv` の当該 `dest_page` の行がすべて反映されているか。`disposition` ごとの扱いが正しいか（`REFERENCE` が本文を持っていないか、`DROP` が混入していないか）。出典と照合して記載が欠落していないか | `mapping.csv` の該当行、作成したページ、出典ファイル |
| **B トンマナ** | `style.md` の全規約に適合しているか。セクション構成が本書のページアウトラインと一致しているか。セクションタイトルが「〜する」形式か。**ページタイトル＋セクションタイトルの組で中身が分かるか**（`style.md` セクションタイトル規約）。**出典の逐語的流用がないか**（判定基準は本節末尾「観点Bの判定基準」参照） | 作成したページ、`style.md`、本書、FW解説書ライブラリ |
| **C 用語** | `glossary.md` の正表記が使われているか。揺れ表記が混入していないか。処理方式の名称が正式名称と一致しているか | 作成したページ、`glossary.md` |
| **D 整合性** | 他ページと内容が重複していないか。`:ref:` の参照先が実在するか。参照が一方向で切れていないか。前提の矛盾がないか。第2部に使い方が、第3部に設定が混入していないか。**見出し・導入文と実際の中身が一致しているか**（チェック項目は本節末尾「観点Dのチェック項目」参照） | 作成したページ、作成済みの全ページ、本書 |

観点AとDが「11.1 担保すべき4点」の1と2に、CとBが3と4に対応する。

**観点Bの判定基準（出典の逐語的流用）**

「出典の骨格を踏襲している」のような主観的な基準では判定がぶれる。指摘してよいのは、次のいずれかに当てはまる場合に限る。

- 出典の一文がほぼそのまま（語順・接続・修飾関係が一致した状態で）残っている
- 出典の見出し・箇条書きの構造がそのまま持ち込まれている
- 出典固有の言い回し（現行解説書の「〜すること。」調の指示文など）がそのまま残っている

次は指摘しない。

- 用語・クラス名・データタイプ名・短い技術的言明（20字程度まで）の一致。言い換えると意味が変わるため
- 列挙の順序が出典と同じであること。順序自体が出典の示すモデルである場合がある
- 出典と同じ事実を述べていること。事実は変えられない

**字数は目安であり、厳密な閾値ではない。** 一文で完結する技術的な結論（「テストソースコードの重複を大幅に削減できる」等）は、
20字をやや超えていても、言い換えると結論の強さ・対象・因果関係が変わってしまう場合は指摘しない。逆に、20字以内でも
文全体の構造（主語・述語・接続）が出典の一文と一致していれば指摘してよい。**すでにユーザーが実物比較のうえ「対応不要」
と判定した箇所は、本基準を機械的に再適用して蒸し返さない。** ユーザーの個別判断は本基準より優先する。

指摘する場合は、**出典の該当文と成果物の該当文を並べて引用する**こと。並べられない指摘は出さない。

**観点Dのチェック項目（見出し・導入文と中身の一致）**

- [ ] 各セクション見出しが、そのセクションの実際の中身を表しているか
- [ ] 表・箇条書き・コード例の導入文が、直後の実物の中身と一致しているか（導入文が対象を限定しているのに、実物にはその範囲外の項目が含まれていないか）
- [ ] ページタイトル＋セクションタイトルの組だけで中身が分かるか（`style.md` の規約）

### 11.7 レビューの運用

- 指摘には重大度区分を付ける。区分は次の3つに限る

| 区分 | 内容 | 扱い |
|---|---|---|
| `must` | 事実誤り、`glossary.md` の正表記違反、`style.md` の規約違反、見出し・導入文と中身の不一致、`design.md` の構成違反、`vocabulary.md` のページ名・`design.md` の確定内容との不一致 | レビューラウンド内で必ず修正する。ユーザー判断に回さない |
| `decide` | 出典にない内容の追加可否、ページ構成の選択など、規約で決まらない判断 | ユーザーに上げる |
| `note` | 規約に反しないが改善余地がある表現 | 記録するのみ。修正ラウンドを費やさない |

- レビューは**最大3ラウンド**。**3ラウンド上限に達してユーザーレビューに上げてよいのは `decide` のみ。** `must` が残った状態でユーザーレビューに上げない。`must` が3ラウンドで解消しない場合は、自己判断で4ラウンド目を実施するのではなく、原因（指摘が不明確／修正が反映されない等）を記録して報告する
- 指摘は**対応の有無にかかわらず全件記録する**。対応しないと判断したものも、理由とともに残す
- 指摘が0件だったラウンドも、その旨を記録する
- レビュー記録は `reviews/page-<ページID>.md` に、以下の形式で残す

| 列 | 内容 |
|---|---|
| 指摘ID | 一意 |
| ラウンド | 1〜3 |
| 観点 | A / B / C / D |
| 区分 | `must` / `decide` / `note` |
| 指摘内容 | |
| 対応要否 | 要 / 不要 |
| 不要の理由 | 「不要」の場合は必ず記入 |
| 対応内容 | |

対応しなかった指摘を消さないのは、**後から「なぜそう判断したか」を検証できるようにする**ため。記録がなければ、見落としと意図的な判断を区別できない。

### 11.8 機械検証できないもの

次の3点は機械検証の対象外であり、人またはサブエージェントの判断に委ねる。曖昧にせず、担保方法を定めておく。

**割当先が適切かどうか**

`dest_page` が `vocabulary.md` に存在することは検証できるが、その割当先が内容に照らして適切かは検証できない。マッピング作成時の3観点レビュー（割当先の妥当性 / `disposition` の妥当性 / `audience` の妥当性）で担保する。

**`DROP` が妥当かどうか**

`note` に理由が書かれているかは検証できるが、その理由が妥当かは検証できない。マッピング統合後に `DROP` の全件をレビューする。内容が失われるかどうかを決める最後の砦であるため、件数の多寡にかかわらず全件を対象とする。

**書き直しによる内容の変質**

本刷新では出典の文面をそのまま流用せず、トンマナに合わせて書き直す（「8. トンマナ」）。書き直しの過程で内容が変質する危険があり、これは機械検証できない。観点Aのレビューで出典と照合して検出するが、完全ではない。**1ページずつ作り、1ページずつレビューする理由がここにある。**

### 11.9 段階ごとのゲート

各段階で担保することと、次に進む条件を定める。前段階の承認を得るまで次に進まない。

| 段階 | 担保すること | 次に進む条件 |
|---|---|---|
| セクション抽出 | 現行解説書とinput資料の全行が台帳に載る | 未カバーの非空行0件、冪等性（md5一致） |
| 用語集 | 表記揺れの正表記が確定する | 表記揺れが実在する用語と、本書が章・セクション名に使う用語を網羅 |
| トンマナ規約 | 記述の基準が明文化される | 8観点すべてにFW解説書からの根拠2件以上 |
| 分割判断 | 大きいセクションの分割位置が確定する | 分割後の行範囲が元セクションを過不足なく覆う |
| マッピング | 全セクションの行先が決まる | `verify_mapping.py` の全検査を通過、`DROP` 全件のレビュー完了 |
| 現行解説書の削除 | 白紙の状態を作る | 削除前のファイル一覧が記録済み、画像・素材が保持されている |
| ページ作成 | マッピングどおりのページができる | ページごとに4観点レビュー完了、`make html` エラー0 |

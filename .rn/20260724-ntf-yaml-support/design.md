# NTF解説書 刷新設計

## 1. 読者と構成

読者は2種類。両者に共通する前提は独立させ、3部構成とする。

| 読者 | 知りたいこと | 参照する部 |
|---|---|---|
| アーキテクト | NTFの全体構造・仕組み・設定 | 第1部、第2部 |
| アプリ開発者 | テストの書き方 | 第1部、第3部 |

第4部はツールの利用者が参照する。ツールごとに導入と使い方を1箇所にまとめ、他の部を行き来せずに完結させる。

```
テスティングフレームワーク
├── テスティングフレームワークとは      第1部・概念（両読者の共通前提）
├── 導入と設定                          第2部・アーキテクト向け
├── テストの実装方法                    第3部・アプリ開発者向け
└── ツール                              第4部・ツールごとに完結
```

読者の振り分けは最上位 `index.rst` の本文で行う。

## 2. 第1部 テスティングフレームワークとは

**1ページ。** FW解説書の `Nablarchアプリケーションフレームワークとは`（`ja/application_framework/application_framework/nablarch/`）の構成に倣う。

セクションの並び順は、読者がこのページに来て最初に欲しい答え（「これは何か」「自分は何を書けばいいか」）を起点に決める。元の現行解説書（`06_TestFWGuide/01_Abstract.rst`）の記載順をそのまま踏襲しない。

| 順 | セクション | 記載内容 |
|---|---|---|
| 1 | 全体像 | NTFの位置づけ（1〜2文）。JUnitベースであること。Nablarchに特化したテスト補助機能を提供すること |
| 2 | 特徴 | なぜNTFを使う価値があるか。3点（下記「特徴に置く3点」参照） |
| 3 | テストの種類 | クラス単体テスト / リクエスト単体テスト / 取引単体テストの違いと使い分け。リクエスト単体テストが対象とする処理方式ごとの内訳を含む |
| 4 | アーキテクチャ | 自動テストフレームワークの構成。テストクラスの継承構造。リクエスト単体テストがハンドラキューを通す仕組み |
| 5 | テストデータ | テストデータを外部ファイル化する意味。セットアップデータと期待値。データブロックの考え方 |
| 6 | 対象範囲 | 対応しないもの（Jakarta Batch、マルチスレッド機能）。対応する処理方式の一覧は「テストの種類」が持つため、ここでは `:ref:` で導線を置くにとどめる |
| 7 | 稼動環境 | JUnit 4 / JUnit 5。モジュール一覧（依存関係） |

**「テストの種類」を「アーキテクチャ」より前に置く。** 現行解説書・design.md旧版はアーキテクチャを先に置いていたが、「テストの種類」の目的は読者が自分の書くべきテストを判断できるようにすることであり、このページで最も行動につながる情報である。先に読ませることで、読者は目的の処理方式別ページ（第2部・第3部）に最短で辿り着ける。「アーキテクチャ」はその後に続けることで、直前に見た3種類の違い（例: リクエスト単体テストが「本番に近い構成でテストできる」）を支える仕組みの説明として機能する。

**「特徴」を「全体像」の直後、「テストの種類」より前に置く。** 「全体像」（これは何か）と「特徴」（なぜ使う価値があるか）は別の問いであり、分けて答える。「特徴」を先に読ませることで、後続の「テストの種類」（対比表の「本番に近い構成でテストできる」）・「アーキテクチャ」（ハンドラキューを通す仕組み）・「テストデータ」（外部化・データブロック）が、特徴で示した価値提案の詳細説明として機能する（2026-08-05 ユーザー提案）。

### 「特徴」に置く3点

1. **本番同等の経路でテストできる** — リクエスト単体テストはNAFのハンドラキューを通して実行されるため、環境差分以外は本番と同じ経路でテストできる
2. **テストコードは定型・少量で済む** — テストロジックはNTFが提供し、利用者はテストデータを宣言的に書くだけでよい（テストロジックとテストデータの分離）
3. **利用目的に応じたテストデータ形式を選べる** — 人が書きやすいExcel形式、AIが扱いやすいテキストのYAML形式を提供する

**1・2はマッピング行の `dest_section` を変更せず、同一ページ内の `:ref:` で解決する。** `current-0162`/`0164`/`0166`（`全体像`）・`current-0165`（`アーキテクチャ`）・`current-0163`/`0176`（`テストデータ`）はそのままの割当を維持し、「特徴」は1〜2文の要約＋詳細セクションへの `:ref:` にとどめる。特徴と詳細セクションは同一ページ内にあり、「重複がない」（design.md §11.1）が問題にする「複数ページに同じ内容が存在し片方だけ更新されて食い違う」状態ではないため、マッピング行を動かす必要がない（2026-08-05、実装時に確認）。

**3（Excel/YAML）は #8 の時点では保留する。** 唯一の出典は `input-0183`（`testdata-converter-design.md:13-15`、「ExcelのNTFテストデータをAIエージェントが扱えるYAMLにも対応させる」）だが、`dest_page=テストデータ変換ツール`（第4部、作成順は最後）に割当済み。本ページに同じ内容を新規行として重複させると「重複がない」に反する。第3部「テストデータの書き方」page（design.md L85 参照。作成順は本ページの次）に Excel/YAML比較の出典があるため、そちらの作成後に本ページへ短い要約＋`:ref:`を追加することを検討する。それまでは「特徴」は1・2の2点のみとする。

### 「テストの種類」に置く対比

読者が自分の書くべきテストを判断できるよう、以下を示す。

| テストの種類 | 実行方法 | テスト範囲 | 備考 |
|---|---|---|---|
| クラス単体テスト | JUnitで自動実行 | クラス単体 | エンティティ、コンポーネント |
| リクエスト単体テスト | JUnitで自動実行 | 1リクエスト（ハンドラキューを通す） | 本番に近い構成でテストできる |
| 取引単体テスト | 手動操作 | 複数リクエストにまたがる業務の流れ | APサーバへのデプロイが必要。エビデンスは画面ハードコピー・DBダンプ |

取引単体テストが自動テストではないことを明示する。

**リクエスト単体テストの処理方式ごとの内訳は、対比表の直後に地の文で続ける。独立した「正式名称」見出しは置かない。** 「本文書で使うテスト種別の正式名称の索引」という枠組みは、解説書の執筆側が用語を統一するための内部整理（`glossary.md`と同じ性質）であり、読者が読みたい情報ではない。読者にとっての事実は「リクエスト単体テストは、対象とする処理方式によって中身が変わる」というだけである。文言も「正式名称は以下のとおり」ではなく「リクエスト単体テストは、対象とする処理方式によって次の6つに分かれる」とする（2026-08-05 ユーザー指摘）。他ページから処理方式ごとの名称を参照するための `:ref:` アンカーは維持する（第2部・第3部が処理方式ごとの名称を使うため参照先として必要）。内容（`input-0028`、6処理方式の名称と一行説明）自体は変更しない。

**「Java・Jakarta EEの要件」は記載しない。** 現行解説書47ファイル・input資料10ファイルの全域を検索したが出典が存在しないため（`#6`確定、`checks/task-06.md`①参照）。

### モジュール一覧の集約

依存関係（`nablarch-testing`、`nablarch-testing-junit5`、JUnit関連等）は本ページの「稼動環境」に集約する。処理方式ごとのページには置かない。

処理方式固有の依存があるものだけ、当該ページに記載する。現時点で該当するのはRESTfulウェブサービス（`nablarch-testing-rest`、`nablarch-testing-jetty12`、`nablarch-testing-default-configuration`）およびYAML形式（`nablarch-testing-yaml`）。

## 3. 第2部 導入と設定

構成を以下のとおり確定する（`#6`確定、`checks/task-06.md`①③参照）。

```
導入と設定
├── 共通設定                    テストデータの配置、日時固定、採番、トランザクション等
├── クラス単体テストの設定
├── リクエスト単体テストの設定   処理方式ごと（6ページ）
│     ウェブアプリケーション / RESTfulウェブサービス / HTTPメッセージング /
│     Nablarchバッチアプリケーション / MOMによるメッセージング /
│     テーブルをキューとして使ったメッセージング
├── 取引単体テストの設定         処理方式ごと（3ページ）
│     RESTfulウェブサービス / HTTPメッセージング / MOMによるメッセージング
│     （実データがない ウェブアプリケーション / Nablarchバッチアプリケーション /
│      テーブルをキューとして使ったメッセージング はページを設けない）
├── JUnit 5用拡張機能
└── マスタデータ復旧機能
```

**「テストデータの形式」は廃止する。** Excel/YAMLの比較に相当する内容は既に第3部「テストデータの書き方」にあり移動は発生しない。「使い分け」（形式選択の判断指針）に相当する出典は存在しないため記載しない（`#6`確定、`checks/task-06.md`②参照）。

**「取引単体テストの設定」は実データのある3処理方式のみページ化する。** ウェブアプリケーション・Nablarchバッチアプリケーションは出典が0行のため（`#5b`実ファイル通読済み）、テーブルをキューとして使ったメッセージングは導線ページも設けない（`#6`確定、後述「6. 処理方式の名称」参照）。

処理方式ごとのページ名は `mapping/vocabulary.md` の確定語彙に従う。

### ページのアウトライン

第2部の各ページは以下のセクション構成に揃える。FW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）の型に倣う。

```
<ページタイトル>
├── 機能概要（任意）
│     全体像（図）              何がどうテストされるか
│     主なクラスとリソース      名称・役割・作成単位の表
│     前提事項                  適用できないケース
├── 使用方法（必須）
│     テストを実行できるようにする
│     コンポーネントを設定する
│     <個別設定>する
└── 拡張例（任意）
      <拡張手順>する
```

**「使用方法」のみ必須とし、「機能概要」「拡張例」は出典が無い場合は見出し自体を置かない。** 処理方式別ページのように設定量が薄いページでは、独立した機能概要・拡張例の出典が構造的に存在しないことがあるため（`#6`確定・design.md §3改訂、`checks/task-06.md`未処理1参照）。省略した場合も `verify_mapping.py` は0件を advisory として出力し続け、割当漏れの兆候として監視する。

**セクションタイトルは「〜する」形式とし、`mapping/style.md`のセクションタイトル規約（ページタイトルとの組で内容が分かること）に従う。** 読者がタイトルを見て目的の情報に辿り着けること。ライブラリの「排他制御を使うために準備する」「楽観的ロックを行う」と同じ形式。

「主なクラスとリソース」の表にクラスの役割を集約する。同じクラスの説明を拡張例で再掲しない。拡張例では「拡張するには〇〇を継承する」と手順として記載する。

### 記載範囲

| 記載する | 記載しない |
|---|---|
| 主なクラスとリソース | テストソースコードの実装例 |
| コンポーネント設定ファイルの設定項目一覧 | テストデータの記述例 |
| 設定ファイルの記述例 | |
| 拡張方法（クラス差し替え、独自Extension等） | |

「使い方」に該当するものは第3部に置き、第2部からは `:ref:` で参照する。

## 4. 第3部 テストの実装方法

```
テストの実装方法
├── テストデータの書き方                            1ページ
├── テストデータの記載例                            1ページ
├── クラス単体テスト
│     ├── エンティティ単体テスト
│     └── コンポーネント単体テスト
├── リクエスト単体テスト
│     ├── ウェブアプリケーション
│     ├── RESTfulウェブサービス
│     ├── HTTPメッセージング
│     ├── Nablarchバッチアプリケーション
│     ├── MOMによるメッセージング
│     └── テーブルをキューとして使ったメッセージング
└── 取引単体テスト
      ├── ウェブアプリケーション
      ├── RESTfulウェブサービス
      ├── HTTPメッセージング
      ├── Nablarchバッチアプリケーション
      ├── MOMによるメッセージング
      └── テーブルをキューとして使ったメッセージング
```

処理方式ごとのページ名は、`dest_page` の値だけでテスト種別を判別できるよう、マッピング上は `リクエスト単体テスト（ウェブアプリケーション）` の形式を維持する（`mapping/vocabulary.md` の定義）。

**取引単体テストは6ページ（実データのある5処理方式＋テーブルをキューとして使ったメッセージングの導線1）を維持する。** 第2部「取引単体テストの設定」が3処理方式に絞られるのとは異なり、第3部の取引単体テストは全6処理方式に実データまたは導線としての出典があるため、ページ構成を縮小しない（`#6`確定、`checks/task-06.md`③未処理2参照）。行数の小さい3ページ（HTTPメッセージング33行・RESTfulウェブサービス32行・ウェブアプリケーション48行）も統合せず独立ページとして残す。

### ページのアウトライン

第3部の各ページは以下のセクション構成に揃える。

```
<ページタイトル>
├── 機能概要        このページで何ができるようになるか
└── 使用方法
      テストクラスを作成する
      テストメソッドを作成する
      テストデータを作成する      （「テストデータの書き方」への :ref:）
      テストを実行する
      テスト結果を確認する
```

**拡張例は第3部に置かない。** 拡張はコンポーネント設定とクラス差し替えであり、アーキテクトの領域のため第2部に置く。

**セクションタイトルは「〜する」形式とする。**

### テストデータの2ページ

| ページ | 役割 |
|---|---|
| テストデータの書き方 | 記法の仕様。どう書けばどう解釈されるか |
| テストデータの記載例 | 用途別の実例。Excel と YAML の対比で示す |

**それぞれ1ページにまとめる。** 開発者が記法を調べるとき、テーブル・ファイル・メッセージングを同じページ内で探せる状態にする。ページを跨がせない。

**「書き方」から「記載例」へのリンクを必須とする。** 仕様を読んだ読者が対応する実例に到達できること。

**この2ページにも一般の第3部ページアウトライン（機能概要＋使用方法）を適用する。** 候補出典（各資料の冒頭導入文・全体像節）を実ファイルで通読した結果、「テストデータの書き方」は主要出典（`ntf-testdata-doc.md`、ページ全体を対象とする唯一の導入文）が機能概要に該当し確定する。「テストデータの記載例」は候補5件がいずれも個別カテゴリ（ファイル/メッセージング/特殊値/テーブル/testShots）の記述例集ごとの導入文であり、ページ全体を対象にした記述が出典に存在しないため、機能概要を持たない例外ページとして確定する（`HTMLチェックツール`の「導入」と同型の扱い）。判断根拠と移した行・移さなかった行は`#6`確定、`checks/task-06.md`分類6を参照。

## 5. 第4部 ツール

NTFが提供するツールを、ツールごとに1箇所にまとめる。導入と使い方を同じ場所に置き、他の部を行き来せずに完結させる。

```
ツール
├── リクエスト単体データ作成ツール    ブラウザ操作からテストデータを作成する
├── テストデータ変換ツール            Excel と YAML を相互変換する
├── マスタデータ投入ツール            データベースにマスタデータを投入する
└── HTMLチェックツール                HTMLの妥当性を検査する
```

### ページのアウトライン

```
<ツール名>
├── 機能概要        何ができるか。どの場面で使うか
├── 導入            インストール手順、依存関係、設定
└── 使用方法
      <操作手順>する
```

現行解説書のリクエスト単体データ作成ツールとマスタデータ投入ツールは、本体ページとインストールガイドの2ページに分かれている。これを1ページに統合し、「導入」セクションとして収める。

HTMLチェックツールはリクエスト単体テストに標準で組み込まれ、テスト実行時に自動実行される。インストール手順を持たないため「導入」セクションは設けず、実行要否や検査内容の設定を「使用方法」に記載する。

**テストデータ変換ツールも「導入」を持たない。** 出典（`testdata-converter-design.md`全362行）にインストール手順・依存関係・設定に該当する記述が存在しないため（実ファイル通読済み）。候補となる記述（解くべき課題、形式に依存するか否かという設計思想の説明）はいずれも「機能概要」に該当する（`#6`確定、`checks/task-06.md`分類8参照）。

### 第2部・第3部との切り分け

ツールの設定であっても、第2部には置かない。ツールを使う人が1箇所で完結できることを優先する。第2部・第3部からツールに言及する場合は `:ref:` で参照する。

### テーブルをキューとして使ったメッセージング

扱いはページ単位で異なる（`#6`確定、`checks/task-06.md`参照）。

## 7. 用語

### 用語集を作成する

既存解説書とinput資料で用語が揺れているため、マッピングと合わせて用語集を作成し、全ページで統一する。

用語集の作成方針は次のとおり。

- 既存解説書（`ja/development_tools/testing_framework/`）とinput資料の双方から用語を抽出する
- FW解説書に同じ概念の用語がある場合、**FW解説書の用語を採用する**
- input資料の `ntf-doc-terms.md` は用語の候補として扱う。そのまま採用せず、既存解説書およびFW解説書と突き合わせて確定する
- 表記揺れ（例: 「主なクラス, リソース」と「主なクラスとリソース」）は正表記を1つ決める

### 「〜したい」形式の見出しを廃止する

現行の「目的別API使用方法」（`03_Tips.rst`）は「〜したい」形式の逆引きページだが、独立ページとしては設けない。

各項目は該当する第2部・第3部のページの「使用方法」セクションにマージし、見出しを「**〜する**」形式に統一する。読者はセクションタイトルから直接辿り着ける。

## 8. トンマナ

既存解説書のRSTとinput資料は、いずれもFW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）と記述の調子が揃っていない。作成するページは**FW解説書のライブラリに揃える**。

揃える対象は以下。

- 文体（だ・である調）
- セクションタイトルの形式（「〜する」）。加えて、ページ作成時は `mapping/style.md` のセクションタイトル規約（ページタイトルとセクションタイトルの組で一意であり、かつその組だけで中身が分かること。`#6`確定）に従う
- 見出しのアンダーライン記法
- コードブロックのインデントと言語指定
- アドモニション（`tip` / `note` / `important`）の使い分け
- 表の記法
- `:ref:` ラベルの命名規則
- 1文の長さ、改行位置

**既存RSTおよびinput資料の文面をそのまま流用しない。** 内容は引き継ぐが、記述はFW解説書の調子に合わせて書き直す。

### 出典と確定設計が食い違う場合

出典（現行解説書・input資料）と、`#6` で確定した設計（`design.md` の各節、
`mapping/vocabulary.md` のページ名、`mapping/glossary.md` の正表記）が食い違う場合、
**確定した設計を優先する。**

出典に無いことは、確定した設計に基づく記述を妨げない。「マッピングにない内容を
追加しない」が禁じているのは、出典にも確定設計にも根拠のない**新規の主題内容**を
書くことであって、確定設計を反映することではない。

例（`#8` A-3）: テスト種別の正式名称表は本文書の名称索引であり、`vocabulary.md` の
ページ名と一致させる。出典 `input-0028` が6区分時代の資料で当該行を持たないことは、
行を落とす根拠にならない。

## 10. マッピングの仕組み

本書の章構成に従って解説書を再構築するにあたり、記載内容が失われないこと、および各記述の出自を追えることを保証する仕組みを定める。

### 10.1 ファイルの関係

```
[入力]
  develop の ja/development_tools/testing_framework/   47 rst
  .rn/20260724-ntf-yaml-support/input/                 10 md
        │
        │  mapping/tools/extract_sections.py
        ▼
[全量の台帳]
  mapping/sections-current.csv    377セクション   9,783行
  mapping/sections-input.csv      202セクション   3,203行
                                  計579セクション 12,986行
        │
        │  30バッチのサブエージェント
        │  （判断材料）
        │    design.md        割当先の定義
        │    vocabulary.md    dest_page / dest_section の許容値
        │    split-plan.md    100行超23セクションの分割位置
        │    glossary.md      用語の正表記
        │    style.md         記述規約
        ▼
[中間成果物]
  mapping/_batch/batch-01.csv 〜 batch-30.csv
        │
        │  統合
        ▼
[最終成果物]
  mapping/mapping.csv
        │
        │  mapping/tools/verify_mapping.py
        ▼
[検証]
```

`_batch/` は統合後も残す。どのサブエージェントがどのセクションを判断したかを追跡でき、指摘が出たときの再実行単位が明確になるため。

### 10.2 網羅性の保証

3段階で担保する。

| 段階 | 保証すること | 検証方法 |
|---|---|---|
| 抽出時点 | 全行がいずれかのセクションに属する | `body_start_line`〜`body_end_line` の和集合が全行を覆い、未カバーの非空行が0件であること |
| マッピング時点 | 全セクションが `mapping.csv` に登場し、行が消えていない | `verify_mapping.py`（下表） |
| ページ作成時点 | `mapping.csv` の該当行がページに反映されている | 観点A（網羅性）のサブエージェントレビュー |

抽出時点の検証により、**12,986行が台帳の全量**であることが確定している。

`verify_mapping.py` が機械検証する項目は次のとおり。

| 検査 | 意味 |
|---|---|
| 全 `section_id` が `mapping.csv` に登場する | セクションの取りこぼしゼロ |
| 各セクションについて、紐づく行の行範囲の和集合が元のセクション範囲と一致する（隙間・重複ゼロ） | `SPLIT` で行が消えていない |
| `lines` 合計が 12,986 と一致する | 全量が台帳に載っている |
| `dest_part` / `dest_page` / `dest_section` が `vocabulary.md` の値と完全一致する | 存在しないページへの割当を防ぐ |
| `disposition` / `audience` / `dest_page` に空欄がない | 判断漏れがない |
| `DROP` の全行に `note` がある | 落とした根拠が残る |
| 重複を理由とする `DROP` に、重複先の `section_id` が記載されている | 重複を口実に内容が失われることを防ぐ |
| 同一内容が複数の `dest_page` に `MOVE` されていない | 重複の混入を検出する（検出のみ。判定は人が行う） |

`lines` 合計 12,986 の一致は、`DROP` 行を `mapping.csv` に残す限り必ず成立する。これは**取りこぼしがないこと**の確認であって、**全量が新構成に移ったこと**の証明ではない。両者を混同しないよう、`verify_mapping.py` は次の2つを並べて出力する。

- `lines` 合計（全行）— 台帳の全量
- `lines` 合計（`DROP` を除く）— 新構成に移る実質的な分量

### 10.3 トレーサビリティ

`mapping.csv` の1行が、出典と行先を両方向に指す。

```
mapping_id      M-0087
src_section_id  current-0080
src_type        current
src_file        .../05_UnitTestGuide/02_RequestUnitTest/index.rst
src_body_start  132
src_body_end    145
heading_path    リクエスト単体テストの実施方法 > テストデータの書き方 > setUpDbシート
lines           14
audience        user
dest_part       第3部 テストの実装方法
dest_page       テストデータの書き方
dest_section    使用方法
disposition     MOVE

```

これにより次が追える。

- **出典 → 行先** — 旧解説書のこの14行がどのページのどのセクションへ移ったか
- **行先 → 出典** — 新ページのこの記述がどこから来たか
- **失われたもの** — `disposition=DROP` の行と、その理由
- **判断主体** — `_batch/` のどのCSVに含まれるかで、どのサブエージェントが判断したか

## 11. 刷新の品質担保

本刷新は現行解説書を全面的に作り直す。作り直しは記載内容が失われる危険を伴うため、何をどう担保するかを定める。

### 11.1 担保すべき4点

| # | 担保すること | 失敗したときに起きること |
|---|---|---|
| 1 | 全量を失わない | 現行解説書にあった情報が新解説書から消える |
| 2 | 重複がない | 同じ内容が複数ページにあり、片方だけ更新されて食い違う |
| 3 | 用語が統一されている | 同じものが別の名前で呼ばれ、読者が別物と誤解する |
| 4 | トンマナが揃っている | ページごとに調子が違い、解説書全体として読みにくい |

### 11.2 白紙から作る

現行ファイルを部分的に編集する方式は採らない。**現行の解説書を削除してから、マッピングに基づいて1ページずつ作成する。**

理由は3点。

- 旧記述が残ったまま新記述を追加すると、重複が発生する
- どの記述がどの作業で入ったか追跡できなくなる
- **マッピングにない記述の混入を検出できない**

削除後に増えたファイルはすべてマッピングに基づくものになる。混入を構造的に防げる。削除しても develop ブランチで元の内容を参照できるため、情報は失われない。

### 11.3 マッピングを唯一の基準とする

作成するページの内容は `mapping/mapping.csv` に従う。**マッピングにない記述を追加しない。マッピングにある記述を落とさない。** 判断に迷う場合は、その場で判断せずレビューに上げる。

マッピングそのものの網羅性は「10. マッピングの仕組み」で担保する。

### 11.4 1ページずつ作り、1ページずつレビューする

1ページ作成するごとにレビューを行い、承認を得てから次ページへ進む。まとめて作らない。

理由は、**差分を小さく保ち、全量を確認できる状態を維持する**ため。20ページを一度に作れば、レビューは要点の抜き取りにならざるを得ない。1ページなら、マッピングの該当行とページの内容を1対1で突き合わせられる。

### 11.5 最初の1ページで基準を作る

第1部（概念、1ページ）を作った時点で、以下を確認する。

- 書き直しの度合いは適切か（変えすぎていないか、変えなさすぎないか）
- 内容が失われていないか
- トンマナが揃っているか

ここで基準が固まれば、残りのページは同じ基準で進められる。**方針が誤っていた場合の手戻りを1ページ分に抑える。**

### 11.6 ページごとの4観点レビュー

各ページについて、以下4つを**それぞれ別のサブエージェント**で実施する。1つのサブエージェントに複数観点を持たせない。観点を混ぜると、どれかが手薄になる。

| 観点 | 見るもの | 入力 |
|---|---|---|
| **A 網羅性** | `mapping.csv` の当該 `dest_page` の行がすべて反映されているか。`disposition` ごとの扱いが正しいか（`REFERENCE` が本文を持っていないか、`DROP` が混入していないか）。出典と照合して記載が欠落していないか | `mapping.csv` の該当行、作成したページ、出典ファイル |
| **B トンマナ** | `style.md` の全規約に適合しているか。セクション構成が本書のページアウトラインと一致しているか。セクションタイトルが「〜する」形式か。**ページタイトル＋セクションタイトルの組で中身が分かるか**（`style.md` セクションタイトル規約）。**出典の逐語的流用がないか**（判定基準は本節末尾「観点Bの判定基準」参照） | 作成したページ、`style.md`、本書、FW解説書ライブラリ |
| **C 用語** | `glossary.md` の正表記が使われているか。揺れ表記が混入していないか。処理方式の名称が正式名称と一致しているか | 作成したページ、`glossary.md` |
| **D 整合性** | 他ページと内容が重複していないか。`:ref:` の参照先が実在するか。参照が一方向で切れていないか。前提の矛盾がないか。第2部に使い方が、第3部に設定が混入していないか。**見出し・導入文と実際の中身が一致しているか**（チェック項目は本節末尾「観点Dのチェック項目」参照） | 作成したページ、作成済みの全ページ、本書 |

観点AとDが「11.1 担保すべき4点」の1と2に、CとBが3と4に対応する。

**観点Bの判定基準（出典の逐語的流用）**

「出典の骨格を踏襲している」のような主観的な基準では判定がぶれる。指摘してよいのは、次のいずれかに当てはまる場合に限る。

- 出典の一文がほぼそのまま（語順・接続・修飾関係が一致した状態で）残っている
- 出典の見出し・箇条書きの構造がそのまま持ち込まれている
- 出典固有の言い回し（現行解説書の「〜すること。」調の指示文など）がそのまま残っている

次は指摘しない。

- 用語・クラス名・データタイプ名・短い技術的言明（20字程度まで）の一致。言い換えると意味が変わるため
- 列挙の順序が出典と同じであること。順序自体が出典の示すモデルである場合がある
- 出典と同じ事実を述べていること。事実は変えられない

**字数は目安であり、厳密な閾値ではない。** 一文で完結する技術的な結論（「テストソースコードの重複を大幅に削減できる」等）は、
20字をやや超えていても、言い換えると結論の強さ・対象・因果関係が変わってしまう場合は指摘しない。逆に、20字以内でも
文全体の構造（主語・述語・接続）が出典の一文と一致していれば指摘してよい。**すでにユーザーが実物比較のうえ「対応不要」
と判定した箇所は、本基準を機械的に再適用して蒸し返さない。** ユーザーの個別判断は本基準より優先する。

指摘する場合は、**出典の該当文と成果物の該当文を並べて引用する**こと。並べられない指摘は出さない。

**観点Dのチェック項目（見出し・導入文と中身の一致）**

- [ ] 各セクション見出しが、そのセクションの実際の中身を表しているか
- [ ] 表・箇条書き・コード例の導入文が、直後の実物の中身と一致しているか（導入文が対象を限定しているのに、実物にはその範囲外の項目が含まれていないか）
- [ ] ページタイトル＋セクションタイトルの組だけで中身が分かるか（`style.md` の規約）

### 11.7 レビューの運用

- 指摘には重大度区分を付ける。区分は次の3つに限る

| 区分 | 内容 | 扱い |
|---|---|---|
| `must` | 事実誤り、`glossary.md` の正表記違反、`style.md` の規約違反、見出し・導入文と中身の不一致、`design.md` の構成違反、`vocabulary.md` のページ名・`design.md` の確定内容との不一致 | レビューラウンド内で必ず修正する。ユーザー判断に回さない |
| `decide` | 出典にない内容の追加可否、ページ構成の選択など、規約で決まらない判断 | ユーザーに上げる |
| `note` | 規約に反しないが改善余地がある表現 | 記録するのみ。修正ラウンドを費やさない |

- レビューは**最大3ラウンド**。**3ラウンド上限に達してユーザーレビューに上げてよいのは `decide` のみ。** `must` が残った状態でユーザーレビューに上げない。`must` が3ラウンドで解消しない場合は、自己判断で4ラウンド目を実施するのではなく、原因（指摘が不明確／修正が反映されない等）を記録して報告する
- 指摘は**対応の有無にかかわらず全件記録する**。対応しないと判断したものも、理由とともに残す
- 指摘が0件だったラウンドも、その旨を記録する
- レビュー記録は `reviews/page-<ページID>.md` に、以下の形式で残す

| 列 | 内容 |
|---|---|
| 指摘ID | 一意 |
| ラウンド | 1〜3 |
| 観点 | A / B / C / D |
| 区分 | `must` / `decide` / `note` |
| 指摘内容 | |
| 対応要否 | 要 / 不要 |
| 不要の理由 | 「不要」の場合は必ず記入 |
| 対応内容 | |

対応しなかった指摘を消さないのは、**後から「なぜそう判断したか」を検証できるようにする**ため。記録がなければ、見落としと意図的な判断を区別できない。

### 11.8 機械検証できないもの

次の3点は機械検証の対象外であり、人またはサブエージェントの判断に委ねる。曖昧にせず、担保方法を定めておく。

**割当先が適切かどうか**

`dest_page` が `vocabulary.md` に存在することは検証できるが、その割当先が内容に照らして適切かは検証できない。マッピング作成時の3観点レビュー（割当先の妥当性 / `disposition` の妥当性 / `audience` の妥当性）で担保する。

**`DROP` が妥当かどうか**

`note` に理由が書かれているかは検証できるが、その理由が妥当かは検証できない。マッピング統合後に `DROP` の全件をレビューする。内容が失われるかどうかを決める最後の砦であるため、件数の多寡にかかわらず全件を対象とする。

**書き直しによる内容の変質**

本刷新では出典の文面をそのまま流用せず、トンマナに合わせて書き直す（「8. トンマナ」）。書き直しの過程で内容が変質する危険があり、これは機械検証できない。観点Aのレビューで出典と照合して検出するが、完全ではない。**1ページずつ作り、1ページずつレビューする理由がここにある。**

### 11.9 段階ごとのゲート

各段階で担保することと、次に進む条件を定める。前段階の承認を得るまで次に進まない。

| 段階 | 担保すること | 次に進む条件 |
|---|---|---|
| セクション抽出 | 現行解説書とinput資料の全行が台帳に載る | 未カバーの非空行0件、冪等性（md5一致） |
| 用語集 | 表記揺れの正表記が確定する | 表記揺れが実在する用語と、本書が章・セクション名に使う用語を網羅 |
| トンマナ規約 | 記述の基準が明文化される | 8観点すべてにFW解説書からの根拠2件以上 |
| 分割判断 | 大きいセクションの分割位置が確定する | 分割後の行範囲が元セクションを過不足なく覆う |

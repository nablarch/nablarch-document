# NTF解説書 刷新設計

## 1. 読者と構成

読者は2種類。両者に共通する前提は独立させ、3部構成とする。

| 読者 | 知りたいこと | 参照する部 |
|---|---|---|
| アーキテクト | NTFの全体構造・仕組み・設定 | 第1部、第2部 |
| アプリ開発者 | テストの書き方 | 第1部、第3部 |

第4部はツールの利用者が参照する。ツールごとに導入と使い方を1箇所にまとめ、他の部を行き来せずに完結させる。

```
テスティングフレームワーク
├── テスティングフレームワークとは      第1部・概念（両読者の共通前提）
├── 導入と設定                          第2部・アーキテクト向け
├── テストの実装方法                    第3部・アプリ開発者向け
└── ツール                              第4部・ツールごとに完結
```

読者の振り分けは最上位 `index.rst` の本文で行う。

### 「全体像」に含める特徴

各特徴は「Xができる」という能力の提示だけで終えず、それによって読者（アプリ開発者・アーキテクトのいずれか、あるいは両方）にとって何が嬉しいのかという具体的な裏付け・帰結までを1つの塊として書く。2026-08-05 #8フィードバック「特徴、XXXできる、だから何が嬉しいの？利用者のベネフィットを伝えませんか？」を受けた規約。

1. **本番同等の経路でテストできる** — リクエスト単体テストはNAFのハンドラキューを通して実行されるため、環境差分以外は本番と同じ経路でテストできる。単体テストの段階から経路に起因する不具合を早期に見つけられ、結合テストや本番運用まで問題を持ち越さずに済む
2. **テストコードは定型・少量で済む** — テストデータのセットアップや期待値とのアサートなどのテストロジックはNTFが提供し、利用者はテストデータをテストコードとは別ファイルに宣言的に書くだけでよい。基幹システムはテーブル数や項目数が多くテストデータのパターンも多数に上りやすいため、テストデータをテストコードから切り離せることは、大量のテストケースを効率的に用意・保守するうえで欠かせない（2026-08-05 `/rn:gm`フィードバック「テストコードは定型かつ少量で済むには、暗黙的にテストデータの外部化が含まれてますよね。基幹システムだとテーブル数やカラム数など大規模なデータが想定されるので、外部化必須ですよね」を受けて改訂。旧「テストデータ」節が担っていた外部化の事実をここへ統合した。詳細は下記「「テストデータ」節を廃止する」参照）
3. **利用目的に応じたテストデータ形式を選べる** — 人が書きやすいExcel形式、AIが扱いやすいテキストのYAML形式を相互変換可能な形で提供する。開発者がレビュー・編集する場面とAIエージェントが自動生成・解析する場面のどちらにも、同じテストデータ資産を使い分けられる
4. **使い慣れたJUnitの書き方をそのまま活かせる** — JUnit 4を基盤とするため、アノテーション・assertメソッドなどJUnitの機能や知識をそのまま使え、新たに専用の記法を覚える必要がなく学習コストを抑えて導入できる

**マッピング行の `dest_section` は変更しない。** 4点とも実体は `全体像` セクション（統合後のH2）の中にそのまま存在する。

- 1・2・4: `current-0162`/`0164`/`0166`（JUnitベース・Nablarch特化API・JUnit4互換性とコード例）・`current-0165`（アーキテクチャの図。ハンドラキューを通す仕組みの裏付けとして1点目が要約）は `全体像`／`アーキテクチャ` という元の割当のまま存在し、特徴の各点はその要約として同一ページ内に新規マッピング行を追加せず書く。`current-0163`/`0176`（テストデータ外部化）は、2026-08-05 #8フィードバック対応（「テストデータ」節廃止、下記参照）で `dest_section` を `テストデータ` から `全体像` へ変更し、2点目の要約として統合した。

### 「テストの種類」に置く対比

読者が自分の書くべきテストを判断できるよう、以下を示す。

| テストの種類 | 実行方法 | テスト範囲 | 備考 |
|---|---|---|---|
| クラス単体テスト | JUnitで自動実行 | クラス単体 | エンティティ、コンポーネント |
| リクエスト単体テスト | JUnitで自動実行 | 1リクエスト（ハンドラキューを通す） | 本番に近い構成でテストできる |
| 取引単体テスト | 手動操作 | 複数リクエストにまたがる業務の流れ | APサーバへのデプロイが必要。エビデンスは画面ハードコピー・DBダンプ |

取引単体テストが自動テストではないことを明示する。

**リクエスト単体テストの処理方式ごとの内訳は、対比表の直後に地の文で続ける。独立した「正式名称」見出しは置かない。** 「本文書で使うテスト種別の正式名称の索引」という枠組みは、解説書の執筆側が用語を統一するための内部整理（`glossary.md`と同じ性質）であり、読者が読みたい情報ではない。読者にとっての事実は「リクエスト単体テストは、対象とする処理方式によって中身が変わる」というだけである。文言も「正式名称は以下のとおり」ではなく「リクエスト単体テストは、対象とする処理方式によって次の6つに分かれる」とする（2026-08-05 ユーザー指摘）。他ページから処理方式ごとの名称を参照するための `:ref:` アンカーは維持する（第2部・第3部が処理方式ごとの名称を使うため参照先として必要）。

**内訳の表は、リクエスト単体テストの6処理方式のみを載せる。クラス単体テスト・取引単体テストの行は載せない。** 2026-08-05 #8フィードバック「このうちリクエスト単体テストは、対象とする処理方式によって、次の6つに分かれる、の下にある表にクラス単体、取引単体を含めてるのはなぜ？不要では？」を受けて改訂。出典 `input-0028` は元々クラス単体テスト・6処理方式・取引単体テストの計8行を持つが、クラス単体テスト・取引単体テストの2行（名称と一行説明のみ）は、直前の3行対比表（本節）が既に同じ事実を保持しており、そのまま載せると「次の6つに分かれる」という導入文と矛盾するうえ「重複がない」（design.md §11.1）にも反する。したがって内訳表は6処理方式の行のみを残す。6処理方式の名称・説明文自体は変更しない。

### テストデータの2ページ

| ページ | 役割 |
|---|---|
| テストデータの書き方 | 記法の仕様。どう書けばどう解釈されるか |

**上記2つの例外のうち、「テストデータの書き方」には第3部ページアウトラインを機能概要＋テストデータの構造＋使用方法の形で適用し、「テストデータの記載例」はページアウトラインの2セクションをいずれも持たない構成にする。** 「テストデータの書き方」は主要出典（`ntf-testdata-doc.md`、ページ全体を対象とする唯一の導入文）が機能概要に該当し確定する。「テストデータの記載例」は候補5件がいずれも個別カテゴリ（ファイル/メッセージング/特殊値/テーブル/testShots）の記述例集ごとの導入文であり、ページ全体を対象にした記述が出典に存在しないため機能概要を持たない（`HTMLチェックツール`の「導入」と同型の扱い）。当初はこれに加えて「使用方法」1セクションで全カテゴリを束ねる構成にしていたが、2026-08-06のユーザー指摘（「記載例のセクションが並ぶだけのページに『使用方法』という見出しは合わない」）を受けて撤回した。本ページは「使用方法」という1つの説明を持たず、見出しをL2として並べるだけの構成にする。並べる見出しは次のとおりとする。

- 「テストデータの書き方」の`使用方法`配下の各L3と同名の見出し（例: 「テーブルのデータを記述する」「LIST_MAPのデータを記述する」）

## 5. 第4部 ツール

NTFが提供するツールを、ツールごとに1箇所にまとめる。導入と使い方を同じ場所に置き、他の部を行き来せずに完結させる。

```
ツール
├── リクエスト単体データ作成ツール    ブラウザ操作からテストデータを作成する
├── テストデータ変換ツール            Excel と YAML を相互変換する
├── マスタデータ投入ツール            データベースにマスタデータを投入する
└── HTMLチェックツール                HTMLの妥当性を検査する
```

### ページのアウトライン

```
<ツール名>
├── 機能概要        何ができるか。どの場面で使うか
├── 導入            インストール手順、依存関係、設定
└── 使用方法
      <操作手順>する
```

現行解説書のリクエスト単体データ作成ツールとマスタデータ投入ツールは、本体ページとインストールガイドの2ページに分かれている。これを1ページに統合し、「導入」セクションとして収める。

HTMLチェックツールはリクエスト単体テストに標準で組み込まれ、テスト実行時に自動実行される。インストール手順を持たないため「導入」セクションは設けず、実行要否や検査内容の設定を「使用方法」に記載する。

**テストデータ変換ツールも「導入」を持たない。** 出典（`testdata-converter-design.md`全362行）にインストール手順・依存関係・設定に該当する記述が存在しないため（実ファイル通読済み）。候補となる記述（解くべき課題、形式に依存するか否かという設計思想の説明）はいずれも「機能概要」に該当する（`#6`確定、`checks/task-06.md`分類8参照）。

### 第2部・第3部との切り分け

ツールの設定であっても、第2部には置かない。ツールを使う人が1箇所で完結できることを優先する。第2部・第3部からツールに言及する場合は `:ref:` で参照する。

## 8. トンマナ

既存解説書のRSTとinput資料は、いずれもFW解説書のライブラリ（`ja/application_framework/application_framework/libraries/`）と記述の調子が揃っていない。作成するページは**FW解説書のライブラリに揃える**。

揃える対象は以下。

- 文体（だ・である調）
- セクションタイトルの形式（「〜する」）。加えて、ページ作成時は `mapping/style.md` のセクションタイトル規約（ページタイトルとセクションタイトルの組で一意であり、かつその組だけで中身が分かること。`#6`確定）に従う
- 見出しのアンダーライン記法
- コードブロックのインデントと言語指定
- アドモニション（`tip` / `note` / `important`）の使い分け
- 表の記法
- `:ref:` ラベルの命名規則
- 1文の長さ、改行位置
- 各ページ先頭の目次（`.. contents::` ディレクティブ）（2026-08-06、`/rn:gm`フィードバックにより追加。`mapping/style.md` S-09参照）
- Excel/YAML形式を対比するイラストの書き方（識別子行は表の外・普通の文字、紛れる場合は太字ラベル）（2026-08-06、`/rn:gm`フィードバックにより追加。`mapping/style.md` S-10参照）

**既存RSTおよびinput資料の文面をそのまま流用しない。** 内容は引き継ぐが、記述はFW解説書の調子に合わせて書き直す。

### 出典と確定設計が食い違う場合

出典（現行解説書・input資料）と、`#6` で確定した設計（`design.md` の各節、
`mapping/vocabulary.md` のページ名、`mapping/glossary.md` の正表記）が食い違う場合、
**確定した設計を優先する。**

出典に無いことは、確定した設計に基づく記述を妨げない。「マッピングにない内容を
追加しない」が禁じているのは、出典にも確定設計にも根拠のない**新規の主題内容**を
書くことであって、確定設計を反映することではない。

例（`#8` A-3）: テスト種別の正式名称表は本文書の名称索引であり、`vocabulary.md` の
ページ名と一致させる。出典 `input-0028` が6区分時代の資料で当該行を持たないことは、
行を落とす根拠にならない。

### 出典と実装が食い違う場合

出典の記述が、検証可能な実装の挙動と食い違う場合は、実装を優先する。根拠として、
確認した実装のファイル名・行番号・参照したコミットを `reviews/page-*.md` に記録する。
実装を確認できない場合は `decide` としてユーザーに上げる。

### 10.1 ファイルの関係

```

        │    design.md        割当先の定義

```

`_batch/` は統合後も残す。どのサブエージェントがどのセクションを判断したかを追跡でき、指摘が出たときの再実行単位が明確になるため。

### 10.2 網羅性の保証

3段階で担保する。

| 段階 | 保証すること | 検証方法 |
|---|---|---|
| 抽出時点 | 全行がいずれかのセクションに属する | `body_start_line`〜`body_end_line` の和集合が全行を覆い、未カバーの非空行が0件であること |
| マッピング時点 | 全セクションが `mapping.csv` に登場し、行が消えていない | `verify_mapping.py`（下表） |
| ページ作成時点 | `mapping.csv` の該当行がページに反映されている | 観点A（網羅性）のサブエージェントレビュー |

抽出時点の検証により、**12,986行が台帳の全量**であることが確定している。

`verify_mapping.py` が機械検証する項目は次のとおり。

| 検査 | 意味 |
|---|---|
| 全 `section_id` が `mapping.csv` に登場する | セクションの取りこぼしゼロ |
| 各セクションについて、紐づく行の行範囲の和集合が元のセクション範囲と一致する（隙間・重複ゼロ） | `SPLIT` で行が消えていない |
| `lines` 合計が 12,986 と一致する | 全量が台帳に載っている |
| `dest_part` / `dest_page` / `dest_section` が `vocabulary.md` の値と完全一致する | 存在しないページへの割当を防ぐ |
| `disposition` / `audience` / `dest_page` に空欄がない | 判断漏れがない |
| `DROP` の全行に `note` がある | 落とした根拠が残る |
| 重複を理由とする `DROP` に、重複先の `section_id` が記載されている | 重複を口実に内容が失われることを防ぐ |
| 同一内容が複数の `dest_page` に `MOVE` されていない | 重複の混入を検出する（検出のみ。判定は人が行う） |

`lines` 合計 12,986 の一致は、`DROP` 行を `mapping.csv` に残す限り必ず成立する。これは**取りこぼしがないこと**の確認であって、**全量が新構成に移ったこと**の証明ではない。両者を混同しないよう、`verify_mapping.py` は次の2つを並べて出力する。

- `lines` 合計（全行）— 台帳の全量
- `lines` 合計（`DROP` を除く）— 新構成に移る実質的な分量

## 11. 刷新の品質担保

本刷新は現行解説書を全面的に作り直す。作り直しは記載内容が失われる危険を伴うため、何をどう担保するかを定める。

### 11.1 担保すべき4点

| # | 担保すること | 失敗したときに起きること |
|---|---|---|
| 1 | 全量を失わない | 現行解説書にあった情報が新解説書から消える |
| 2 | 重複がない | 同じ内容が複数ページにあり、片方だけ更新されて食い違う |
| 3 | 用語が統一されている | 同じものが別の名前で呼ばれ、読者が別物と誤解する |
| 4 | トンマナが揃っている | ページごとに調子が違い、解説書全体として読みにくい |

### 11.2 白紙から作る

現行ファイルを部分的に編集する方式は採らない。**現行の解説書を削除してから、マッピングに基づいて1ページずつ作成する。**

理由は3点。

- 旧記述が残ったまま新記述を追加すると、重複が発生する
- どの記述がどの作業で入ったか追跡できなくなる
- **マッピングにない記述の混入を検出できない**

削除後に増えたファイルはすべてマッピングに基づくものになる。混入を構造的に防げる。削除しても develop ブランチで元の内容を参照できるため、情報は失われない。

### 11.3 マッピングを唯一の基準とする

作成するページの内容は `mapping/mapping.csv` に従う。**マッピングにない記述を追加しない。マッピングにある記述を落とさない。** 判断に迷う場合は、その場で判断せずレビューに上げる。

マッピングそのものの網羅性は「10. マッピングの仕組み」で担保する。

### 11.4 1ページずつ作り、1ページずつレビューする

1ページ作成するごとにレビューを行い、承認を得てから次ページへ進む。まとめて作らない。

理由は、**差分を小さく保ち、全量を確認できる状態を維持する**ため。20ページを一度に作れば、レビューは要点の抜き取りにならざるを得ない。1ページなら、マッピングの該当行とページの内容を1対1で突き合わせられる。

### 11.5 最初の1ページで基準を作る

第1部（概念、1ページ）を作った時点で、以下を確認する。

- 書き直しの度合いは適切か（変えすぎていないか、変えなさすぎないか）
- 内容が失われていないか
- トンマナが揃っているか

ここで基準が固まれば、残りのページは同じ基準で進められる。**方針が誤っていた場合の手戻りを1ページ分に抑える。**

### 11.6 ページごとの4観点レビュー

各ページについて、以下4つを**それぞれ別のサブエージェント**で実施する。1つのサブエージェントに複数観点を持たせない。観点を混ぜると、どれかが手薄になる。

| 観点 | 見るもの | 入力 |
|---|---|---|
| **A 網羅性** | `mapping.csv` の当該 `dest_page` の行がすべて反映されているか。`disposition` ごとの扱いが正しいか（`REFERENCE` が本文を持っていないか、`DROP` が混入していないか）。出典と照合して記載が欠落していないか | `mapping.csv` の該当行、作成したページ、出典ファイル |
| **B トンマナ** | `style.md` の全規約に適合しているか。セクション構成が本書のページアウトラインと一致しているか。セクションタイトルが「〜する」形式か。**ページタイトル＋セクションタイトルの組で中身が分かるか**（`style.md` セクションタイトル規約）。**出典の逐語的流用がないか**（判定基準は本節末尾「観点Bの判定基準」参照） | 作成したページ、`style.md`、本書、FW解説書ライブラリ |
| **C 用語** | `glossary.md` の正表記が使われているか。揺れ表記が混入していないか。処理方式の名称が正式名称と一致しているか | 作成したページ、`glossary.md` |
| **D 整合性** | 他ページと内容が重複していないか。`:ref:` の参照先が実在するか。参照が一方向で切れていないか。前提の矛盾がないか。第2部に使い方が、第3部に設定が混入していないか。**見出し・導入文と実際の中身が一致しているか**（チェック項目は本節末尾「観点Dのチェック項目」参照） | 作成したページ、作成済みの全ページ、本書 |

観点AとDが「11.1 担保すべき4点」の1と2に、CとBが3と4に対応する。

**観点Bの判定基準（出典の逐語的流用）**

「出典の骨格を踏襲している」のような主観的な基準では判定がぶれる。指摘してよいのは、次のいずれかに当てはまる場合に限る。

- 出典の一文がほぼそのまま（語順・接続・修飾関係が一致した状態で）残っている
- 出典の見出し・箇条書きの構造がそのまま持ち込まれている
- 出典固有の言い回し（現行解説書の「〜すること。」調の指示文など）がそのまま残っている

次は指摘しない。

- 用語・クラス名・データタイプ名・短い技術的言明（20字程度まで）の一致。言い換えると意味が変わるため
- 列挙の順序が出典と同じであること。順序自体が出典の示すモデルである場合がある
- 出典と同じ事実を述べていること。事実は変えられない

**字数は目安であり、厳密な閾値ではない。** 一文で完結する技術的な結論（「テストソースコードの重複を大幅に削減できる」等）は、
20字をやや超えていても、言い換えると結論の強さ・対象・因果関係が変わってしまう場合は指摘しない。逆に、20字以内でも
文全体の構造（主語・述語・接続）が出典の一文と一致していれば指摘してよい。**すでにユーザーが実物比較のうえ「対応不要」
と判定した箇所は、本基準を機械的に再適用して蒸し返さない。** ユーザーの個別判断は本基準より優先する。

指摘する場合は、**出典の該当文と成果物の該当文を並べて引用する**こと。並べられない指摘は出さない。

**観点Dのチェック項目（見出し・導入文と中身の一致）**

- [ ] 各セクション見出しが、そのセクションの実際の中身を表しているか
- [ ] 表・箇条書き・コード例の導入文が、直後の実物の中身と一致しているか（導入文が対象を限定しているのに、実物にはその範囲外の項目が含まれていないか）
- [ ] ページタイトル＋セクションタイトルの組だけで中身が分かるか（`style.md` の規約）

### 11.7 レビューの運用

- 指摘には重大度区分を付ける。区分は次の3つに限る

| 区分 | 内容 | 扱い |
|---|---|---|
| `must` | 事実誤り、`glossary.md` の正表記違反、`style.md` の規約違反、見出し・導入文と中身の不一致、`design.md` の構成違反、`vocabulary.md` のページ名・`design.md` の確定内容との不一致 | レビューラウンド内で必ず修正する。ユーザー判断に回さない |
| `decide` | 出典にない内容の追加可否、ページ構成の選択など、規約で決まらない判断 | ユーザーに上げる |
| `note` | 規約に反しないが改善余地がある表現 | 記録するのみ。修正ラウンドを費やさない |

- レビューは**最大3ラウンド**。**3ラウンド上限に達してユーザーレビューに上げてよいのは `decide` のみ。** `must` が残った状態でユーザーレビューに上げない。`must` が3ラウンドで解消しない場合は、自己判断で4ラウンド目を実施するのではなく、原因（指摘が不明確／修正が反映されない等）を記録して報告する
- 指摘は**対応の有無にかかわらず全件記録する**。対応しないと判断したものも、理由とともに残す
- 指摘が0件だったラウンドも、その旨を記録する
- レビュー記録は `reviews/page-<ページID>.md` に、以下の形式で残す

| 列 | 内容 |
|---|---|
| 指摘ID | 一意 |
| ラウンド | 1〜3 |
| 観点 | A / B / C / D |
| 区分 | `must` / `decide` / `note` |
| 指摘内容 | |
| 対応要否 | 要 / 不要 |
| 不要の理由 | 「不要」の場合は必ず記入 |
| 対応内容 | |

対応しなかった指摘を消さないのは、**後から「なぜそう判断したか」を検証できるようにする**ため。記録がなければ、見落としと意図的な判断を区別できない。

### 11.8 機械検証できないもの

次の3点は機械検証の対象外であり、人またはサブエージェントの判断に委ねる。曖昧にせず、担保方法を定めておく。

**割当先が適切かどうか**

`dest_page` が `vocabulary.md` に存在することは検証できるが、その割当先が内容に照らして適切かは検証できない。マッピング作成時の3観点レビュー（割当先の妥当性 / `disposition` の妥当性 / `audience` の妥当性）で担保する。

**`DROP` が妥当かどうか**

`note` に理由が書かれているかは検証できるが、その理由が妥当かは検証できない。マッピング統合後に `DROP` の全件をレビューする。内容が失われるかどうかを決める最後の砦であるため、件数の多寡にかかわらず全件を対象とする。

**書き直しによる内容の変質**

本刷新では出典の文面をそのまま流用せず、トンマナに合わせて書き直す（「8. トンマナ」）。書き直しの過程で内容が変質する危険があり、これは機械検証できない。観点Aのレビューで出典と照合して検出するが、完全ではない。**1ページずつ作り、1ページずつレビューする理由がここにある。**

### 11.9 段階ごとのゲート

各段階で担保することと、次に進む条件を定める。前段階の承認を得るまで次に進まない。

| 段階 | 担保すること | 次に進む条件 |
|---|---|---|
| セクション抽出 | 現行解説書とinput資料の全行が台帳に載る | 未カバーの非空行0件、冪等性（md5一致） |
| 用語集 | 表記揺れの正表記が確定する | 表記揺れが実在する用語と、本書が章・セクション名に使う用語を網羅 |
| トンマナ規約 | 記述の基準が明文化される | 8観点すべてにFW解説書からの根拠2件以上 |
| 分割判断 | 大きいセクションの分割位置が確定する | 分割後の行範囲が元セクションを過不足なく覆う |
| マッピング | 全セクションの行先が決まる | `verify_mapping.py` の全検査を通過、`DROP` 全件のレビュー完了 |
| 現行解説書の削除 | 白紙の状態を作る | 削除前のファイル一覧が記録済み、画像・素材が保持されている |
| ページ作成 | マッピングどおりのページができる | ページごとに4観点レビュー完了、`make html` エラー0 |

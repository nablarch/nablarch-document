テスティングフレームワークとは
==================================================

全体像
--------------------------------------------------
テスティングフレームワークは、JUnitをベースに、Nablarchアプリケーションのテストを補助する機能を提供するフレームワークである。トランザクション制御やシステム日時の設定など、Nablarchアプリケーションに特化したAPIを提供する。

アノテーション、assertメソッド、Matcherクラスなど、JUnit 4が備える機能は、テスティングフレームワーク上でもそのまま利用できる。これは、テスティングフレームワークがJUnit 4を基盤としているためである。JUnit 5上で動かす方法は、 :ref:`稼動環境 <testing_framework_about-operating_environment>` を参照。

テストメソッドは、JUnit 4のアノテーションを使って作成する。テスト対象の処理を記述したメソッドに、``@Test`` アノテーションを付与する。

.. code-block:: java

  public class SampleTest {

      @Test
      public void testSomething() {
          // テスト処理
      }
  }

.. tip::

  ``@Before`` や ``@After`` などのアノテーションも使用できる。これらを使うと、テストメソッドの前後で、リソースの取得・解放などの共通処理を行える。

特徴
--------------------------------------------------
テスティングフレームワークには、次の特徴がある。

本番同等の経路でテストできる
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
リクエスト単体テストは、Nablarch Application Frameworkのハンドラキューを通して実行される。環境差分を除き、本番と同じ経路でテストできる。詳細は :ref:`アーキテクチャ <testing_framework_about-architecture>` を参照。

テストコードは定型かつ少量で済む
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストロジックはテスティングフレームワークが提供する。利用者はテストデータを宣言的に記述するだけでよく、テストコードはテスト対象を呼び出す定型的な記述にとどまる。詳細は :ref:`テストデータ <testing_framework_about-test_data>` を参照。

利用目的に応じたテストデータ形式を選べる
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータは、人が編集しやすいExcel形式と、AIエージェントが扱いやすいテキストのYAML形式のいずれかで記述できる。両形式は相互に変換できる。詳細は :ref:`テストデータ変換ツール <testdata_converter>` を参照。

テストの種類
--------------------------------------------------
テスティングフレームワークが提供するテストは、クラス単体テスト・リクエスト単体テスト・取引単体テストの3種類である。それぞれの実行方法とテスト範囲の違いは、以下のとおり。

.. list-table::
  :header-rows: 1
  :widths: 20,20,30,30

  * - テストの種類
    - 実行方法
    - テスト範囲
    - 備考
  * - クラス単体テスト
    - JUnitで自動実行
    - クラス単体
    - エンティティ、コンポーネント
  * - リクエスト単体テスト
    - JUnitで自動実行
    - 1リクエスト（ハンドラキューを通す）
    - 本番に近い構成でテストできる
  * - 取引単体テスト
    - 手動操作
    - 複数リクエストにまたがる業務の流れ
    - APサーバへのデプロイが必要。エビデンスは画面ハードコピー・DBダンプ

.. important::

  取引単体テストは、自動実行ではなく手動操作によって行う。自動実行の対象となるのは、クラス単体テストとリクエスト単体テストである。

.. _testing_framework_about-test_type_names:

このうちリクエスト単体テストは、対象とする処理方式によって、次の6つに分かれる。

==================================================================  ========================================================================================
テスト種別                                                          内容
==================================================================  ========================================================================================
クラス単体テスト                                                    Action・Componentクラスなどの単体テスト
リクエスト単体テスト（ウェブアプリケーション）                      HTTPリクエスト1件単位のテスト（シンクライアント型）。Ajax等のリッチクライアントは未対応
リクエスト単体テスト（RESTfulウェブサービス）                       REST APIの1リクエスト単位のテスト
リクエスト単体テスト（HTTPメッセージング）                          HTTPによる電文の送信から応答受信までを1リクエスト単位で行うテスト
リクエスト単体テスト（Nablarchバッチアプリケーション）              バッチの1起動単位のテスト
リクエスト単体テスト（MOMによるメッセージング）                     MOMによる要求電文の受信、または同期応答メッセージ送信を1リクエスト単位で行うテスト
リクエスト単体テスト（テーブルをキューとして使ったメッセージング）  テーブル上の未処理レコードを対象に、Nablarchバッチアプリケーションと同じ方法で行うテスト
取引単体テスト                                                      複数リクエストをまたぐ業務取引単位のテスト
==================================================================  ========================================================================================

テストデータ
--------------------------------------------------
テストデータの外部化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータは、テストコードとは別のファイルに記載できる。テスティングフレームワークは、データベースへの準備データや期待するテスト結果を、このファイルからAPIを通じて読み込んで使用する。

テストデータをテストコード中に書くと、どこに何があるか把握しにくくなり、保守の手間も増える。テストデータはテストコードに書かず、1か所にまとめておく。

* テストケースにどのようなバリエーションがあるかは、テストデータを見るだけで把握できる。
* テストコードにはロジックだけを残し、データにまつわる関心事はテストデータ側に切り出せる。
* テストケースを追加する際も、実行の仕組み自体には手を加えず、テストデータへの追記だけで済む。
* テストコード中にリテラル値でデータを記載する方式では、データのバリエーションが増えるほど重複したコードが増えてしまうが、テストデータとして外部化しておけばテストコードの重複を大幅に削減できる。

テストの独立性
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストの実行順序に結果が左右されないよう、テストコード・テストデータを作成する。1クラスだけを実行した場合と、複数クラスをまとめて実行した場合とで、結果が変わってはならない。

この配慮が必要なのは、テスティングフレームワークがテスト中にコミットを行う仕組みだからである。前のテストが更新したデータベースの内容が、後続のテストに影響することがある。そのため各テストクラスは、自らが必要とする事前条件を、他のテストクラスに頼らず自分自身で準備しておく。こうしておけば、実行順序が変わっても偶然の成否に左右されず、事前条件もそのテストクラスのデータまたはソースコードだけを見れば把握できるようになる。

読み取り専用のマスタデータを共通のテストデータとしてまとめて外部化しておくと、プロジェクト全体でデータを再利用でき、テストデータのメンテナンスも容易になり、テスト実行速度の向上にもつながる。投入のタイミングは、全テスト実行前に1回で済ませるか、あらかじめ準備済みであることを前提としてテストを実行すればよい。

.. tip::

  マスタデータ投入ツールを使うと、マスタデータの投入を行える。またマスタデータ復旧機能を使えば、テスト終了時にマスタデータへの変更を自動的に元へ戻せるため、マスタデータを変更するテストケースであっても、他のテストケースから独立させたまま実行できる。

データブロックの考え方
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータには、テストケース・セットアップ・検証の3つの用途がある。いずれも、データブロック単位で管理する。

============  ======================================================================  ======================================================
用途          内容                                                                    主なデータタイプ
============  ======================================================================  ======================================================
テストケース  1件が1ケースの実行条件を表す。                                          ``LIST_MAP=testShots``
セットアップ  テスト前に投入する準備データ（データベースへの投入、ファイルの配置）。  ``SETUP_TABLE`` / ``SETUP_FIXED`` / ``SETUP_VARIABLE``
検証          テスト後の期待値（データベース・出力ファイル・電文・ログなど）。        ``EXPECTED_*`` / ``RESPONSE_*``
============  ======================================================================  ======================================================

個々のデータブロックは、読み込み単位というまとまりの内側に複数個が共存する形で格納され、その読み込み単位はテストクラス1つ分のデータごとに分かれる。データタイプは、テストデータを解析する際の起点となる識別子であり、グループID・テストケース一覧（``testShots``/``requestParams``）・ファイルデータ・メッセージングは、いずれもこのデータタイプに紐づいて意味が定まる。

一方、データブロック単体を特定するには、データタイプ（``SETUP_TABLE`` など14種を数える）だけでは足りず、識別子の値（テーブル名・ファイルパス・IDなど、データタイプに応じて意味が変わる値）を組み合わせる必要がある。この組み合わせにより、読み込み単位内に同じデータタイプのデータブロックが複数並んでいても一意に区別できる。

また、特殊記法（値を実値に変換する記法）・マーカーカラム（読み込み対象外のカラムを示す標識）・コメント（``//`` 以降を読み込み対象外とする注釈記法）など、値の解釈に関する規則は、テストケース・セットアップ・検証のいずれのデータタイプにも共通して適用される。

対象範囲
--------------------------------------------------
対応する処理方式は、 :ref:`テストの種類 <testing_framework_about-test_type_names>` を参照。

.. important::

  テスティングフレームワークは、 :ref:`Jakarta Batchに準拠したバッチアプリケーション <jsr352_batch>` を対象としていない。これらの基盤・ライブラリを使うアプリケーションでは、`JUnit(外部サイト、英語) <https://junit.org/junit5/>`_ を直接使うなど、テスティングフレームワーク以外の方法でテストする。

.. important::

  マルチスレッド機能を使うアプリケーションも、テスティングフレームワークの対象外である。結合テストなど、テスティングフレームワークとは別の方法でこれらのテストを行う。

稼動環境
--------------------------------------------------
テスティングフレームワークは、JUnit 4をベースに動作する。JUnit 5用拡張機能（``nablarch-testing-junit5``）を使用することで、JUnit 5上でも使用できる。

モジュール一覧
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
JUnit 5用拡張機能を使用する場合は、以下のモジュールを依存関係に追加する。

.. code-block:: xml

  <dependency>
    <groupId>com.nablarch.framework</groupId>
    <artifactId>nablarch-testing-junit5</artifactId>
    <scope>test</scope>
  </dependency>

JUnit 5用拡張機能を使わずに、JUnit Vintageを使ってテスティングフレームワークをJUnit 5上で動かす場合は、以下の2つのアーティファクトを依存関係に追加する。

* ``org.junit.jupiter:junit-jupiter``
* ``org.junit.vintage:junit-vintage-engine``

.. code-block:: xml

  <dependencyManagement>
    <dependencies>

      <!-- バージョンを揃えるため、JUnitが提供しているbomを読み込む -->
      <dependency>
        <groupId>org.junit</groupId>
        <artifactId>junit-bom</artifactId>
        <version>5.8.2</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <dependencies>

    <!-- 以下の依存関係を追加する -->
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <scope>test</scope>
    </dependency>
    <dependency>
      <groupId>org.junit.vintage</groupId>
      <artifactId>junit-vintage-engine</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

テスティングフレームワークとは
==================================================

全体像
--------------------------------------------------
テスティングフレームワークは、JUnitをベースに、Nablarchアプリケーションのテストを補助する機能を提供するフレームワークである。
トランザクション制御やシステム日時の設定など、Nablarchアプリケーションに特化したAPIを提供する。

テスティングフレームワークはJUnit 4をベースとしており、アノテーション、assertメソッド、Matcherクラスなど、
JUnit 4が提供する機能をそのまま利用できる。JUnit 5上で動かす方法は、 :ref:`稼動環境 <testing_framework_about-operating_environment>` を参照。

テストメソッドは、JUnit 4のアノテーションを使って作成する。テスト対象の処理を記述したメソッドに、``@Test`` アノテーションを付与する。

.. code-block:: java

  public class SampleTest {

      @Test
      public void testSomething() {
          // テスト処理
      }
  }

.. tip::

  ``@Before`` や ``@After`` などのアノテーションも使用できる。これらを使うと、テストメソッドの前後で、
  リソースの取得・解放などの共通処理を行える。

--------------------------------------------------
テスティングフレームワークを使用したテストは、以下の構成物から成る。構成物どうしの関係は、次の図のとおり。

  :scale: 80

コンポーネント設定ファイル・環境設定ファイル  テスト実行時の各種設定を記載する。                                                                              アプリケーションプログラマ（個別のテストに固有の設定が必要な場合）

テストの種類
--------------------------------------------------
テスティングフレームワークが提供するテストは、クラス単体テスト・リクエスト単体テスト・取引単体テストの3種類である。
それぞれの実行方法とテスト範囲の違いは、以下のとおり。

.. list-table::
  :header-rows: 1
  :widths: 20,20,30,30

  * - テストの種類
    - 実行方法
    - テスト範囲
    - 備考
  * - クラス単体テスト
    - JUnitで自動実行
    - クラス単体
    - エンティティ、コンポーネント
  * - リクエスト単体テスト
    - JUnitで自動実行
    - 1リクエスト（ハンドラキューを通す）
    - 本番に近い構成でテストできる
  * - 取引単体テスト
    - 手動操作
    - 複数リクエストにまたがる業務の流れ
    - APサーバへのデプロイが必要。エビデンスは画面ハードコピー・DBダンプ

.. important::

  取引単体テストは、自動実行ではなく手動操作によって行う。自動実行の対象となるのは、クラス単体テストとリクエスト単体テストである。

処理方式ごとの正式名称
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
リクエスト単体テストは、対象とする処理方式によって、以下のとおり呼び分ける。

.. list-table::
  :header-rows: 1
  :widths: 40,60

  * - 正式名称
    - 内容
  * - クラス単体テスト
    - Action・Componentクラスなどの単体テスト
  * - リクエスト単体テスト（ウェブアプリケーション）
    - HTTPリクエスト1件単位のテスト（シンクライアント型）。Ajax等のリッチクライアントは未対応
  * - リクエスト単体テスト（RESTfulウェブサービス）
    - REST APIの1リクエスト単位のテスト
  * - リクエスト単体テスト（HTTPメッセージング）
    - HTTPによる要求電文1件単位のテスト
  * - リクエスト単体テスト（Nablarchバッチアプリケーション）
    - バッチの1起動単位のテスト
  * - リクエスト単体テスト（MOMによるメッセージング）
    - MQで受信する要求電文1件単位のテスト
  * - リクエスト単体テスト（テーブルをキューとして使ったメッセージング）
    - テーブル上の未処理レコードを対象とした、バッチと同じ起動単位のテスト
  * - 取引単体テスト
    - 複数リクエストをまたぐ業務取引単位のテスト

テストデータ
--------------------------------------------------
テストデータファイルへの外部化
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータは、テストソースコードとは別のテストデータファイルに記載できる。データベースへの準備データや、
期待するテスト結果を記載したテストデータファイルを、テスティングフレームワークのAPIを通じて使用できる。

テストソースコードとテストデータファイルとでテストデータが混在すると、可読性・保守性が低下する。
テストソースコード中にはテストデータを記載せず、テストデータはすべてテストデータファイルに記載すること。

* テストケースにどのようなバリエーションがあるかは、テストデータファイルを見るだけで把握できる。
* テストロジックはテストソースコードに、テストデータはテストデータファイルにと、役割が明確に分かれる。
* テストデータファイルを読み込んで実行する構造にしておけば、テストケースの追加が容易になる。
* テストソースコード中にリテラル値でデータを記載する方式では、データのバリエーションが増えるほど重複したコードが
  増えてしまうが、テストデータファイルに外部化しておけばテストソースコードの重複を大幅に削減できる。

テストの独立性
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストの実行順序に結果が左右されないよう、テストソースコード・テストデータを作成する。1クラスだけを実行した場合と、
複数クラスをまとめて実行した場合とで、結果が変わってはならない。

この配慮が必要なのは、テスティングフレームワークがテスト中にコミットを行う仕組みだからである。前のテストが更新した
データベースの内容が、後続のテストに影響することがある。そのため各テストクラスは、自らが必要とする事前条件を、
他のテストクラスに頼らず自分自身で準備しておく。こうしておけば、実行順序が変わっても偶然の成否に左右されず、
事前条件もそのテストクラスのデータまたはソースコードだけを見れば把握できるようになる。

マスタデータのような読み取り専用のテーブルの準備については、共通のテストデータファイルを用意してそこに記載する。

.. tip::

  マスタデータ投入ツールを使うと、マスタデータの投入を行える。またマスタデータ復旧機能を使うと、テスト内でマスタ
  データに加えた変更を、テスト終了時に元の状態へ自動的に戻せる。この機能があるため、マスタデータの変更を伴う
  テストケースであっても、他のテストケースへ影響を与えずに実行できる。

データブロックの考え方
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータには、テストケース・セットアップ・検証の3つの用途がある。いずれも、データブロック単位で管理する。

.. list-table::
  :header-rows: 1
  :widths: 20,50,30

  * - 用途
    - 内容
    - 主なデータタイプ
  * - テストケース
    - 1件が1ケースの実行条件を表す。
    - ``LIST_MAP=testShots``
  * - セットアップ
    - テスト前に投入する準備データ（データベースへの投入、ファイルの配置）。
    - ``SETUP_TABLE`` / ``SETUP_FIXED`` / ``SETUP_VARIABLE``
  * - 検証
    - テスト後の期待値（データベース・出力ファイル・電文・ログなど）。
    - ``EXPECTED_*`` / ``RESPONSE_*``

データの格納階層は、テストクラス1つ分のデータが読み込み単位に分かれ、その中に複数のデータブロックが
共存する構造になっている。データタイプは、テストデータを解析する際の起点となる識別子であり、
グループID・テストケース一覧（``testShots``/``requestParams``）・ファイルデータ・メッセージングは、
いずれもこのデータタイプに紐づいて意味が定まる。

一方、個々のデータブロックを区別する単位は、データタイプ（``SETUP_TABLE`` など14種を数える）と、
識別子の値（テーブル名・ファイルパス・IDなど、データタイプに応じて意味が変わる値）との組み合わせである。
読み込み単位内に同じデータタイプのデータブロックが複数並ぶ場合も、この組み合わせによって一意に区別できる。

また、特殊記法（値を実値に変換する記法）やマーカーカラム（読み込み対象外のカラムを示す標識）など、
値の解釈に関する規則は、テストケース・セットアップ・検証のいずれのデータタイプにも共通して適用される。

対象範囲
--------------------------------------------------
.. important::

  テスティングフレームワークは、 :ref:`Jakarta Batchに準拠したバッチアプリケーション <jsr352_batch>` に対応していない。
  このため、これらの基盤・ライブラリを使用するアプリケーションのテストは、`JUnit(外部サイト、英語) <https://junit.org/junit5/>`_
  など、テスティングフレームワーク以外の手段で行うこと。

.. important::

  マルチスレッド機能を使用するアプリケーションは、テスティングフレームワークの対応対象外である。
  このようなアプリケーションのテストは、結合テストなど、テスティングフレームワーク以外の手段で行うこと。

.. _testing_framework_about-operating_environment:

稼動環境
--------------------------------------------------
テスティングフレームワークは、JUnit 4をベースに動作する。JUnit 5用拡張機能（``nablarch-testing-junit5``）を
使用することで、JUnit 5上でも使用できる。

モジュール一覧
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
JUnit 5用拡張機能を使用する場合は、以下のモジュールを依存関係に追加する。

.. code-block:: xml

  <dependency>
    <groupId>com.nablarch.framework</groupId>
    <artifactId>nablarch-testing-junit5</artifactId>
    <scope>test</scope>
  </dependency>

JUnit 5用拡張機能を使わずに、JUnit Vintageを使ってテスティングフレームワークをJUnit 5上で動かす場合は、
以下の2つのアーティファクトを依存関係に追加する。

* ``org.junit.jupiter:junit-jupiter``
* ``org.junit.vintage:junit-vintage-engine``

.. code-block:: xml

  <dependencyManagement>
    <dependencies>

      <!-- バージョンを揃えるため、JUnitが提供しているbomを読み込む -->
      <dependency>
        <groupId>org.junit</groupId>
        <artifactId>junit-bom</artifactId>
        <version>5.8.2</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <dependencies>

    <!-- 以下の依存関係を追加する -->
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <scope>test</scope>
    </dependency>
    <dependency>
      <groupId>org.junit.vintage</groupId>
      <artifactId>junit-vintage-engine</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

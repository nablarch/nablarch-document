テストデータの書き方
==================================================

.. contents:: 目次
  :depth: 3
  :local:

.. _testdata_notation-overview:

機能概要
--------------------------------------------------
このページでは、テスティングフレームワークが読み込むテストデータの記述仕様を、Excel形式とYAML形式を対比しながら説明する。両形式のいずれで記述する場合にも、ここで説明する記法が共通して適用される。実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。

.. _testdata_notation-usage:

使用方法
--------------------------------------------------

.. _testdata_notation-file_structure:

ファイル構成と記述時の注意点を確認する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
データベースへの準備データやデータベース検索結果の比較などをJavaのソースコードで表現するよりも、表形式で記述したほうが可読性・編集のしやすさの点で有利であるため、テスティングフレームワークはこれらのデータをテストソースコードとは別のファイル（Excelファイルまたは\ YAML\ ファイル）に記述する方式を採用している。

テストデータは、テストクラスと1対1で対応する。

.. list-table::
  :header-rows: 1
  :widths: 15,40,45

  * - 形式
    - テストクラスに対応するもの
    - 読み込み単位
  * - Excel
    - 同名の1つの\ Excelファイル\ （\ ``.xls``\ または\ ``.xlsx``\ ）
    - 1シート
  * - YAML
    - 同名の1つのディレクトリ
    - 1つの\ YAMLファイル

ディレクトリ構成の対応は、以下のとおりである。

.. code-block:: text

  【Excel】                              【YAML】
  src/test/java/com/example/            src/test/java/com/example/
    FooTest.xls                           FooTest/
      ├── case01  ← シート                  ├── case01.yaml  ← ファイル
      └── case02  ← シート                  └── case02.yaml  ← ファイル

Excelファイルの配置・命名にも規約がある。テストソースコードと同じディレクトリに、テストソースコードと同じ名前（拡張子のみ異なる）で配置することが推奨されており、この規約に従うと、テストクラス側でディレクトリ名やファイル名を明示的に指定しなくてもテストデータを読み込める。

.. list-table::
  :header-rows: 1
  :widths: 30,35,35

  * - ファイルの種類
    - 配置ディレクトリ
    - ファイル名
  * - テストソースファイル
    - ``<PROJECT_ROOT>/test/jp/co/tis/example/db/``
    - ``ExampleDbAccessTest.java``
  * - Excelファイル
    - 同上
    - ``ExampleDbAccessTest.xlsx``

Excelシートについても、1テストメソッドにつき1シートを用意し、シート名をテストメソッド名と同名にすることが推奨される。例えば、テストメソッド ``testInsert()`` に対応するシート名は ``testInsert`` である。

.. tip::

  シート名とテストメソッド名の対応は「制約」ではなく「推奨」であり、両者が異なっていても正しく動作する。ただし独自の命名規約を採用する場合は、プロジェクト内でその規約を一貫させる必要がある。

Excelのセルの書式は、必ず文字列書式に統一しておく必要がある。着手前の段階で対象範囲のセルをあらかじめ文字列書式にしておくとよい。罫線やセルの色付けは任意であり、行うとレビュー品質や保守性の向上が期待できる。

.. important::

  Excelファイルに文字列以外の書式でデータを記述した場合、正しくデータを読み取れなくなる。

YAMLファイルは\ YAML 1.2\ に準拠する。\ YAML 1.1\ との主な違いとして、``yes``\ ・\ ``no``\ ・\ ``on``\ ・\ ``off``\ は真偽値ではなく文字列として扱われる点に注意する。\ YAML\ テストデータには\ JSON Schema\ が定義されており、``nablarch-testing-yaml``\ の\ jar\ に ``nablarch/test/ntf-testdata-yaml-schema.json`` として同梱されている。パース時に\ ``YamlLoader``\ というパーサがこのスキーマでの検証を行い、型不正（文字列フィールドへの数値記述など）・必須フィールドの欠落・未定義キーの記述・\ enum\ 違反などがあると ``YamlSchemaValidationException`` をスローする。

ファイルが存在しない場合や空の場合、値の書き方については、以下のように\ Excel\ 形式と\ YAML\ 形式で扱いが異なる。

.. list-table::
  :header-rows: 1
  :widths: 20,40,40

  * - 項目
    - Excel
    - YAML
  * - ファイルなし時
    - エラー
    - ファイルが存在しない、またはパースに失敗した場合はエラー
  * - 空ファイル時
    - 空シートは存在しないシートとして扱われる
    - 空ファイル（0バイト）は空データとして扱われる（エラーにはならない）
  * - 値の書き方
    - セルは必ず文字列書式で記述する（数値・日付書式の動作は保証されない）
    - 値は必ずダブルクォートで囲んで記述する

1つの読み込み単位（\ Excel\ の1シート、\ YAML\ の1ファイル）の中には、テストケース・準備データ・期待値という3つの用途のデータが、\ :ref:`データブロック <testdata_notation-data_block_types>`\ 単位で共存する。

.. list-table::
  :header-rows: 1
  :widths: 15,45,40

  * - 用途
    - 内容
    - 主なデータブロック
  * - テストケース
    - 1エントリ1ケースの実行条件（期待するステータスコードなど）
    - テストケース一覧（\ ``LIST_MAP=testShots``\ ）
  * - 準備データ
    - テスト実行前にデータベース・ファイルへ投入するデータ
    - ``SETUP_TABLE``\ ・\ ``SETUP_FIXED``\ ・\ ``SETUP_VARIABLE``\ など
  * - 期待値
    - テスト実行後に確認する状態（データベース・出力ファイル・電文・検索結果など）
    - ``EXPECTED_*``\ ・\ ``RESPONSE_*``\ など

テストクラス1つ分のデータが読み込み単位に分かれ、その中に複数のデータブロックが共存するという格納階層は、次の図のとおりである。

.. code-block:: text

  テストクラス（Excel: 1ファイル / YAML: 1ディレクトリ）
  └── 読み込み単位（Excel: 1シート / YAML: 1ファイル）
        └── データブロック（種別 + 識別子の値）
              └── レコード定義 / フィールド / データ

ここまでのファイル構成を踏まえたうえで、テストデータを記述する際は次の点に留意する。

.. important::

  テストデータは、テストメソッドの実行順序によって結果が変わらないように記述する。クラス単体で実行しても、複数まとめて実行しても同じ結果になる必要がある。テスティングフレームワークはテスト実行中にコミットを行うため、前後のテストによってデータベースの内容が変わる可能性がある。そのため、自テストクラスで必要な事前条件は、全て自テストクラス内のテストデータで準備しておかなければならない。こうしておくことで、実行順序による偶然の成功・失敗を防げるとともに、テストデータまたはソースコードだけを見れば事前条件が分かる状態を保てる。

.. tip::

  マスタデータのように基本的に読み取り専用のテーブルは、共通のテストデータファイルを用意してそこに記述し、プロジェクト全体で再利用するとよい。テスト実行前に1回だけ投入するか、あらかじめ準備済みという前提でテストを実行する運用にすると、テストデータの保守が容易になり、テスト実行速度も上がる。

  マスタデータの投入にはマスタデータ投入ツールを使用する。またマスタデータ復旧機能を使うと、テストで発生したマスタデータの変更をテスト終了時に自動的に元の状態へ戻せるため、マスタデータへの変更を伴うテストケースであっても、他のテストケースに影響を与えずに実行できる。

.. _testdata_notation-data_block_types:

データブロックの種別を確認する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
データタイプは、データブロックの用途を示す予約語であり、解析の起点になる。データタイプを軸に、グループID・テストケース一覧・ファイルデータ・メッセージングの各記法が結び付き、特殊記法・コメント・マーカーカラムはセル値やエントリ値の解釈規則として全データタイプに横断的にかかる。

.. code-block:: text

  データタイプ（データブロックの先頭に置く予約語）
  ├── グループID          … 同種データブロックの識別
  ├── テストケース一覧    … testShots
  ├── ファイルデータ      … 固定長・可変長のフィールド定義
  └── メッセージング      … 電文・フレームワーク制御ヘッダ

  特殊記法・コメント・マーカーカラム（値の解釈規則）は、上記の全データタイプに横断的にかかる。

使用できるデータタイプは、以下の14種である。

.. list-table::
  :header-rows: 1
  :widths: 30,35,35

  * - データタイプ
    - 用途
    - 同一\ ID\ のデータブロックが複数ある場合
  * - ``SETUP_TABLE``
    - テスト実行前にデータベースへ登録するテーブルデータ
    - 同じグループのものを全て収集
  * - ``EXPECTED_TABLE``
    - テスト実行後に比較するテーブルデータ（省略カラムは比較対象外）
    - 同じグループのものを全て収集
  * - ``EXPECTED_COMPLETE_TABLE``
    - テスト実行後に比較するテーブルデータ（省略カラムにはデフォルト値が入っているものとして比較）
    - 同じグループのものを全て収集
  * - ``LIST_MAP``
    - キーバリュー形式の汎用データ（テストケース一覧・期待値など）
    - 最初の1件のみ有効（2件目以降は無視）
  * - ``SETUP_FIXED``
    - 準備用の固定長ファイル
    - 同じグループのものを全て収集
  * - ``EXPECTED_FIXED``
    - 期待値を示す固定長ファイル
    - 同じグループのものを全て収集
  * - ``SETUP_VARIABLE``
    - 準備用の可変長ファイル
    - 同じグループのものを全て収集
  * - ``EXPECTED_VARIABLE``
    - 期待値を示す可変長ファイル
    - 同じグループのものを全て収集
  * - ``MESSAGE``
    - メッセージングのテストで使用する電文データ（\ ``setUpMessages``\ または\ ``expectedMessages``\ ）
    - 最初の1件のみ有効（2件目以降は無視）
  * - ``EXPECTED_REQUEST_HEADER_MESSAGES``
    - 要求電文（ヘッダ）の期待値を示す固定長ファイル
    - グループID指定時は全件収集、ID直接指定時は最初の1件
  * - ``EXPECTED_REQUEST_BODY_MESSAGES``
    - 要求電文（本文）の期待値を示す固定長ファイル
    - グループID指定時は全件収集、ID直接指定時は最初の1件
  * - ``RESPONSE_HEADER_MESSAGES``
    - 応答電文（ヘッダ）を示す固定長ファイル
    - グループID指定時は全件収集、ID直接指定時は最初の1件
  * - ``RESPONSE_BODY_MESSAGES``
    - 応答電文（本文）を示す固定長ファイル
    - グループID指定時は全件収集、ID直接指定時は最初の1件
  * - ``DEFAULT``
    - フレームワーク内部用（通常は使用しない）
    - ―

データブロックは、データタイプと識別子の値（テーブル名・ファイルパス・IDなど）の組み合わせで識別する。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - データブロック先頭セルに ``データタイプ=識別子の値`` の形式で記載する。データタイプ名で始まっていれば合致する（前方一致）。例: ``SETUP_TABLE=USER_MASTER``
  * - YAML
    - データタイプごとに専用のトップレベルキーを使う（完全一致のため前方一致は発生しない）

YAML\ のトップレベルキーの対応は、以下のとおりである。

.. list-table::
  :header-rows: 1
  :widths: 50,50

  * - データタイプ
    - YAML\ のトップレベルキー
  * - ``SETUP_TABLE``
    - ``setup_tables``
  * - ``EXPECTED_TABLE``
    - ``expected_tables``
  * - ``EXPECTED_COMPLETE_TABLE``
    - ``expected_complete_tables``
  * - ``LIST_MAP``
    - ``list_maps``
  * - ``SETUP_FIXED``\ ・\ ``SETUP_VARIABLE``
    - ``setup_files``
  * - ``EXPECTED_FIXED``\ ・\ ``EXPECTED_VARIABLE``
    - ``expected_files``
  * - ``MESSAGE``
    - ``messages``
  * - ``EXPECTED_REQUEST_HEADER_MESSAGES``
    - ``expected_request_header_messages``
  * - ``EXPECTED_REQUEST_BODY_MESSAGES``
    - ``expected_request_body_messages``
  * - ``RESPONSE_HEADER_MESSAGES``
    - ``response_header_messages``
  * - ``RESPONSE_BODY_MESSAGES``
    - ``response_body_messages``

.. code-block:: yaml

  setup_tables:
    - table: USER_MASTER
      rows:
        # ...

YAML\ 形式では、同一ファイル内でトップレベルキーを重複させることはできない。同種のデータは、同じキーの下にリストとして並べる（重複するとエラーになる）。Excel\ 形式では、同一シート内に同じデータタイプのデータブロックを複数記述できる。データタイプによって、全件収集または先着一致で収集される（詳細は :ref:`グループIDでデータブロックを分ける <testdata_notation-group_id>` を参照）。

.. _testdata_notation-group_id:

グループIDでデータブロックを分ける
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
同じ読み込み単位の中に、同じデータタイプのデータブロックを複数記述したい場合は、グループIDでそれらを区別する。テストケース一覧の各カラムでグループIDを参照することで、テストケースごとに異なる準備データ・期待値を使い分けられる。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - データタイプ名の直後に ``[グループID]`` を付ける。例: ``SETUP_TABLE[case_001]=EMPLOYEE_TABLE``
  * - YAML
    - エントリに ``group_id:`` フィールドを設ける

.. code-block:: yaml

  setup_tables:
    - group_id: case01
      table: USER_MASTER
      rows:
        # ...

例えば、従業員の所属を変更するケースと氏名を変更するケースの2種類を1つのシートに混在させる場合、以下のように記述する。

.. list-table::
  :header-rows: 1
  :widths: 50,50

  * - 準備データ
    - 期待値
  * - | ``SETUP_TABLE[case_001]=EMPLOYEE``
      | ID・氏名・所属コードの初期値を記載
    - | ``EXPECTED_TABLE[case_001]=EMPLOYEE``
      | 所属コードの変更後の値を記載
  * - | ``SETUP_TABLE[case_002]=EMPLOYEE``
      | ID・氏名・所属コードの初期値を記載
    - | ``EXPECTED_TABLE[case_002]=EMPLOYEE``
      | 氏名の変更後の値を記載

グループIDを省略した場合は、グループIDを持たないデータブロック（デフォルトグループ）が対象になる。テストケース一覧のカラムで、デフォルトグループを明示的に使いたい場合は ``default`` と記載する。デフォルトグループと個別グループのデータは併用でき、両方が混在した場合は両方のデータが有効になる。Nablarchバッチアプリケーションでは、グループIDに文字列として ``"default"`` を指定した場合も、グループIDなしと同等に扱われる（ウェブアプリケーション・メッセージングのテストには、この挙動は適用されない）。

.. important::

  複数のデータタイプ、または複数のグループIDのデータを記述する際は、それぞれをまとめて記述すること。Excel\ 形式はシート内のデータを上から順に読み込む方式であるため、異なるデータタイプ・異なるグループIDのデータを交互に記述すると、途中で読み込みが終了し、以降のデータの誤りが検出されないままテストが成功してしまうことがある。

データブロックの収集方法は、データタイプによってあらかじめ決まっている。

.. list-table::
  :header-rows: 1
  :widths: 15,45,40

  * - 方式
    - 選び方
    - 該当データタイプ
  * - 単一
    - データタイプとIDが完全一致する最初の1ブロックを取得
    - ``LIST_MAP``\ ・\ ``MESSAGE``\ など
  * - グループ
    - ``データタイプ + グループID + '='`` で前方一致する複数ブロックを収集
    - テーブル・ファイルなど

Excel\ 形式のこの制約は、シートを上から順に読む実装に由来する。YAML\ 形式はトップレベルのキーごとに独立して読み込むため、この制約はなく、記述順序や異なるデータブロックの交互記述を気にする必要がない。

.. _testdata_notation-table_data:

テーブルのデータを記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
データベースのテーブルに対応するテストデータ（テーブルデータ）は、``SETUP_TABLE``\ ・\ ``EXPECTED_TABLE``\ ・\ ``EXPECTED_COMPLETE_TABLE``\ ・\ ``LIST_MAP``\ のいずれかのデータタイプで記述する。いずれも、1行目に ``データタイプ=値``\ 、2行目にカラム名（\ ``LIST_MAP``\ の場合は\ Map\ のキー）、3行目以降にデータ行を置く共通の書式を持つ。

.. list-table::
  :header-rows: 1
  :widths: 25,75

  * - Excel
    - 1行目にカラム名、2行目以降にデータを記載する
  * - YAML
    - ``rows:``\ 配列に、各行をオブジェクトとして記述する

.. list-table::
  :header-rows: 0
  :widths: 34,33,33

  * - ``SETUP_TABLE=テーブル名``
    -
    -
  * - カラム1
    - カラム2
    - カラム3
  * - 値1
    - 値2
    - 値3

.. code-block:: yaml

  setup_tables:
    - table: テーブル名
      rows:
        - カラム1: "値1"
          カラム2: "値2"
          カラム3: "値3"

YAML\ 形式では、``setup_tables``\ ・\ ``expected_tables``\ ・\ ``expected_complete_tables``\ の各エントリに ``table`` キーが必須であり、省略するとエラーになる。カラム名を列挙するヘッダ行の末尾に空カラムがあった場合は自動的に除去されるため、末尾のカラムは省略できる。データ側のエントリがヘッダより少ない場合は、不足分が空文字で補完される。

例えば、``SETUP_TABLE=EMPLOYEE``\ と ``SETUP_TABLE=DEPT``\ で従業員・所属の初期データを登録し、テスト実行後の検索結果を ``LIST_MAP=expected``\ として期待値にする場合、``LIST_MAP``\ の2行目には\ SELECT\ 文で指定したカラム名または別名を記載する。更新系のテストケースでは、``SETUP_TABLE``\ に更新前の値（例えば真偽値カラム\ ``EXPIRED``\ に\ ``FALSE``\ ）を記載し、``EXPECTED_TABLE``\ に更新後の値（``TRUE``\ など）を記載することで、更新結果を検証できる。

テストクラス全体で共通する準備データは、``setUpDb``\ という名前の読み込み単位（\ Excel\ 形式では ``setUpDb`` という名前のシート）にまとめて記載する。ここに記載した ``SETUP_TABLE`` は、テストメソッドの実行前に投入される。1つの読み込み単位に複数の ``SETUP_TABLE`` を記述することもでき、実行時にはその読み込み単位内の全ての ``SETUP_TABLE`` が登録対象になる。

準備データ（\ ``SETUP_TABLE``\ ）を記述する際は、以下の点に注意する。

- 主キーカラムは記述を省略できない。省略すると型に応じたデフォルト値（数値型は\ ``0``\ 、文字型は半角スペースなど）がそのまま\ INSERT\ されてしまう
- \ FK\ が設定された数値カラムも同様に省略できない。省略すると値\ ``0``\ が\ INSERT\ され、参照先テーブルに\ ID=0\ の行がない場合は\ FK\ 違反でエラーになる。\ NULL\ にしたいカラムは、省略ではなく\ ``null``\ を明示的に指定する（カラムの省略は\ NULL\ の指定と等価ではない）
- \ ``SETUP_TABLE``\ による登録は、対象テーブルを一旦全件\ DELETE\ したうえで\ INSERT\ し直すという動きになる。テスト終了後の後片付けはテスティングフレームワーク側で行われないため、別のテストが残した子テーブルの行が原因で、親テーブルの\ DELETE\ が\ FK\ 違反により失敗するケースがある。\ FK\ 関係を持つ親テーブルを準備する際は、子テーブル側も\ ``SETUP_TABLE``\ の対象に含めておく（削除順序は子から親になる）

null\ 値・空文字の記述は、以下のように\ Excel\ 形式と\ YAML\ 形式で対比できる。

.. list-table::
  :header-rows: 1
  :widths: 25,40,35

  * - 値の指定
    - Excel
    - YAML
  * - null（\ Java\ の\ null\ ）
    - セルに ``null``\ （大文字小文字不問）
    - アンクォートの ``null``\ （``"null"``\ でも同じ結果）
  * - 空文字
    - セルを空にする
    - ``""``
  * - 日付型カラムの空文字
    - セルを空にする（\ null\ 扱い）
    - ``""``\ （\ null\ 扱い）

期待値（\ ``EXPECTED_TABLE``\ ）を記述する際は、以下の点に注意する。

- カラムを省略すると、その列は比較の対象から外れる。検証したい列だけを書けばよい
- 期待側の行とデータベース側の行は、主キーの値で突き合わされる。このため主キーカラムだけは期待側でも省略できない
- データベース側に存在する行は、期待側に漏れなく記述する必要がある。記述されていないデータベース行が見つかると、余分な行がある旨のエラーになる（一部の行だけを検証対象にすることはできない）

.. important::

  主キーが自動採番（\ IDENTITY\ ・シーケンスなど）の場合、テスト実行時に払い出される値が不定になるため期待側に主キー値を書けず、複数行の検証が成立しない。テスト時に主キー値を既知にできる設計（業務キーの複合主キーなど）にしておく必要がある。

比較実行時のレコードの順序は、主キーを突合して比較されるため意識する必要はない。1つの読み込み単位に複数の ``EXPECTED_TABLE`` を記述することもでき、実行時には全て比較される。``java.sql.Timestamp``\ 型カラムの期待値のフォーマットは ``"yyyy-mm-dd hh:mm:ss.fffffffff"``\ （\ f\ はナノ秒9桁）であり、ナノ秒が設定されていない場合でも0ナノ秒として表示されるため、期待値には末尾に小数点とゼロを付与しておく必要がある（例: ``2010-01-01 12:34:56.0``\ ）。

.. _testdata_notation-column_omission:

カラムを省略する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
データベースの準備データ・期待値を記述する際、テストに関係のないカラムは記述を省略できる。省略したカラムには、テスティングフレームワークによりデフォルト値が設定されているものとして扱われる。これにより、テストデータの可読性が向上するとともに、テーブル定義が変更された場合でも、無関係なカラムであればテストデータの修正が不要になる。この機能は、多くのカラムのうち一部だけが更新される更新系テストケースで特に有効である。

.. important::

  データベースの検索結果の期待値を記述する際は、検索対象カラムを全て記述しなければならない（主キーだけを確認するといった部分的な確認方法は不可）。登録系テストの場合も、新規に登録されたレコードの全カラムを確認する必要があるため、カラムを省略できない。

準備データでカラムを省略する場合、省略したカラムにはデフォルト値が設定されているものとして扱われる。ただし主キーカラムは省略できない。期待値でカラムを省略した場合の挙動は、データタイプによって異なる。``EXPECTED_TABLE``\ では、省略したカラムは単純に比較対象外になる。一方、無関係なカラムが更新されていないことも確認したい更新系テストでは、``EXPECTED_TABLE``\ の代わりに ``EXPECTED_COMPLETE_TABLE``\ を使う。``EXPECTED_COMPLETE_TABLE``\ では、省略したカラムにはデフォルト値が格納されているものとして比較が行われる。

省略時のデフォルト値は、以下のとおりである（コンポーネント設定ファイルで明示的に指定していない場合の値であり、``BasicDefaultValues``\ クラスでカスタマイズできる）。

.. list-table::
  :header-rows: 1
  :widths: 40,60

  * - カラム型
    - デフォルト値
  * - 数値型
    - ``0``
  * - 固定長文字列型（\ CHAR\ ・\ NCHAR\ ）
    - 半角スペース\ ×\ カラム長
  * - 可変長文字列型（\ VARCHAR\ など）
    - ``" "``\ （半角スペース1文字）
  * - 日付型
    - \ epoch\ 起点（\ JVM\ のタイムゾーン設定に依存。\ JST\ 環境では\ ``"1970-01-01 09:00:00.0"``\ ）
  * - バイナリ型
    - 10バイトのゼロバイト列の\ HexString
  * - Boolean\ 型
    - ``"false"``

.. important::

  ``DATE``\ カラムのデフォルト値は、実行する\ JVM\ のタイムゾーン設定によって変わる値であり、\ JST\ 環境と\ UTC\ 環境とで異なる結果になる点に注意する。また\ Excel\ 形式では、同一シート内で ``EXPECTED_TABLE``\ と ``EXPECTED_COMPLETE_TABLE``\ を混在させると、後から出現するデータタイプ側が読み込まれずに終わる。データタイプごとにまとめて記述すること（\ YAML\ 形式は ``expected_tables``\ ・\ ``expected_complete_tables``\ がそれぞれ独立したキーのため、この制約を受けない）。

例えば「有効期限を過ぎたレコードは削除フラグが\ ``1``\ に更新されること」というテストケースで、テスト対象の機能に無関係なカラム（``COL_A``\ ～\ ``COL_D``\ ）を持つテーブルを扱う場合、全カラムを記載すると可読性が下がるうえ、テーブル定義の変更時に無関係な修正が発生する。関係のあるカラム（主キー・有効期限・削除フラグ）だけに絞り、期待値のデータタイプを ``EXPECTED_TABLE``\ から ``EXPECTED_COMPLETE_TABLE``\ に変えることで、省略したカラムにはデフォルト値が入っているものとして比較が行われ、無関係な列の変更有無まで含めて検証できる。

Excel\ ファイルに記述できるカラムのデータ型には制約がある。:java:extdoc:`SqlPStatement <nablarch.core.db.statement.SqlPStatement>` が対応している型のカラムのみをテストデータとして記述でき、それ以外のデータ型（例えば\ Oracle\ の\ ROWID\ や\ PostgreSQL\ の\ OID\ など）のカラムは記述できない。

検索結果・データベースの状態を期待値と比較する場合は、テストケース一覧のカラムに記載したグループIDで、それぞれのデータと紐付ける。

RESTful\ ウェブサービスのリクエスト単体テストでは、テストメソッドの名前でシートを用意し、``SETUP_TABLE``\ というデータタイプでテストメソッド単位のデータベース初期値を記述できる。ここに記載したデータは、テストメソッド実行時に投入される。

利用者が呼び出す入口の\ API\ （``TestDataParser``\ ）では、``EXPECTED_TABLE``\ と ``EXPECTED_COMPLETE_TABLE``\ は1つの取得結果にマージされる。後者は、省略カラムにデフォルト値を補完してから統合される。

実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。

.. _testdata_notation-list_map:

LIST_MAPのデータを記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストケース一覧は、``LIST_MAP``\ というデータタイプの利用例の1つである。ここでは\ ``LIST_MAP``\ 自体の記法を説明する。テストケース一覧（``testShots``\ ）が持つカラムの処理方式ごとの説明は、後続の\ :ref:`テストケース一覧（testShots）を記述する <testdata_notation-test_shots>`\ で行う。

キーバリュー形式の汎用データをまとめて記述したい場合は、``LIST_MAP``\ というデータタイプを使う。読み込むと、\ Java\ の ``List<Map<String, String>>``\ 形式のオブジェクトとして取得できる。テストケース一覧・リクエストパラメータ・期待値オブジェクト・期待ログなど、さまざまな用途で使われる。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - 1行目に ``LIST_MAP=``\ に続けてシート内で一意になる\ ID\ を記載する。2行目を\ Map\ のキー、3行目以降を\ Map\ の値として読み込む
  * - YAML
    - ``list_maps:``\ 下の、指定した\ ID\ を持つエントリに記載する

.. code-block:: yaml

  list_maps:
    - id: testShots
      rows:
        - no: "1"
          description: "正常系"
        - no: "2"
          description: "異常系"

以下のメソッドにより、シート名と\ ID\ を指定して\ List\ 形式または\ Map\ 形式でデータを取得できる。

- ``TestSupport#getListMap(String sheetName, String id)``
- ``DbAccessTestSupport#getListMap(String sheetName, String id)``

例えば、以下の表は、

.. list-table::
  :header-rows: 1
  :widths: 50,50

  * - empNo
    - expected
  * - 00001
    - 山田太郎
  * - 00002
    - 鈴木一郎

以下のコードで取得できる\ List\ と等価である。

.. code-block:: java

  List<Map<String, String>> list = new ArrayList<Map<String, String>>();
  Map<String, String> first = new HashMap<String, String>();
  first.put("empNo", "00001");
  first.put("expected", "山田太郎");
  list.add(first);
  Map<String, String> second = new HashMap<String, String>();
  second.put("empNo", "00002");
  second.put("expected", "鈴木一郎");
  list.add(second);

``LIST_MAP``\ のID\ は完全一致で検索される。同一ファイル内に同じ\ ID\ のエントリが複数ある場合は先着一致となり、2件目以降は無視される。指定した\ ID\ のエントリが存在しない場合は、エラーにはならず空データとして扱われる。この\ ID\ 解決規則は、\ ThreadContext\ に設定する値やログ検証データなど、``testShots``\ 以外の用途でも共通である。例えば、``ThreadContext``\ に設定する値（\ ``USER_ID``\ ・\ ``REQUEST_ID``\ ・\ ``LANG``\ など）や、期待するユーザ情報（漢字氏名・カナ氏名・メールアドレスなど）を保持する用途にも、同じ ``LIST_MAP``\ の書式を使う。

.. _testdata_notation-test_shots:

テストケース一覧（testShots）を記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

testShots本体を記述する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
``testShots``\ は、テストケース一覧を表す予約\ ID\ である。フレームワークがこの\ ID\ を持つデータブロックを自動的に読み込み、各エントリを1つのテストケースとして実行する。旧称の ``testCases``\ も動作するが、新規に作成する場合は ``testShots``\ を使う。テスト実行には ``testShots``\ に1件以上のエントリが必要であり、0件の場合はエラーになる。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - ``LIST_MAP=testShots``\ データブロックに記載する
  * - YAML
    - ``list_maps:``\ 下の ``id: testShots``\ エントリに記載する

``testShots``\ の1行が1つのテストケースに対応する。カラムには値を直接記述するものと、他のデータブロック（``LIST_MAP``\ やテーブル・ファイル・電文の各データブロック）のグループID・名前を参照するものがある。処理方式ごとに必須カラム・オプションカラムが定まっており、処理方式に対応するクラスは以下のとおりである。

.. list-table::
  :header-rows: 1
  :widths: 50,50

  * - 処理方式
    - 対応クラス
  * - ウェブアプリケーション
    - ``HttpRequestTestSupport``
  * - Nablarch\ バッチアプリケーション
    - ``BatchRequestTestSupport``
  * - メッセージング
    - ``MessagingRequestTestSupport``
  * - エンティティバリデーション
    - ``EntityTestSupport``

エンティティバリデーションを除く各処理方式に共通する必須カラムは、以下のとおりである。ここでの「必須」は、カラム自体を定義しておく必要があるという意味であり、値そのものは空でもよい。

.. list-table::
  :header-rows: 1
  :widths: 25,75

  * - カラム名
    - 説明
  * - ``no``
    - テストケース番号を1からの連番で記載する。空の場合はエラーになる
  * - ``description``
    - そのテストケースの説明を記載する（旧名 ``case``\ も可）。両方とも未定義の場合はエラーになる。ウェブアプリケーションのリクエスト単体テストでは、出力される\ HTML\ ダンプのファイル名にも使用される
  * - ``expectedStatusCode``
    - 期待するステータスコードを記載する（ウェブアプリケーションでは\ HTTP\ ステータスコード）

ウェブアプリケーションのカラムを記述する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
共通カラムに加えて、以下のカラムを使用できる。

.. list-table::
  :header-rows: 1
  :widths: 25,60,15

  * - カラム名
    - 説明
    - 必須
  * - ``context``
    - リクエストID・ユーザ情報を記載した ``LIST_MAP``\ 名。1エントリのみ有効。``REQUEST_ID``\ が空の場合は例外がスローされる
    - 必須
  * - ``HTTP_METHOD``
    - HTTP\ メソッドを記載する。空の場合は\ ``"POST"``\ が設定される
    -
  * - ``isValidToken``
    - CSRF\ トークン制御フラグ。``true``\ を指定したときのみトークンを設定する。それ以外（``false``\ ・空欄・``1``\ など）はトークンなしとして扱われる（``Boolean.parseBoolean``\ で評価）
    - 必須
  * - ``cookie``
    - 必要となる\ Cookie\ 情報を記載した ``LIST_MAP``\ 名。省略した場合は\ Cookie\ なしとして扱われる。指定した\ LIST_MAP\ が空の場合はエラーになる
    -
  * - ``queryParams``
    - 必要となるクエリパラメータ情報を記載した ``LIST_MAP``\ 名。省略した場合はパラメータなしとして扱われる。指定した\ LIST_MAP\ が空の場合はエラーになる
    -
  * - ``setUpDb``
    - この値と同じ名前を持つ読み込み単位内の全 ``SETUP_TABLE``\ を、テストメソッド開始前に1回だけ\ INSERT\ する。空の場合はスキップされる
    -
  * - ``setUpTable``
    - 同じグループIDを持つ ``SETUP_TABLE``\ を収集して\ INSERT\ する。空の場合はスキップされる
    -
  * - ``expectedStatusCode``
    - 期待するステータスコードを記載する
    - 必須
  * - ``expectedMessageId``
    - 出力されることを期待するメッセージ\ ID\ 。複数の場合はカンマ区切りで列挙する。空欄の場合にメッセージが出力されるとテスト失敗になる
    -
  * - ``expectedSearch``
    - 検索結果の期待値を記載した ``LIST_MAP``\ 名。空の場合はスキップされる。検索結果をリクエストスコープから取得する際の既定キーは\ ``searchResult``\ であり、``setSearchResultKey``\ で変更できる
    -
  * - ``expectedTable``
    - 期待するテーブルのグループID。同じグループIDを持つ ``EXPECTED_TABLE``\ ・\ ``EXPECTED_COMPLETE_TABLE``\ で検証する。空の場合はスキップされる
    -
  * - ``forwardUri``
    - 期待するフォワード先の\ URI\ を指定する。未指定の場合、\ JSP\ へのフォワードが発生しないことを検証する扱いになる
    - 必須
  * - ``expectedContentLength``\ ・\ ``expectedContentType``\ ・\ ``expectedContentFileName``
    - ファイルダウンロードのテストで使用する、期待するコンテンツレングス・コンテンツタイプ・コンテンツディスポジションのファイル名。空の場合はスキップされる
    -
  * - ``expectedMessage``\ ・\ ``responseMessage``
    - 同期応答メッセージ送信を行う場合の、期待する要求電文・返却する応答電文のグループID
    -
  * - ``expectedMessageByClient``\ ・\ ``responseMessageByClient``
    - HTTPメッセージ送信を行う場合の、期待する要求電文・返却する応答電文のグループID
    -

``requestParams``\ ・\ ``responseResult``\ は、``testShots``\ のカラムではなく、読み込み単位内に置く予約\ ID\ を持つ ``LIST_MAP``\ である。送信する\ HTTP\ リクエストパラメータは、``requestParams``\ という\ ID\ を持つ ``LIST_MAP``\ に、テストケース一覧と行単位で対応させて記載する。テストケース一覧の先頭行のテストケースには、リクエストパラメータ表の先頭行のデータが対応するというように、行の順序で結び付く。テストケースとの対応が分かりやすいよう、テストケース番号をマーカーカラム（後述）として記載するとよい。\ HTTP\ レスポンス（リクエストスコープ）の期待値も同様に、``responseResult``\ という\ ID\ を持つ ``LIST_MAP``\ に、行単位で対応させて記載する。``responseResult``\ を用意しない場合、この検証はスキップされる。

.. tip::

  リクエストパラメータは必ず記載する必要がある。初期画面表示のリクエストなど、リクエストパラメータが存在しない場合でも、``LIST_MAP=requestParams``\ には、テストケース番号の列だけを記載した列を用意し、テストケース数分の行を用意する。

1つのキーに対して複数の値を送信したい場合は、値をカンマ区切りで記述する。値にカンマそのものを含めたい場合は\ ``\``\ でエスケープし、``\``\ そのものを含めたい場合は\ ``\``\ 自身をエスケープして ``\\`` と記述する。

``isValidToken``\ に\ ``true``\ を設定した場合にトークンが検証される点については、二重サブミット防止の説明を参照。``expectedMessageByClient``\ ・\ ``responseMessageByClient``\ は、HTTPメッセージ送信を行う場合に使うカラムである。同一アクション内で\ MOM\ による同期応答メッセージ送信とHTTPメッセージ送信を同時に行う場合は、``expectedMessage``\ ・\ ``responseMessage``\ に\ MOM\ 側のグループIDを、``expectedMessageByClient``\ ・\ ``responseMessageByClient``\ に\ HTTP\ 側のグループIDを、それぞれ個別に指定する。

.. tip::

  グループIDは\ MOM\ による同期応答メッセージ送信と\ HTTP\ メッセージ送信でそれぞれ別の値を設定する必要がある。同一のグループIDを指定すると、正しく結果検証が行われない。

    - 同期応答メッセージ送信・HTTPメッセージ送信を行う場合の、期待する要求電文・返却する応答電文のグループID
    -

コマンドライン引数を指定する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
バッチ起動時のコマンドライン引数を指定するには、``args[n]``\ （添字\ n\ は0以上の整数）という形式でカラムを追加する。

.. important::

  添字\ n\ は連続した整数でなければならない。

テストケース一覧に上記以外のカラムを追加すると、そのカラムはコマンドラインオプションとみなされる。例えば ``paramA``\ ・\ ``paramB``\ というカラムに ``valueA``\ ・\ ``valueB``\ という値を記載すると、以下のコマンドラインオプションを指定したことになる。

.. code-block:: bash

  -paramA=valueA -paramB=valueB

メッセージングのカラムを記述する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
同期応答メッセージ受信・応答不要メッセージ受信などのメッセージング処理では、共通カラムに加えて以下のカラムを使用できる。

.. list-table::
  :header-rows: 1
  :widths: 25,55,20

  * - カラム名
    - 説明
    - 空の場合
  * - ``diConfig``
    - コンポーネント設定ファイルへのパスを記載する（必須）
    -
  * - ``requestPath``
    - 常駐プロセスを実行する際のリクエストパスを記載する（必須）
    -
  * - ``userId``
    - 実行ユーザ\ ID\ を記載する（必須）
    -
  * - ``setUpDb``
    - この値と同じ名前を持つ読み込み単位内の全 ``SETUP_TABLE``\ を、テストメソッド開始前に1回だけ\ INSERT\ する
    - スキップ
  * - ``setUpTable``
    - 同じグループIDを持つ ``SETUP_TABLE``\ を収集して\ INSERT\ する
    - スキップ
  * - ``expectedTable``
    - 同じグループIDを持つ ``EXPECTED_TABLE``\ ・\ ``EXPECTED_COMPLETE_TABLE``\ でデータベースを検証する
    - スキップ
  * - ``expectedMessage``
    - 同じグループIDを持つ要求電文のデータブロックで検証する
    - スキップ
  * - ``responseMessage``
    - 同じグループIDを持つ応答電文のデータブロックをレスポンスとして返す
    - スキップ
  * - ``expectedLog``
    - 期待するログメッセージを記載した ``LIST_MAP``\ の\ ID\ 。指定した\ LIST_MAP\ が空の場合はエラーになる
    - スキップ

期待するログメッセージは、``LIST_MAP=expectedLogMessages``\ として定義し、``logLevel``\ （期待するログレベル）と ``message1``\ （期待するログに含まれる文言。複数設定する場合は ``message2``\ ・\ ``message3``\ ...と連番で追加）のカラムをAND条件で評価する。

HTTP\ メッセージ受信では、共通カラムに加えて ``diConfig``\ ・\ ``requestPath``\ ・\ ``userId``\ （いずれも必須）を使用する。JSON\ ・\ XML\ データ形式を使用する場合、``expectedStatusCode``\ は空欄にする。

.. tip::

  JSON\ および\ XML\ データ形式を使用する場合、ステータスコードの比較も、電文のメッセージボディとの比較で行う。フレームワーク制御ヘッダもメッセージボディに含まれるためである。

エンティティバリデーションのカラムを記述する
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
エンティティバリデーションは、共通カラム（``no``\ ・\ ``description``\ ・\ ``expectedStatusCode``\ ）を使わない別体系であり、以下の必須カラムを持つ。

.. list-table::
  :header-rows: 1
  :widths: 30,70

  * - カラム名
    - 説明
  * - ``title``
    - テストケースの説明
  * - ``expectedMessageId1``
    - 期待するバリデーションメッセージ\ ID\ （複数ある場合は ``expectedMessageId2``\ ・\ ``expectedMessageId3``\ ...と連番で追加）
  * - ``propertyName1``
    - バリデーション対象のプロパティ名（同上、連番で追加可能）

このほか、``params``\ という予約\ ID\ を持つデータブロックに入力パラメータを定義する。``params``\ のエントリ数は、``testShots``\ の行数と一致している必要がある。

実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。

ファイルのデータを記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
固定長ファイル・可変長ファイルに対応するテストデータ（ファイルデータ）は、``SETUP_FIXED``\ ・\ ``EXPECTED_FIXED``\ （固定長）、``SETUP_VARIABLE``\ ・\ ``EXPECTED_VARIABLE``\ （可変長）のいずれかのデータタイプで記述する。ファイルデータブロックは、以下の順序で記述する。

.. code-block:: text

  ディレクティブ（0件以上）
    → レコード種別 + フィールド名称
      → データ型（各フィールドの型）
        → フィールド長（固定長のみ）
          → データ（1件以上）

各行の名称と役割は、以下のとおりである。

.. list-table::
  :header-rows: 1
  :widths: 30,70

  * - 用語
    - 定義
  * - レコード種別行
    - ファイルデータのレコード種別を示す行
  * - フィールド名称行
    - 各フィールド名称を並べた行
  * - データ型行
    - フィールドのデータ型を示す行（日本語表記の例: ``半角英字``\ ）
  * - フィールド長行
    - 各フィールドのバイト長を示す行（固定長ファイルのみ存在）
  * - データ行
    - 実データを並べた行
  * - パディング
    - フィールド長に対してデータのバイト長が短い場合に、データ型に応じて自動で補完される処理

Excel\ 形式では、以下の書式で記述する。

.. list-table::
  :header-rows: 0
  :widths: 25,25,25,25

  * - ``SETUP_FIXED[グループID]=ファイルパス``
    -
    -
    -
  * - ディレクティブ行
    -
    -
    -
  * - レコード種別
    - フィールド名称(1)
    - フィールド名称(2)
    - ...
  * -
    - データ型(1)
    - データ型(2)
    - ...
  * -
    - フィールド長(1)
    - フィールド長(2)
    - ...
  * -
    - データ(1-1)
    - データ(2-1)
    - ...
  * -
    - データ(1-2)
    - データ(2-2)
    - ...

.. list-table::
  :header-rows: 1
  :widths: 25,75

  * - 名称
    - 説明
  * - グループID
    - テストケース一覧の ``setUpFile``\ などに記載されたグループIDと紐付ける
  * - ファイルパス
    - カレントディレクトリからのファイルパス（ファイル名を含む）を記載する
  * - ディレクティブ行
    - ディレクティブを記載する。ディレクティブ名のセルの右のセルに設定値を記載する（複数行指定可）
  * - レコード種別
    - レコード種別を記載する。複数レコードレイアウトの場合は、この記述を連続して記載する
  * - フィールド名称
    - フィールドの数だけ記載する
  * - データ型
    - フィールドのデータ型を、``半角英字``\ のように日本語名称で記載する
  * - フィールド長
    - フィールドの数だけ記載する。``"-"``\ を指定すると、追加した全レコードの最大バイト長に自動拡張される
  * - データ
    - 複数レコード存在する場合は次の行に続けて記載する

.. important::

  1つのレコード種別において、フィールド名称に重複した名称は許容されない。例えば「氏名」というフィールドが2つ以上あってはならない（通常はこのような場合、「本会員氏名」「家族会員氏名」のように一意な名称を付ける）。異なるレコード種別間で同一の名称が存在するのは問題ない（例えばヘッダレコードとトレーラレコードにそれぞれ「件数」というフィールド名称があってもよい）。

.. tip::

  フィールド名称・データ型・フィールド長の記述は、外部インタフェース設計書からコピー＆ペーストすると効率よく作成できる（ペースト時に「行列を入れ替える」オプションを使う）。

可変長ファイルの準備も、固定長とほぼ同様である。固定長との違いは、可変長ファイルの場合はフィールド長行を記載しない点のみである。

.. tip::

  フィールド区切り文字を変更する場合は、``field-separator``\ ディレクティブを明示的に指定する。例えば区切り文字をタブにしたい場合は ``field-separator=\t``\ と指定する。

具体例として、ヘッダレコード1件・データレコード2件・トレーラレコード1件・エンドレコード1件で構成される会員データファイルを考える。文字コードは\ ``Windows-31J``\ 、レコード区切り文字は\ ``CRLF``\ とする。この例のように、1つのファイルデータブロック内に複数のレコードレイアウトを連続して記述すると、データの後ろに新たなレコード種別とフィールド名称を書いた時点で、新しいレコードレイアウトとして扱われる。

.. list-table::
  :header-rows: 1
  :widths: 20,25,25,30

  * - レコード種別
    - フィールド1
    - フィールド2
    - フィールド3
  * - ヘッダ
    - レコード区分（半角数字1桁）: ``0``
    - FILLER（半角10桁）
    -
  * - データ
    - レコード区分（半角数字1桁）: ``1``
    - 会員番号（半角数字10桁）: ``0000000001``
    - 入会日（半角数字8桁）: ``20100101``
  * - トレーラ
    - レコード区分（半角数字1桁）: ``8``
    - レコード件数（数値5桁）: ``2``
    - FILLER（半角4桁）
  * - エンド
    - レコード区分（半角数字1桁）: ``9``
    - FILLER（半角10桁）
    -

YAML\ 形式では、以下のように記述する。

.. code-block:: yaml

  setup_files:
    - path: work/input.txt
      type: fixed
      directives:
        text-encoding: MS932
      records:
        - record_type: DATA
          fields:
            - {name: USER_ID, type: 半角, length: 10}
            - {name: AMOUNT,  type: 数値, length: 10}
          rows:
            - ["001", "5000"]

- ``fields:``\ の各要素は ``{name: フィールド名, type: データ型, length: バイト長}``\ の形式
- ``type``\ は\ Excel\ と同じ日本語型名称で記述する（変換ツールも\ Excel\ の型名称をそのまま出力する）
- ``length``\ は整数（``length: 10``\ ）または文字列（``length: "10"``\ ）のどちらでも有効であり、変換ツールが生成した\ YAML\ は文字列形式になる
- ``rows:``\ の各行は配列形式で、``fields:``\ と同じ順序・同じ件数で値を並べる
- ``rows:``\ 内の値はダブルクォートで囲む

Excel\ 形式には固有の制約として、データの先頭要素を必ず空（\ null\ または空文字）にするというルールがある。\ YAML\ 形式にこの制約はない。

0バイトの空ファイルを表現するには、ディレクティブのみを記述してレコード定義を省略する。

.. code-block:: text

  SETUP_VARIABLE=work/members.csv

  text-encoding    Windows-31J
  record-separator CRLF
  // 空ファイル

固定長ファイルと可変長ファイルには、それぞれ固有の記法制約がある。固定長ファイルでは、フィールド名称・データ型・フィールド長の3リストが同サイズで必須であり、1ファイルデータブロック内の全レコード定義は同一レコード長でなければならない（違反時はエラー）。フィールド値がフィールド長を超えた場合もエラーになる。可変長ファイルでは、フィールド名称・データ型の2リストが同サイズで必須であり、フィールド長は不要である。可変長ファイルの空エントリ（先頭フィールドが空の行）はデータ行として扱われ、全フィールドが\ ``""``\ のレコードとして保持される。固定長ファイルの空エントリはスペースパディングされた定長レコードとして書き出される（この空エントリの扱いは、テーブルデータの空行のスキップとは異なる仕組みである）。

ファイルデータの記述時にエラーとなるのは、以下のようなケースである。

- 同一レコード種別内でフィールド名称が重複している
- フィールド名称リストまたはデータ型リストが未指定または空である
- フィールド名称・データ型・フィールド長リストのサイズが一致していない
- 存在しないフィールド名称を指定している
- データ要素数が不正である
- ディレクティブまたはレコード種別・フィールド名称定義の要素数が2未満である
- ファイルの読み込みに失敗した（\ IO\ エラー）
- 日付型カラムの値が日付として解析できない

パディングと、バイナリデータの記述方法は、以下のとおりである。指定したフィールド長に対してデータのバイト長が短い場合、そのフィールドのデータ型に応じたパディングが行われる（パディングのアルゴリズムは\ Nablarch Application Framework\ 本体と同様である）。バイナリデータは16進数形式で記述する。例えば ``0x1AB``\ と記述した場合、``0000 0001 1010 1011``\ （``0x01AB``\ ）という2バイトのバイト配列に解釈される。

.. tip::

  テストデータにプレフィックス\ ``0x``\ が付与されていない場合、そのデータは文字列とみなされ、ディレクティブの文字コードでエンコードされてバイト配列に変換される。例えば、文字コードが\ Windows-31J\ のファイルで、バイナリ型のフィールドに ``1AB``\ と記載した場合、3バイトのバイト配列に変換される。

準備用ファイルデータ（``SETUP_FIXED``\ ・\ ``SETUP_VARIABLE``\ ）は、固定長・可変長の区別なくまとめて収集される。期待値ファイル（``EXPECTED_FIXED``\ ・\ ``EXPECTED_VARIABLE``\ ）も同様である。固定長か可変長かは、データブロック内の記述で区別される。YAML\ 形式では、``setup_files``\ ・\ ``expected_files``\ の各エントリに ``path``\ キーが必須であり、省略するとエラーになる。利用者が呼び出す入口の\ API\ （``TestDataParser``\ ）の ``getSetupFile``\ メソッドでは、固定長（``SETUP_FIXED``\ ）と可変長（``SETUP_VARIABLE``\ ）がまとめて1つのファイルデータのリストとして返される。

期待するファイルの内容は、準備データと同じ書式で、データタイプだけを ``EXPECTED_FIXED``\ ・\ ``EXPECTED_VARIABLE``\ に変えて記述する。検索結果・データベースの状態と同様、グループIDでテストケース一覧と紐付ける。常駐バッチ・都度起動バッチのいずれでも、ファイルデータの記述方法は共通である。

ディレクティブは、ファイル・電文のフォーマットに関する属性を、キー名と値の2要素で記述するものである（最低2要素が必要）。既定値は、コンポーネント設定ファイルで\ map\ 形式によりまとめて指定することもできる。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - ファイルデータブロックの先頭（レコード定義より前）に ``| キー名 | 値 |``\ の形で記載する
  * - YAML
    - ``directives:``\ オブジェクトに ``key: value``\ 形式で記載する

固定長ファイルで有効なディレクティブキーは、以下の11個に限定される（無効なキーを指定するとエラーになる）。

.. list-table::
  :header-rows: 1
  :widths: 40,60

  * - ディレクティブキー
    - 説明
  * - ``file-type``
    - 自動設定される（``"Fixed"``\ ）。通常は記述不要
  * - ``text-encoding``
    - ファイルの文字エンコーディング
  * - ``record-length``
    - フィールド長合計から自動計算される。通常は記述不要
  * - ``record-separator``
    - レコード区切り文字
  * - ``positive-zone-sign-nibble``\ ・\ ``negative-zone-sign-nibble``
    - ゾーン10進数の正符号・負符号ニブル
  * - ``positive-pack-sign-nibble``\ ・\ ``negative-pack-sign-nibble``
    - パック10進数の正符号・負符号ニブル
  * - ``required-decimal-point``
    - 小数点を必須とするか（``true``\ / ``false``\ ）
  * - ``fixed-sign-position``
    - 符号を固定位置に置くか（``true``\ / ``false``\ ）
  * - ``required-plus-sign``
    - 正符号を出力するか（``true``\ / ``false``\ ）

可変長ファイルで有効なディレクティブキーは、以下の9個に限定される（無効なキーを指定するとエラーになる）。

.. list-table::
  :header-rows: 1
  :widths: 40,60

  * - ディレクティブキー
    - 説明
  * - ``file-type``
    - 自動設定される（``"Variable"``\ ）。通常は記述不要
  * - ``text-encoding``
    - ファイルの文字エンコーディング
  * - ``record-separator``
    - レコード区切り。``NONE``\ / ``CR``\ / ``LF``\ / ``CRLF``\ または任意のリテラル文字列が有効
  * - ``field-separator``
    - フィールド区切り文字。デフォルトは ``","``\ 。1文字のみ有効であり、2文字以上はエラーになる
  * - ``quoting-delimiter``
    - クォート文字
  * - ``ignore-blank-lines``
    - 空行を無視するか
  * - ``requires-title``
    - タイトル行の有無
  * - ``max-record-length``
    - レコードの最大長
  * - ``title-record-type-name``
    - タイトルレコードの種別名

フィールドのデータ型は、以下の日本語型名称で指定する（使用できない型名称を指定するとエラーになる）。

.. list-table::
  :header-rows: 1
  :widths: 45,15,40

  * - 型名称
    - 型記号
    - 用途
  * - ``半角英字``\ / ``半角数字``\ / ``半角記号``\ / ``半角カナ``\ / ``半角英数字``\ / ``半角英数字記号``\ / ``半角``
    - ``X``
    - 半角文字
  * - ``全角英字``\ / ``全角数字``\ / ``全角ひらがな``\ / ``全角カタカナ``\ / ``全角漢字``\ / ``全角``
    - ``N``
    - 全角文字
  * - ``全半角``
    - ``XN``
    - 全角・半角混在
  * - ``数値``\ / ``符号無ゾーン10進数``
    - ``Z``
    - ゾーン10進数（符号なし）
  * - ``符号付ゾーン10進数``
    - ``SZ``
    - ゾーン10進数（符号あり）
  * - ``符号無パック10進数``
    - ``P``
    - パック10進数（符号なし）
  * - ``符号付パック10進数``
    - ``SP``
    - パック10進数（符号あり）
  * - ``符号無数値``
    - ``X9``

  * - ``符号付数値``

    - ``B``

.. _testdata_notation-messaging_data:

メッセージングのデータを記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
メッセージング（MOMによるメッセージング・HTTPメッセージングなど）のテストデータでは、要求電文・応答電文を電文単位のデータブロックとして記述する。電文を構成する要素は、電文・要求電文・応答電文・フレームワーク制御ヘッダ・メッセージボディといった一般的な用語のほか、``setUpMessages``\ （メッセージング受信テストにおける要求電文\ ID\ 、固定値）・``expectedMessages``\ （同、応答電文期待値\ ID\ 、固定値）・``no``\ （複数電文送信時の連番・送信順序を示す電文内フィールド）というテスティングフレームワーク固有の予約語を使う。

``MESSAGE=setUpMessages``\ （要求電文）または ``MESSAGE=expectedMessages``\ （応答電文）として、テストの入力データ・期待値となる電文を定義する。先頭行の名前は固定であり、次行以降には、その電文全体で共通の値となるディレクティブとフレームワーク制御ヘッダを、キー・値の形式で記載する。フレームワーク制御ヘッダを解釈するためには、``FwHeaderDefinition``\ 実装クラスが ``fwHeaderDefinition``\ という名前でコンポーネント登録されていることが前提であり、異なる名前で登録している場合は ``getFwHeaderDefinitionName()``\ メソッドをオーバーライドする。同期応答メッセージ送信のテストデータファイルは、``sendSyncTestData/{requestId}/message``\ というパス（末尾の\ ``message``\ は固定のパスセグメント）に配置する。Excel\ 形式では ``MESSAGE=sendSyncTestData/{requestId}/message``\ をデータブロックの識別子として記載し、YAML\ 形式では ``messages:``\ の ``id:``\ に同じ文字列を指定する。

フレームワーク制御ヘッダ以降のメッセージボディは、1行目がフィールド名称（先頭セルは ``no``\ ）、2行目がデータ型、3行目がフィールド長、4行目以降がデータという構成である。

.. important::

  フィールド名称に重複した名称は許容されない。例えば「氏名」というフィールドが2つ以上あってはならない。

.. tip::

  JSON\ ・\ XML\ データ形式を使用する場合は、1シートに1テストケースのみ記述する。メッセージボディについて、各行の文字列長が同一であることを期待するというテスティングフレームワークの制約によるものであり、要求電文の長さがリクエストごとに異なるのが一般的な\ JSON\ ・\ XML\ 形式では、事実上1テストケースしか記述できない。

YAML\ 形式では、フレームワーク制御ヘッダを ``fw_header:``\ マップで記述する。``fw_header:``\ マップは ``messages``\ （``MESSAGE``\ ）でのみ使用し、``EXPECTED_REQUEST_HEADER_MESSAGES``\ ・\ ``EXPECTED_REQUEST_BODY_MESSAGES``\ ・\ ``RESPONSE_HEADER_MESSAGES``\ ・\ ``RESPONSE_BODY_MESSAGES``\ の4種では使わず、``requestId``\ などのヘッダフィールドも含めて ``records``\ の ``fields:``\ ・\ ``rows:``\ にフィールド単位で記載する（値の指定とフィールド単位の検証・生成というテスト手法の違いによる）。

.. list-table::
  :header-rows: 1
  :widths: 15,85

  * - 形式
    - 記述方法
  * - Excel
    - フィールド名称行（``no``\ 行）より前に ``| フィールド名 | 値 |``\ （ディレクティブと同じ「名前・値」形式）で記載する
  * - YAML
    - ``fw_header:``\ マップ（キー: 値）。キー名は固定ではなく、``reader.fwHeaderfields``\ の設定に合わせる

フレームワーク制御ヘッダのフィールド名はプロジェクトごとに異なる。既定値は ``requestId``\ ・\ ``userId``\ ・\ ``resendFlag``\ ・\ ``resultCode``\ の4種だが固定ではなく、``SystemRepository``\ の ``reader.fwHeaderfields``\ キーでプロジェクトが任意の名前に変更できる（例: ``reader.fwHeaderfields=requestId,addHeader``\ ）。

.. code-block:: yaml

  messages:
    - id: requestMessages
      directives:
        text-encoding: Windows-31J
      fw_header:
        requestId: hoge
        userId: moge
      records:
        - record_type: default
          fields:
            - {name: ユーザ名, type: 全角, length: 50}
            - {name: 備考,     type: 全角, length: 200}
          rows:
            - ["電文太郎", "特筆なし"]

``directives:``\ （``text-encoding``\ など）と ``fw_header:``\ （``requestId``\ など）は別キーである。Excel\ 形式ではどちらも「名前・値」の行だが、\ YAML\ 形式ではフレームワーク制御ヘッダを独立したキーとして分離する。``fw_header:``\ に記載したキーは全てフレームワーク制御ヘッダとして扱われ、``reader.fwHeaderfields``\ でフィルタして取り捨てられることはない。メッセージボディ側のフィールドは、従来どおり ``records:``\ の ``fields:``\ ・\ ``rows:``\ に記載する。``record_type``\ の値は、フレームワーク内部で常に ``"default"``\ に置き換えられる。\ Excel\ ・\ YAML\ とも任意の値を装飾的に記述できるが、実行時の挙動には影響しない。

.. important::

  旧版ではフレームワーク制御ヘッダを ``record_type: FW_HEADER``\ のレコードとして表していたが、現在の仕様ではフレームワーク制御ヘッダは ``fw_header:``\ マップで記述する。``record_type``\ に特別な予約値はない。

同期応答メッセージ送信では、要求電文の期待値と応答電文を、以下の4つのデータタイプで記述する。

.. list-table::
  :header-rows: 1
  :widths: 40,20,40

  * - データタイプ
    - 設定値
    - 用途
  * - ``EXPECTED_REQUEST_HEADER_MESSAGES``
    - リクエストID
    - 要求電文ヘッダの期待値
  * - ``EXPECTED_REQUEST_BODY_MESSAGES``
    - リクエストID
    - 要求電文本文の期待値
  * - ``RESPONSE_HEADER_MESSAGES``
    - リクエストID
    - 応答電文ヘッダデータ
  * - ``RESPONSE_BODY_MESSAGES``
    - リクエストID
    - 応答電文本文データ

グループID付きの書式例は ``EXPECTED_REQUEST_BODY_MESSAGES[グループID]=リクエストID``\ である。ディレクティブには、``file-type``\ （テスティングフレームワークが固定長のみに対応するため）と ``record-length``\ （フィールド長から自動計算されるため）を記載する必要はない。

.. tip::

  1セルに記述すると可読性が落ちるほど文字列が長い場合、``RESPONSE_BODY_MESSAGES``\ ・\ ``EXPECTED_REQUEST_BODY_MESSAGES``\ などの電文本文は、複数のフィールドに分割して記述できる。分割する際の各フィールド名は任意の文字列でよい。

.. tip::

  MOM\ による同期応答メッセージ送信では、要求電文と応答電文のヘッダ部に共通のフォーマットを使うのが一般的である。ボディ部については、要求電文と応答電文で異なるフォーマットを定義できる。

.. important::

  ``EXPECTED_REQUEST_HEADER_MESSAGES``\ と ``EXPECTED_REQUEST_BODY_MESSAGES``\ のエントリ数（``rows``\ 合計）は一致していなければならない（不一致時はエラー）。HTTPメッセージ送信の応答電文本文（``response_body_messages``\ ）は、各データエントリの文字列長が同一である必要がある。フィールド名称に重複は許容されない。複数レコード電文の場合は、ヘッダと本文を交互に記載する必要がある。``expectedMessage``\ ・\ ``responseMessage``\ が空欄のままメッセージ同期送信が行われた場合、テストは失敗する。

1つのリクエストIDで電文をN回送信する場合は、ヘッダ件数とボディ件数を共にN件ずつ記述する。noの値を変えて連続記述し、送信順序と\ no\ の値を一致させる。同一グループIDを持つ複数のメッセージプールを収集する場合、識別子の値をリクエストIDとして使用する。ステータスコードカラムがない場合は、デフォルト値 ``"200"``\ が\ Excel\ ・\ YAML\ 共通で使用される。フォーマット定義ファイルの命名は、応答電文が ``{requestId}_RECEIVE``\ 、要求電文が ``{requestId}_SEND``\ という規則に従う。

応答電文のアサート方式は、ディレクティブの ``file-type``\ の値、または\ ``SystemRepository``\ の ``messaging.assertAsMapFileType``\ キーの設定によって切り替わる。未設定時のデフォルトは ``"Fixed"``\ 形式（項目単位アサート）である。

.. list-table::
  :header-rows: 1
  :widths: 40,60

  * - ``file-type``\ の値
    - アサート方法
  * - ``Fixed``\ または指定なし
    - テストデータに記載された項目単位に電文を分割してアサートする
  * - その他の値
    - 電文全体を文字列として扱いアサートする

.. tip::

  JSON\ ・\ XML\ では電文ごとに電文長が異なるため、テストデータの内容に応じて電文長が自動計算される。テストデータの電文長に合わせて実際の電文を読み込むため、両者の電文長が異なると正常に読み込めない場合がある。そのため\ JSON\ ・\ XML\ を使用する場合は必ず ``file-type``\ を設定し、電文全体を文字列としてアサートを行う必要がある。

応答電文の表の先頭フィールドに ``errorMode:``\ から始まる特定の値を設定すると、障害系のテストを行える。値は、応答電文の表のヘッダおよび本文両方の、``no``\ を除く最初のフィールドに記載する。

.. list-table::
  :header-rows: 1
  :widths: 30,40,30

  * - 設定値
    - 障害内容
    - 動作
  * - ``errorMode:timeout``
    - メッセージ送信中にタイムアウトエラーが発生する場合のテスト
    - 処理方式に応じた例外（\ MOM\ 同期応答送信では\ ``MessageSendSyncTimeoutException``\ 、\ HTTP\ メッセージ送信では\ ``HttpMessagingTimeoutException``\ 。いずれも\ ``MessagingException``\ のサブクラス）を送出する。取引単体テストのモックアップクラスでは\ ``sendSync``\ メソッドの戻り値として\ null\ を返す
  * - ``errorMode:msgException``
    - メッセージ送受信エラーが発生する場合のテスト
    - ``MessagingException``\ をスローする

.. important::

  ``errorMode:``\ による障害系テストが機能するのは、応答電文（\ RESPONSE\ 系）およびモックアップクラス経由の送受信に限られる。``RequestTestingSendSyncSupport``\ （``GroupMessageParser``\ ）を使う経路では、``errorMode:``\ の指定は反映されない。

.. tip::

  業務アクション内で明示的に\ ``MessagingException``\ を制御していないのであれば、個別のリクエスト単体テストで障害系のテストを行う必要はない。

複数回電文を送信する場合は、同一データタイプ・同一リクエストIDのデータをそれぞれまとめて記述し、電文の長さを揃える必要がある（テストケース上、長さを揃えられない場合は手動でテストを行う）。送信対象のリクエストIDが複数存在する場合、送信順序のテストはできない。要求電文に複数のレコードが存在する場合、ヘッダを重複させずに1つのヘッダへ複数の業務データをまとめて記載したくなるが、フレームワークはヘッダとレコードを交互に記載する必要がある（ヘッダを重複定義しないと、業務データとヘッダの数が一致せずアサーションエラーになる）。

応答不要メッセージ受信では、応答電文が存在しないため、応答電文が期待値通りであることを確認する必要がない。期待するデータベースの状態のみ確認すればよく、``MESSAGE=expectedMessages``\ の記述は不要である。

同期応答メッセージ受信（常駐プロセス）における電文のパディング・バイナリデータの扱いも、前述のファイルデータの記法と同様である。

取引単体テストのモックアップクラスでは、応答電文・要求電文のフォーマットとデータを、シート名 ``message``\ 固定の1つのExcelファイルにまとめて定義する。識別子の書式（``EXPECTED_REQUEST_HEADER_MESSAGES=リクエストID``\ など、グループIDを持たない点が同期応答メッセージ送信のテストケースと異なる）でどの電文かを示し、データは応答電文の場合のみ記載する（要求電文はログ出力用のフォーマットのみを定義する）。障害系のテストも同様に ``errorMode:``\ の記法で行える。

実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。

値を特殊記法で記述する
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テストデータの値には、実際の値そのものだけでなく、特別な意味を持つ記法（特殊記法）を使える。パース処理では、読み込んだ各セル・エントリ値を、``Interpreter``\ のチェーンに順に通して変換する。特殊記法に該当する値だけが変換され、それ以外の値はどの\ ``Interpreter``\ にもマッチせずそのまま通る。チェーンに含まれる\ ``Interpreter``\ はDI設定で注入されるため、プロジェクトの設定によって追加・変更できる。

主な特殊記法は、以下のとおりである。

.. list-table::
  :header-rows: 1
  :widths: 25,30,30,15

  * - 値の種類
    - Excel\ での記述
    - YAML\ での記述
    - 備考
  * - 通常の文字列
    - ``abc``
    - ``"abc"``
    - YAML\ はクォート必須（型変換の防止）
  * - null（データベースに\ null\ を格納）
    - ``null``\ ・\ ``Null``\ （半角、大文字小文字不問）
    - ``null``\ （クォートなし）
    - YAML\ の ``"null"``\ （クォートあり）も同じ結果
  * - 文字列の\ null
    - ``"null"``\ ・\ ``"NULL"``\ （前後をダブルクォートで囲む）
    -
    - 前後のダブルクォート（全角・半角問わない）を除いた文字列として扱う
  * - 空文字
    - 空セル
    - ``""``
    -
  * - 先頭ゼロ付き数値
    - ``001``
    - ``"001"``
    - YAML\ でクォートなしだと ``1``\ に型変換される
  * - ``true``\ ・\ ``false``\ （文字列）
    - ``true``
    - ``"true"``
    - YAML\ でクォートなしだと真偽値に型変換される
  * - 半角スペース1文字
    - ``" "``\ （セルに ``"``\ ・スペース・``"``\ と入力）
    - ``" "``
    - 外側のクォートが除去されてスペースになる
  * - ダブルクォート1文字
    - ``"""``\ （セルに ``"``\ ・``"``\ ・``"``\ と入力）
    - ``'"'``\ （\ YAML\ シングルクォート）または ``"\""``
    -
  * - ``${systemTime}``\ ・\ ``${updateTime}``\ ・\ ``${setUpTime}``
    - ``${systemTime}``
    - ``"${systemTime}"``
    - 完全一致の場合のみ変換される
  * - ``${binaryFile:パス}``
    - ``${binaryFile:パス}``
    - ``"${binaryFile:パス}"``
    - パスはデータファイルのディレクトリからの相対パス
  * - ``${文字種,文字数}``
    - ``${半角英字,10}``
    - ``"${半角英字,10}"``
    -
  * - 改行文字
    - ``\r``\ （CR\ ）・\ ``\n``\ （LF\ ）
    - ``"\r"``\ ・\ ``"\n"``
    - デフォルト設定では\ CR\ のみが変換対象

YAML\ 形式では、``rows:``\ 内の全てのデータ値を必ずダブルクォートで囲む必要がある（クォートがないと\ SnakeYAML\ が数値・真偽値に型変換してしまう）。``null``\ のみクォートなしで記述する（``"null"``\ でも同じく\ Java\ の\ null\ になる）。``type:``\ ・\ ``record_type:``\ ・\ ``path:``\ などのスキーマ構造値にはクォートは不要である。

これらの記法を実現するインタープリタは、以下のとおりである。

.. list-table::
  :header-rows: 1
  :widths: 35,65

  * - インタープリタ
    - 変換内容
  * - ``NullInterpreter``
    - ``null``\ ・\ ``NULL``\ ・\ ``Null``\ （大文字小文字不問）を\ Java\ の\ null\ に変換する
  * - ``QuotationTrimmer``
    - 半角または全角ダブルクォートで前後が囲まれた場合のみ、外側1層を除去する。前後のダブルクォートは、``"ab"c"``\ が\ ``ab"c``\ になるように、値中のダブルクォートをエスケープせずそのまま扱う
  * - ``DateTimeInterpreter``
    - ``${systemTime}``\ ・\ ``${updateTime}``\ ・\ ``${setUpTime}``\ の完全一致のみを変換する。部分文字列は変換されない。文字列中の\ ``${...}``\ を置換するには ``CompositeInterpreter``\ との組み合わせが必要になる
  * - ``LineSeparatorInterpreter``
    - ``\r``\ をCR（``0x0D``\ ）に変換する（デフォルト設定）。``setMatchPattern``\ ・\ ``setLineSeparator``\ で変換対象・変換後の改行コードを変更できる
  * - ``BinaryFileInterpreter``
    - ``${binaryFile:パス}``\ でファイル内容をバイナリ読み込みし、\ HexString\ に変換する。パスはテストデータファイル（\ Excel\ ・\ YAML\ ）が置かれているディレクトリからの相対パス
  * - ``BasicJapaneseCharacterInterpreter``
    - ``${文字種,文字数}``\ 形式で、指定した文字種を指定した文字数分まで増幅した文字列を生成する
  * - ``CompositeInterpreter``
    - 文字列中の\ ``${...}``\ 要素を個別に解釈して置換する

``${systemTime}``\ はシステム日時（コンポーネント設定ファイルに設定された\ SystemTimeProvider\ 実装クラスから取得した\ Timestamp\ 、例: ``2011-04-11 01:23:45.0``\ 形式）に変換される。``${updateTime}``\ は\ ``${systemTime}``\ の別名であり、特にデータベースのタイムスタンプ更新時の期待値として使う。``${setUpTime}``\ は、データベースセットアップ時のタイムスタンプに決まった値を使いたい場合に使用する、コンポーネント設定ファイルに記載された固定値である。

``${文字種,文字数}``\ で使用できる文字種は、以下の14種類に限定される（それ以外を指定するとエラーになる）。

.. list-table::
  :header-rows: 1
  :widths: 100

  * - 使用できる文字種
  * - 半角英字 / 半角数字 / 半角記号 / 半角カナ / 全角英字 / 全角数字 / 全角ひらがな / 全角カタカナ / 全角漢字 / 全角記号その他 / 中国語 / サロゲートペア / 改行 / 外字

本記法は単独でも組み合わせても使用できる。例えば ``${半角英字,5}``\ は半角英字5文字に、``${半角数字,2}-${半角数字,4}``\ は\ ``-``\ 以外の部分が変換された文字列になる。

``${binaryFile:パス}``\ のパスは、テストデータファイルのディレクトリからの相対パスであり、Excel\ ・\ YAML\ どちらも同じ動作である（Excel\ では\ Excel\ ファイル、YAML\ では\ YAML\ ファイルが置かれているディレクトリが基準になる）。BLOB\ 列にファイルのデータを格納したい場合などに使用する。

日付は以下の形式で記述できる。

- ``yyyyMMddHHmmssSSS``
- ``yyyy-MM-dd HH:mm:ss.SSS``\ （\ JDBC\ タイムスタンプエスケープ形式）

時刻のミリ秒または全部を後置0埋めの形で省略できる。ミリ秒を省略した場合はミリ秒0として、時刻全部を省略した場合は0時0分0秒000として扱われる。例えば ``20210123123456``\ は「2021年1月23日 12時34分56秒000」と評価される。

.. important::

  ``java.sql.Timestamp``\ 型カラムの期待値は、末尾に ``.0``\ を付与する必要がある（例: ``"2010-01-01 12:34:56.0"``\ ）。末尾の ``.0``\ がないとアサートに失敗する。

セル内の改行（\ Alt+Enter\ ）は\ LF\ として扱われる。これはテスティングフレームワークとは関係のない\ Excel\ 自体の仕様であり、改行コード\ LF\ を表したい場合は、単にセル内で改行すればよい。

可変長ファイルなどで空行を表現したい場合は、特殊記法のダブルクォートを使って ``""``\ のように空文字列を記述する。

.. tip::

  空行を表現する際、行内の全セルを ``""``\ にする必要はなく、いずれか1つのセルに記述すれば十分である。読みやすさの観点からは、先頭のセルに ``""``\ を書く方法を勧める。

HTTP\ リクエストパラメータの値にアップロードファイルを指定したい場合は、値に ``${attach:ファイルパス}``\ と記述する。

.. tip::

  ファイルパスは、テスト実行時のカレントディレクトリ（プロジェクトルートディレクトリ）からの相対パスで記述する。

実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。

.. _testdata_notation-comment_and_marker:

コメント・マーカーカラム・空エントリを扱う
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
テーブルデータや\ ``LIST_MAP``\ のようにヘッダ行を持つデータブロックには、実際のデータには含めたくない情報を記述するための記法がいくつか用意されている。

セルの内容を ``//``\ で始めると、そのセルより右側は読み込み時に無視される。テストデータの値としては不要だが、読み手のために補足情報を残しておきたいときに使う機能である。例えば以下のように、2行目でテーブルの論理名を、末尾でレコードについての補足をコメントできる。

.. list-table::
  :header-rows: 1
  :widths: 20,20,20,20,20

  * - NO
    - FIRST_NAME
    - LAST_NAME
    - ADDRESS
    -
  * - // 番号
    - 名
    - 姓
    - 住所
    -
  * - 0001
    - Andres
    - Segovia
    - Spain
    -
  * - 0002
    - Julian
    - Bream
    - England
    - // このレコードが追加される

行全体をコメントとしてスキップしたい場合は、Excel\ では先頭要素を ``//``\ で始める。YAML\ では ``#``\ をコメント記号として使い、行頭・行末のどちらにも記載できる。Excel\ で先頭以外の要素が ``//``\ で始まる場合、その要素以降が切り捨てられる。YAML\ では、行末に ``#``\ を書くことで同等の記述ができる（例: ``NUMBER_COL: "100"  # 数値カラム``\ ）。

見出し行のカラム名を半角角括弧 ``[ ]``\ で囲むと、そのカラムは「マーカーカラム」として読み込み対象から除外される。Excel\ の見た目のためだけに存在する列を、実際のデータには含めないための仕組みである。

.. list-table::
  :header-rows: 1
  :widths: 50,50

  * - 形式
    - 除外対象
  * - Excel
    - ``SETUP_TABLE``\ ・\ ``EXPECTED_TABLE``\ ・\ ``LIST_MAP``\ すべて
  * - YAML
    - ``setup_tables``\ ・\ ``expected_tables``\ ・\ ``list_maps``\ すべて

例えば、以下のテストデータでは、半角角括弧で囲まれた ``[no]``\ カラムが無視されるため、テスト実行時には\ ``id``\ ・\ ``name``\ の2カラムだけを持つデータと等価になる。

.. list-table::
  :header-rows: 1
  :widths: 20,40,40

  * - [no]
    - id
    - name
  * - 1
    - U0001
    - 山田
  * - 2
    - U0002
    - 田中

ここでは ``LIST_MAP``\ の例を示したが、``SETUP_TABLE``\ ・\ ``EXPECTED_TABLE``\ など他のデータタイプでも同様に使用できる。

全要素が\ null\ または空文字のエントリは読み飛ばされる。Excel\ では行の全セルが空の場合、YAML\ では ``rows:``\ 内の要素が空マッピング（``{}``\ ）またはすべての値が空文字の場合にスキップされる。この空エントリの省略は、可変長ファイルの空行を ``""``\ で表現する記法（前述）とは別の仕組みであり、テーブルデータや\ ``LIST_MAP``\ のエントリ自体を無いものとして扱う点で異なる。

このほか、読み込み時には以下のような整形・補完が行われる。

.. list-table::
  :header-rows: 1
  :widths: 30,70

  * - 対象
    - 整形・補完の内容
  * - ファイル・メッセージ
    - 行末の空セルを取り除く
  * - メッセージ
    - レコード種別が空欄の行に、既定のレコード種別を補う
  * - テーブル
    - マーカーカラムを除外する（前述）
  * - テーブル
    - データベース登録時に、値が省略されたカラムへデフォルト値を補完する（前述）

実際の記述例は :ref:`テストデータの記載例 <testdata_examples>` を参照。
